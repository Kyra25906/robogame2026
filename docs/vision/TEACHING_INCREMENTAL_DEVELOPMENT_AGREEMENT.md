# RoboGame2026 教学式增量开发约定（供 Agent 交接）

## 1. 使用目的

本文是后续开发 Agent 的工作约定。目标有两个：

1. 按照可验证的小步迭代推进 RoboGame2026；
2. 让低年级本科生在开发过程中理解模块职责、数据流、设计取舍、失败边界和验收方法。

不要只交付最终代码，也不要逐行讲解所有语法。先用大白话说明问题，再引入必要的专业名词，并结合当前项目解释其实际作用。

本文不是某个 commit 的状态交接。开始工作前必须重新读取仓库当前状态和相关交接文档。

## 2. 每轮开始前必须做的检查

先进行只读检查，不要凭历史对话猜测当前代码：

```powershell
git branch --show-current
git rev-parse HEAD
git status --short
git diff --stat
```

然后阅读本轮相关的源码、测试、配置、任务清单和交接文档。视觉任务至少检查：

```text
docs/TODO_AND_ISSUES.md
docs/LEARNING_LOG.md
docs/vision/
ros2_ws/src/cube_perception/
tests/
```

检查后先说明：

- 当前分支和完整 commit SHA；
- 工作区是否有其他人或用户留下的修改；
- 本轮准备解决的一个最小问题；
- 本轮明确不做什么；
- 是否需要用户授权修改。

真实项目默认只读。用户明确说“修改、修复、开始实现、生成文档”后，才修改对应范围；授权不能扩大到无关模块。

## 3. 单轮增量原则

每轮只推进一个能独立验证的能力，例如：

- 只分析一种误检来源；
- 只增加一个候选过滤规则；
- 只补一种边界测试；
- 只生成一份验收报告。

不要在同一轮同时改 HSV、ROI、距离、时序规则和任务接口。否则测试失败时无法判断是哪项修改造成的。

推荐顺序：

```text
读取真实现状
→ 明确问题和可信事实
→ 建立可复现基线
→ 提出一个最小改动
→ 编写或补充单元测试
→ 实现改动
→ 运行针对性测试
→ 运行必要回归测试
→ 使用真实样本离线验收
→ 更新任务状态和交接证据
```

如果本轮只是“研究、审计或分析”，默认只读，不顺手修改代码。

## 4. 数据和可信边界

原始事实与程序判断必须分开保存：

```text
原视频/原照片        原始事实，不覆盖
检测 JSONL           算法输出
人工时间段标注       人工事实
HTML/Markdown 报告   汇总与解释
```

必须明确证据等级：

- mock 只能证明软件流程；
- 离线真实照片或视频只能证明这些样本上的表现；
- 未装车相机不能证明安装后的视角、振动、遮挡和曝光表现；
- 构建和单元测试通过只能写 `SOFTWARE TEST PASS`；
- ARM64 构建通过只能写 `ARM64 BUILD PASS`；
- 没有真实硬件闭环证据时，不得写 `HARDWARE PASS` 或 `REAL CAR PASS`。

视觉判断遵守：

- 看不到不等于稳定；
- 证据不足返回 `INCONCLUSIVE`；
- 状态过期或通信异常时不能继续累计稳定证据；
- field 模式不得接受 `mock_qualified` 作为真实证据；
- 稳定观察是在观察窗口内累计新鲜合格证据，不是简单 `sleep`；
- 撤退完成后才开始稳定观察。

报告必须分别写清“能证明什么”和“不能证明什么”。

## 5. 视觉模块当前工作边界

视觉工作优先限制在：

```text
ros2_ws/src/cube_perception/
视觉相关 tests/
docs/vision/
```

如需改动以下内容，先列出接口需求、原因和预期字段，不直接覆盖集成版本：

```text
ros2_ws/src/robogame_bringup/config/robot.yaml
launch 文件
ROS 消息接口
localization
mission_manager
robot_bridge
motion_control
机构协议
树莓派正式配置
```

未获得明确授权时：

- 不连接 STM32；
- 不启动 `robot_bridge`；
- 不运行整车或硬件 launch；
- 不发布 `cmd_vel`；
- 不调用抓取、放置或其他机构动作；
- 不在树莓派上把未提交代码作为唯一代码来源；
- 不合并 `main`；
- 不直接部署真车。

现场参数规则：

- 不猜最终 HSV、ROI、曝光和工作距离；
- 每次只改变一组参数；
- 保留调整前后的结果和报告；
- 相机安装位置改变后，重新确认视野、遮挡、ROI和标定适用性；
- 候选参数必须同时用正样本、负样本和边界样本检验。

## 6. 设计和实现要求

优先使用职责清楚的小模块和显式接口：

- 配置集中管理，不在多处散落常量；
- 业务模块通过参数或对象接收依赖，不自行创建重型外部服务；
- 入口文件只负责创建对象、连接依赖、控制主循环、管理状态和展示结果；
- 复杂筛选、存储协议和业务规则放入独立模块；
- 模块之间传递明确的数据对象，不直接控制对方的底层资源。

需要区分对象生命周期：

- 程序级：配置、服务、长期资源；
- 会话级：一个 workspace 或一次任务；
- 单次处理级：一帧、一个请求或一个视频片段。

错误处理必须回答：

1. 哪些原始事实仍然可信；
2. 哪些结果应继续保存；
3. 哪些状态不能更新；
4. 系统能否安全继续；
5. 应返回失败、取消还是 `INCONCLUSIVE`。

不要硬编码或打印密钥、令牌和敏感配置。外部服务应通过稳定接口接入，失败时不能破坏已保存的原始事实。

## 7. 测试分层和证据要求

测试按以下顺序推进：

1. 单元测试：测试一个模块的公共行为，不访问真实网络和硬件；
2. 模块集成测试：用 Fake 对象连接多个真实模块，验证调用顺序和状态传递；
3. 真实服务或真实样本测试：使用固定输入检查效果、格式、超时和失败；
4. 真实端到端验收：最后才连接真实相机、整车或其他硬件。

测试遵守：

- 使用 Arrange–Act–Assert；
- 一个测试只验证一个主要行为；
- 覆盖正常路径、边界条件和失败降级；
- 网络、模型和硬件使用 Fake；
- 文件测试使用临时目录；
- 测试公共接口，不绑定私有实现；
- 测试可重复运行且不依赖执行顺序；
- 新功能测试通过后运行旧测试，防止回归。

交付时必须给出：

- 完整测试命令；
- 实际通过的测试数量；
- 失败、跳过和警告数量；
- 使用的真实输入；
- 成功标准和失败标准；
- 测试能证明与不能证明的内容。

不能只写“测试通过”。

## 8. 每轮回答格式

每轮按以下顺序回答；研究轮可将“实现功能”写成“研究结果”，但不能省略验收边界。

### 8.1 目的

- 本轮解决什么真实问题；
- 完成后获得什么能力或认识；
- 为什么现在需要处理。

### 8.2 技术路线

- 用简短流程图或文字说明数据流；
- 列出涉及模块；
- 标出输入、处理和输出。

### 8.3 设计原因

- 为什么选择当前拆分；
- 有哪些替代方案；
- 当前方案做了什么取舍；
- 哪些判断仍需真实数据确认。

### 8.4 实现功能或研究结果

- 查看了哪些文件；
- 修改或新增了哪些文件；
- 每个模块、类或函数的职责；
- 实现了什么；
- 核心修改应直接展示准确代码或差异，不能只给文件链接；
- 没有修改时明确写“本轮只读”。

Python 代码必须放入代码围栏，确保以下内容不会被 Markdown 改写：

```python
__file__
__init__
__name__
"__main__"
```

### 8.5 本轮开发知识

- 先用直观语言解释；
- 再给出专业名词；
- 联系当前代码或数据说明实际作用；
- 不为了展示设计模式而强行套用设计模式。

适合结合实际问题逐步介绍：单一职责、依赖注入、分层架构、状态机、数据建模、可信边界、失败隔离、幂等性、状态一致性、缓存、HTTP、测试分层和评测指标。

### 8.6 验收方法

- 给出可在真实项目目录执行的准确命令；
- 写明预期输出和实际结果；
- 包含正常、边界和失败路径；
- 分开说明能证明和不能证明的内容。

### 8.7 下一步建议

- 只提出一个最小下一步；
- 说明本轮故意未做的事项；
- 如需跨模块改动，只列接口需求并等待确认。

最后用简短清单总结：

- 新增能力或认识；
- 已验证内容；
- 尚未包含内容；
- 下一轮目标。

## 9. 文件与 Git 交付规则

保留用户和其他 Agent 的现有文件。遇到脏工作区：

- 不删除、不覆盖、不回滚不属于本轮的修改；
- 只暂存本轮明确相关的文件；
- 提交前检查 `git diff`、`git diff --cached` 和文件清单；
- 不使用破坏性命令清理工作区；
- 不自动合并 `main`。

视觉普通 Git 提交不得包含：

- DOCX、PDF；
- `results/`；
- 原始照片和视频；
- 渲染目录；
- 临时提取文件；
- 与本轮交付无关的生成脚本；
- 个人资料或其他模块的未跟踪文件。

只有用户明确要求提交和推送时才执行。交付后返回：

- 远程分支名；
- 完整 40 位 commit SHA；
- 推送证据；
- 测试命令和测试数量；
- 新增依赖；
- `git status --short` 结果；
- 未提交文件的分类及原因；
- 是否属于部署阻塞项。

如果其他 Agent 在工作期间更新了 HEAD，先重新审计，不要覆盖或假定自己仍位于旧基线。

## 10. 真实环境验收触发条件

修改涉及真实相机、文件持久化、外部服务或主流程时，自动测试通过后应主动安排对应的真实环境验收，但不能擅自启动硬件。

验收前先说明：

- 使用什么真实输入；
- 数据是否外发及外发范围；
- 观察哪些指标；
- 成功和失败标准；
- 是否存在硬件动作风险。

验收后用终端输出、文件数量、JSONL 内容、报告、帧数或任务编号等证据更新状态。历史的一次授权不能视为长期授权。

## 11. 当前视觉研究的示例边界

以空场景橙色误检为例，正确的小步方式是：

```text
先只读统计误检
→ 确认物理来源和时间分布
→ 比较置信度、距离、位置等特征
→ 只提出一个候选过滤规则
→ 用户确认后实现
→ 补正常、边界和失败测试
→ 用原负样本与真实正样本回放对比
```

不能因为一段视频支持 `1.2 m` 工作距离候选，就直接宣称它是最终参数。它只能证明：在当前正负样本中，该值能够保留已采集正样本并过滤已观察到的远距离假候选。任务是否需要在更远处发现方块，仍要由整车任务设计确认。
