## 1. P0:field 模式下必然失败的阻塞缺陷

### P0-1:mission_manager 启动竞态 → 任务立即进入不可恢复的 FAILED

**现象**:field 模式上电后,mission 状态机在 SELF_CHECK 内收到第一条 `communication_ok=False` 的 `/robot/status`,立即 `fail(COMMUNICATION_ERROR)`,FAILED 为永久终态,运动决策/取存/建筑三大项全部 0 分。

**根因(已核实)**:
- `robogame_core/mission.py:80-81`:tick 开头 `if not communication_ok: return self.fail(...)`,对 SELF_CHECK 同样生效;
- `robogame_core/mission.py:82-83`:COMPLETE / FAILED / SAFE_STOP 为终态,不可恢复;
- `mission_manager/node.py:83-86`:SELF_CHECK 分支把 `self.status.communication_ok` 直接传入 tick;
- `robot_bridge/node.py:199,224`:真实模式上电 `_communication_ok=False`,握手(HELLO→ACK)+ 首条 0x12 解码成功才置 True(几十 ms ~ 3s×3 次重试);
- `robot_bridge/node.py:940,994`:第一条发布的 RobotStatus 必然携带 `communication_ok=False`。

**修复方案(设计)**:
1. 新增 `MissionState.WAIT_FOR_COMMUNICATION` 作为启动前置状态(或复用 SELF_CHECK 并增加"未就绪容忍"):在 `communication_ok=True` 之前,状态机保持等待、不评估、不 fail;
2. 给启动等待设上限参数(如 `startup_wait_timeout_s`,默认 15s,覆盖握手 3s×3 + 余量),超时才 `fail(COMMUNICATION_ERROR)`;
3. **运行时语义不变**:离开 SELF_CHECK 之后,`communication_ok=False` 仍按现有失败路径处理(心跳丢失=失败)。

**验证**:
- 单测(mock 时序):先发 `communication_ok=False` 状态 N 帧,再发 True,断言状态机进入 SELF_CHECK 并正常前进;False 持续超时才 fail;
- 行为测试:mission_manager 节点订阅 mock `/robot/status`,模拟「上电→握手→就绪」序列;
- 全量测试回归(当前基线 344 通过,2 error 为运动决策实质内容)。

### P0-2:没有任何相机节点

**现象**:`/camera/image_raw` 无人发布,manipulator_client 的 PICK_* 永远停在 WAITING_TARGET(`manipulator_client/node.py:511-516`),直到 12s 超时。

**根因(已核实)**:`hardware.launch.py` 启动了 robot_bridge / localization / motion_control / cube_perception / manipulator_client / mission_manager,唯独没有相机驱动节点。

**修复方案(设计)**:
1. 新增独立 `camera.launch.py`(usb_cam 或 v4l2_camera,取决于现场已装驱动与 GF100 相机),`hardware.launch.py` 以 include 方式挂入,便于现场按需启用;
2. 分辨率固定 **1280×720**,与 GF100 正式标定一致(ISSUE-014:fx≈2526.98,候选 focal_px=2550);
3. 提供 CameraInfo(经 camera_info_manager 或静态 yaml),使 cube_perception 有真实内参兜底,不再依赖 fallback;
4. **现场依赖**:确认相机 USB 设备路径(`v4l2-ctl --list-devices`)、驱动包安装(usb_cam/v4l2_camera)、安装高度/俯仰(ISSUE-002 遮挡关系)。

**验证**:launch 后 `ros2 topic hz /camera/image_raw`、`ros2 topic echo /camera/camera_info`;cube_perception 输出检测话题;标定内参与实际测距对比。

### P0-3:cube_perception 漏传 robot_field.yaml

**现象**:实机会用 `robot.yaml` 的 `fallback_focal_px: 700.0` 而不是标定的 2550.0。距离公式 `d = W·f/w`,焦距差 3.64 倍 → 真实 0.87m 被算成 0.24m,机器人在 87cm 外就判定"到位可抓",抓取对齐完全失效。

**根因(已核实)**:
- `hardware.launch.py:32`:`cube_perception` 仅 `parameters=[common]`;
- `robot_field.yaml:12-16`:`cube_perception.fallback_focal_px: 2550.0` 从未被加载;
- `robot.yaml:44`:`fallback_focal_px: 700.0`(开发兜底值)。

**修复方案**:`hardware.launch.py` 中 cube_perception 改为 `parameters=[common, field]`(与 robot_bridge、manipulator_client 的传参方式一致)。

**验证**:launch 后 `ros2 param get /cube_perception fallback_focal_px` 应输出 2550.0;配置一致性回归测试补一条「field 层视觉参数覆盖生效」;距离公式单测。

### P0-4:真实模式不支持 RETREAT,但放置流程必经它

**现象**:`manipulator_client._verify_place` 通过后必调 `_start_retreat()` → `/chassis/retreat`(机构服务)→ 真实分支返回 `error_code=9, "unsupported real mechanism command RETREAT"` → MECHANISM_ERROR。

**根因(已核实)**:
- `manipulator_client/node.py:313-318`(验证通过 → `_start_retreat`)、`:344-351`(请求 `/chassis/retreat`,command="RETREAT");
- `robot_bridge/node.py:524-535`:真实模式只映射 `GRAB / RELEASE / HOME`,其余命令 `error_code=9`;mock 模式允许集合 `{GRAB, RELEASE, STOP, RETREAT}`(`:548`);
- 责任边界早已在文档中定案:2026-08-15 结论「RETREAT 归底盘运动责任域,不发送机械协议命令」(TODO_AND_ISSUES.md P0-1A),当前实现未落实。

**修复方案(设计,推荐 A)**:
- **方案 A(推荐)**:field 模式 PLACE 流程在「RELEASE + 放置验证通过」后即成功返回,不再调用机构式撤退与客户端内稳定观察;撤退与稳定验证上移到 mission 级——状态机已有 `RETREAT → VERIFY_BUILD → COMPLETE`(`mission.py:135-140`),`mission_manager._dispatch` 已会把 `retreat_waypoint` 发到 `/motion/goal`(`mission_manager/node.py:70-71`),由 motion_control 执行导航撤退;
- **方案 B(备选)**:manipulator_client 改调 `/motion/goal` 请求导航撤退,并等待运动完成信号作为 `retreat_complete` 证据;
- mock 模式保留现有机构式流程(测试依赖),按 `runtime_mode` 分流;
- **需现场确认**:retreat_waypoint 实测坐标、撤退距离(车体脱离建筑 + 留出视觉观察视距)、停车精度。

**验证**:field 模拟闭环 PLACE → RETREAT → VERIFY_BUILD 全链路不触碰机构服务;mock 回归不变。

### P0-5:retreat_complete 在真实模式恒为 False

**现象**:即使补上 P0-4 的机制,WAITING_RETREAT_EVIDENCE(`manipulator_client/node.py:474-481`)也会卡到超时。

**根因(已核实)**:
- `robot_bridge/node.py:961`:`status.retreat_complete = self.mock_mechanism_state.retreat_complete` **无条件**读 mock 状态;
- `complete_mock_retreat()` 只在 mock 分支调用(`robot_bridge/node.py:564` 区域),真实模式 mock 状态永不更新 → 恒 False。

**修复方案(设计)**:与 P0-4 绑定。
- 若采用方案 A(撤退移出客户端):真实模式不再等待 `retreat_complete`,该问题自然消失,`retreat_complete` 字段语义改为「底盘运动完成信号」由运动链提供;
- 兜底约束:真实模式禁止无条件写 mock 状态值——mock 证据不得泄漏进 field 路径(与 ISSUE-012/ISSUE-019 同一原则)。

**验证**:field 模拟 PLACE 流程不再进入 WAITING_RETREAT_EVIDENCE;新增回归测试断言真实模式 `retreat_complete` 不来自 mock 状态。

### P0-6:field 的稳定性判定必然判失败

**现象**:`robot_field.yaml:10` 为 `placement_evidence_policy: unavailable`,配合 `robot.yaml:74` 的 `placement_max_unavailable_gap_s: 0.0`,稳定观察器必然 INCONCLUSIVE → 上层把 `INCONCLUSIVE` 归为 MECHANISM_ERROR → 建筑搭建失败。

**根因(已核实)**:
- `robogame_core/manipulator.py:75-148`:UNAVAILABLE 证据不推进 `qualified_since_s`(`:120-121` 只对 QUALIFIED 生效),且 gap=0.0 时把已累计的 `qualified_since_s` 清零(`:135-136`),观察超时后 `INCONCLUSIVE`(`:148`);
- `manipulator_client/node.py:389-390`:`_finish("INCONCLUSIVE: ...")`;
- `mission_manager/node.py:47-53`:`INCONCLUSIVE` 前缀不在 `MissionResult` 成员(`robogame_core/models.py:12-20`)→ 默认归类 `MECHANISM_ERROR` → `tick(action_failed=True)` → 重试耗尽 → FAILED。

**修复方案(设计,两层)**:
1. **短期(诚实且不判死)**:`MissionResult` 增加 `INCONCLUSIVE` 成员;mission_manager 对 `INCONCLUSIVE` 不做失败归类——进入 mission 级 `VERIFY_BUILD`(现有 3s 计时兜底,见 P1-4),而不是 MECHANISM_ERROR。同时**保持 `unavailable` 策略不变**(不伪造 STABLE,遵守 ISSUE-012 承诺);
2. **中期(真实证据)**:相机就位后引入真实视觉稳定证据(P0-2/P0-3 落地),policy 改为视觉判定,由 cube_perception VERIFY 阶段提供连续 3s 建筑未倒塌证据。

**验证**:单测「INCONCLUSIVE 不触发 MECHANISM_ERROR」;field 模拟 PLACE 后进入 VERIFY_BUILD 而非 FAILED;全量回归。

## 2. P1:规则明确提供/要求,当前零实现

### P1-1:巡线(规则 3.1.8,5cm 黑线连接启动区↔材料区↔搭建区)

- **现状**:无巡线实现,全靠轮式里程计积分,6 分钟必漂移。
- **方案**(按 TODO_AND_ISSUES.md「巡线归属与待办」,2026-08-17 已定案):
  1. `robogame_core/line_follow.py`:八路灰度原始值 → 横向偏差 + 纠偏输出 + `ON_LINE/LEFT/RIGHT/LOST` 状态机(参考 `navigation.py` 风格);
  2. `tests/test_line_follow.py`:合成数据单元测试(直行、左/右偏、出线、交叉口、恢复);
  3. 算法一接入:`motion_control`/`mission_manager` 把巡线作为「路段类型」接入路线选择(路段链、模式切换、与路点/视觉对准仲裁);
  4. **依赖电控**:确认八路巡线模块是否装车、接口电平、ADC 通道(`HAL_ADC_MODULE_ENABLED` 当前被注释禁用);冻结 V1「巡线遥测」字节布局后才做上送,不猜测载荷。

### P1-2:数字标签识别(规则 3.1.8,6 个 15×15cm 数字标签,墙上 40cm)

- **现状**:无标签识别,唯一的绝对定位源被放弃。
- **方案**:
  1. 确认标签样式(黑白 ArUco/AprilTag?数字牌?)、打印尺寸、安装位置与场地坐标映射表(现场测量);
  2. 新增标签检测(相机 + ArUco/AprilTag 或数字模板识别),输出标签 ID + 6DoF/位姿;
  3. 接入 `localization` 作为绝对矫正源:途经标签时修正 x/y/yaw(消除里程计积分漂移),或由 mission_manager 在路段切换时矫正;
  4. **依赖**:P0-2 相机就位 + 现场标签实测。

### P1-3:斜坡与高台(规则 3.1.5/3.1.6/3.1.7,材料区在中央高地:200mm 高台 + 1.8×0.8m 的 14° 斜坡)

- **现状**:定位纯 2D(x, y, yaw),控制器纯全向平面;爬坡打滑、俯仰导致视距失真、重心变化全无处理。
- **方案**(排在巡线、标签之后,报告建议顺序):
  1. 上坡/下坡作为「路段类型」纳入路线链(P1-1 的路段模型扩展);
  2. 俯仰补偿:IMU pitch 标定后用于视距校正(距离公式加俯仰项)与重心限制;
  3. 爬坡打滑检测:轮式里程计 vs IMU/期望速度差异超阈值 → 降速/停车;
  4. 上下坡限速限加速度、下坡防冲;
  5. **依赖**:IMU 真实可用(当前 `imu_valid=false`,见 2026-08-15 记录,需电控接入真实 IMU 驱动并标定轴向/零偏)。

### P1-4:建筑倒塌检测(规则 3.2.2 S4,「机器人与建筑不再接触后,建筑保持 3s 及以上不倒塌」)

- **现状**:`mission_manager/node.py:91-95` 的 VERIFY_BUILD 是**纯计时 3 秒**,不做任何观测、不检测倒塌。
- **方案**:
  1. 短期:VERIFY_BUILD 保留计时(配合 P0-6 的 INCONCLUSIVE 不判死),明确这是"诚实未证实",不伪造证据;
  2. 中期:相机就位后,VERIFY_BUILD 期间由 cube_perception 的 VERIFY 阶段连续观察建筑区域,检测「机器人脱离后 3s 内建筑未倒塌」,输出建筑存在/塌落判定;
  3. **接口扩展**:需要建筑区域检测(非方块检测)的视觉输出,并解决 ISSUE-002(相机安装高度/俯仰/机械臂遮挡)。
  4. **依赖**:P0-2 相机 + 相机安装位置冻结。

### P1-5:实测场地航点(规则 3.1 场地实测)

- **现状**:`robot.yaml:84-87` 四个 waypoint(`[1.0,0.5,0]` 等)是占位值,不是实测场地坐标,也没有上坡航段。
- **方案**:
  1. 现场实测:启动区、材料区(高台)、搭建区、撤退点的真实坐标与航向,回填 `robot_field.yaml`(field 层覆盖 mission_manager waypoints,不污染公共配置);
  2. 路线链增加上坡航段(结合 P1-3);
  3. 用真实定位驱动任务状态机完成连续自主运行(对应二审评分项「运动决策 20 分」的验收证据)。
