# 给电控组 / 机械组的最小请求单（2026-08-18）

> 用途：算法组把「必须由你们交付、算法无法替代」的事情压缩到最短清单。
> 已经砍掉的部分：凡是算法能自己想办法绕过的，都不在这张单子上了（见文末「我们已经自己扛下来的」）。
> 每项后面标注它解锁二审的多少分。

## 第 1 优先：STM32 非零速度限幅（解锁 60 分，其余全部等它）

**这是整个项目当前唯一的全局阻塞点。**

`chassis.h` 中三个常量目前都是 `0.0f`：

```c
CHASSIS_RPI_VX_LIMIT_MPS   0.0f
CHASSIS_RPI_VY_LIMIT_MPS   0.0f
CHASSIS_RPI_WZ_LIMIT_RADPS 0.0f
```

协议层与底盘控制层在限幅未就绪时**拒绝一切来自树莓派的自动速度命令**。也就是说：

- 上位机算法写得再完善，车也不会自主动一毫米；
- 二审评分里「运动决策 20 + 取存镖 20 + 建筑搭建 20 = 60 分」全部拿不到；
- 算法组**无法也不应该**绕过——`Chassis_RpiLimitsReady()`、`RPI_IsReady()`、`physical_start`、150ms 看门狗、急停锁存都是安全门，拆了会出伤人事故。

### 好消息：这比看起来简单得多

**遥控器下底盘和机械臂已经能动。** 这说明电机、驱动、接线、底盘麦轮解算、机械结构全部是通的——`0.0f` 挡住的只是「树莓派自动速度命令」这一条分支的**授权门**，不是能力问题。

**请电控确认一件事**：遥控路径和树莓派路径是否共用同一套底盘解算（`Chassis_` 那层）？

- **如果是**（大概率）：轮径、轮距、轮序、正方向**已经在遥控路径上验证过了**，不需要重新冻结。这项工作就只剩「填三个非零常量 + 重新烧录」。
- 如果不是：才需要按下面第 1 步补齐参数。

### 需要做的

1. （视上一条而定）确认轮径、轮距/轴距、四轮编号顺序、各轮正转方向——若遥控已在用同一套解算，直接沿用即可。
2. **填一组保守的首次限值**。不需要一步到位，建议起始：
   - `VX / VY` = 0.20 m/s
   - `WZ` = 0.50 rad/s
   联调稳定后再逐步放开，不必现在纠结最终值。
3. **重新编译、烧录**，并**记录 commit 与构建哈希**（不要直接改现场二进制而不留版本，见第 5 项）。
4. **架空复验**：上电默认未授权、HELLO/STATUS 正常、150ms 看门狗生效、STOP 锁存、拔线停车、重连不续跑。
5. 记录并告知：PB2 长按重新授权的现场操作步骤、指示状态、停止条件。
6. **遥控优先级保持不变**：自动模式开通后，遥控介入仍应能立即夺回控制权。这是现场的第二道人工保险，请勿为了自动化而弱化。

### 算法侧配合

我们会在 `docs/field/FIELD_DAY1_EXECUTION_ORDER.md` 的顺序下配合：先只读通信 30 分钟、再架空单轴验方向、再落地低速。**不会一上来就跑完整任务。**

## 第 2 优先：机构能重复抓放（解锁 40 分）

机械组交付「能稳定重复抓取和释放方块的夹爪/升降」，并填写机构冻结表实测值：

| 命令 | 需要的实测参数 |
|---|---|
| `GRAB` | 夹持行程、夹持力/限位、单次动作耗时、成功判据 |
| `LIFT_ABS` | 可达高度范围、精度、每层高度是否与 `[0.10, 0.20, 0.30]` 匹配 |
| `RELEASE` | 张开行程、释放后是否会带倒已放方块 |
| `HOME` | 归位耗时、归位后是否遮挡相机 |

**顺带需要一个答复（阻塞我们的状态机设计）**：机构上「从材料区取出」和「存入车体」是**一个动作还是两个动作**？目前代码里「存放」只是车载记账，没有独立入库动作。如果是两个，我们要加状态。

## 第 4 优先：补装红外巡线阵列 —— 请优先考虑直连树莓派（解锁运动决策精度）

巡线传感器要补装，这个躲不掉。但**接哪儿**有两个方案，差别很大：

### 方案甲（推荐）：数字红外阵列 → 树莓派 GPIO

选**板载比较器 + 电位器调阈值、输出 0/1** 的八路红外模块（TCRT5000 类）。

- **不改 STM32 固件、不动 ADC、不动串口协议** —— 完全绕开电控组当前卡住的那条链路；
- 电控只需要：确认接线与电平，其余由算法组写节点读 GPIO。

> ⚠️ **请电控务必先确认电平**：多数红外模块是 5V 供电 / 5V 逻辑输出，**树莓派 GPIO 只能接 3.3V，直接接会烧板**。要么选支持 3.3V 供电的模块，要么加电平转换或分压。**这一条确认前不要接线。**

### 方案乙：模拟灰度 → STM32 ADC → 串口遥测

需要电控启用 `HAL_ADC_MODULE_ENABLED`（当前被注释禁用）、与算法共同冻结 V1 巡线遥测字节布局、重新编译烧录。信息量略高一点，但外部依赖三重，且会和第 1 优先的固件改动排队。

**如果电控组当前排不开，请直接走甲。** 数字八路对巡线完全够用。

### 无论走哪个方案都需要的

- 模块装车位置与距地高度（典型 5–10mm）；
- 电位器阈值在**比赛场地实际黑线上**整定一次（不要在办公桌上调）。

## 我们已经自己扛下来的（不用你们操心）

为了把上面的单子压到最短，算法组把这些原本要依赖你们的事情改成自己解决：

- **巡线数据通路** → 走 GPIO 直连方案，**不需要你们开 ADC、冻结协议字节、重新烧录固件**（三项全免，只剩接线与电平确认）。
- **坡道 pitch 补偿** → IMU 不可用就降级为固定限速 + 里程计打滑检测，**不再等 IMU 标定**。
- **里程计漂移** → 用 AprilTag 绝对定位矫正，**降低对编码器精度的要求**。
- **第二个相机** → 单相机 + 阶段互斥（抓取段看方块、矫正时定点转向看标签），**不再要求加硬件**。
- **建筑倒塌判定** → 短期用计时兜底并诚实标注未证实，**不阻塞搭建流程**。
- **遥控下走不直、停车冲过头、位置飘** → 这些是**开环**的必然结果，自动模式下由闭环控制（里程计 + IMU + 视觉对准 + 巡线纠偏）解决，**不需要机械把底盘做到手动就很准**。

但有一件事算法补不了，请机械知悉：**机构末端的重复精度**。夹爪每次夹取位置飘、升降停不到指定高度，因为没有位置反馈，算法只能重试不能修正。对策是我们主动降低对它的要求（少搭一层、放置前视觉复核），但根治在机械。
