现场联调时逐项填写。每行一个待确认问题，答案由机械或电控负责人给出并签字。
"冻结"的意思是：填完以后三方都不能单方面修改，改任何一项都要重新确认。

## 一、夹爪

### 为什么这一节重要

夹爪是抓方块的手。如果不知道它张开多大、闭合多快、怎么判断"确实抓住了"，
软件就不知道什么时候该继续前进、什么时候该重试、什么时候该报故障。

**实际场景**：
- 软件发出"抓"命令后，夹爪开始闭合。但闭合不代表抓到——可能方块偏了，夹爪空闭合。
- 如果机械能提供一个独立信号（比如电流超过某个值、或者光电传感器被遮挡），软件才能确认"方块真的在手里"。
- 搬运过程中如果方块滑落，软件需要知道这件事，否则会去放置区放一个"空气方块"。

## 二、升降机构

### 为什么这一节重要

升降机构控制夹爪（和方块）的高度。三层塔需要把方块分别放到不同高度。
如果不知道零点在哪、升到目标高度要多久、断电会不会掉下来，软件规划的高度和时间全是错的。

**实际场景**：
- 上电后升降机构停在某个随机位置。软件需要知道"回零"流程——机构先降到底碰到限位开关，然后把这个位置定为 0 米。
- 软件说"升到 0.2 米"，如果机构实际到了 0.25 米，方块可能放不进去或者撞到上层。
- 如果断电时升降机构会自由下落，那已经放好的塔可能在断电瞬间全部倒塌。

| 编号 | 问题 | 为什么需要知道 | 答案 | 确认人 | 日期 |
|---|---|---|---|---|---|
| L-01 | 上电后升降机构怎样建立零点？是否需要自动回零？ | 没有零点，软件说的"升到0.2米"就没有参考基准 | _待填_ | | |
| L-02 | 回零流程需要多少秒？回零期间机器人能否移动？ | 影响任务启动总时间；如果回零时会碰撞，必须先抬升再移动 | _待填_ | | |
| L-03 | 升降机构的有效行程是多少？（从最低到最高能走多少米） | 软件请求的高度不能超过物理极限 | _待填_ | | |

| L-05 | `height_m` 这个值指的是哪个参考点的高度？（夹爪基准点/方块底面/机构滑块位置/其他） | 不同参考点差几厘米，放塔时会错层 | _待填_ | | |

## 三、底盘速度命令

### 为什么这一节重要

软件通过三个数字控制小车运动：前后速度、左右速度、旋转速度。
但电控可能把"正数"理解为不同方向。如果不确认清楚，软件说"前进"结果小车后退或横移。

**具体例子**：
- 软件发出 `vx=0.3`（意为前进 0.3 m/s）。如果电控把正 vx 理解为后退，车就往反方向走。
- 软件发出 `wz=1.0`（意为逆时针旋转 1 rad/s）。如果电控把正 wz 理解为顺时针，车就反着转。

| 编号 | 问题 | 为什么需要知道 | 答案 | 确认人 | 日期 |
|---|---|---|---|---|---|
| D-01 | 电控收到的 `vx` 单位是 m/s 吗？正方向是车头前方吗？ | 单位和方向错了，所有导航计算全错 | **已确认**：vx/vy=m/s，wz=rad/s。坐标系 ROS 惯例：+x 前、+y 左、+z 上、+wz 逆时针（俯视） | 电控组 | 2026-08-08 |
| D-02 | `vy` 单位是 m/s 吗？正方向是车体左方吗？ | 同上 | 同上，见 D-01 | | |
| D-03 | `wz` 单位是 rad/s 吗？正方向是逆时针吗？ | 同上 | 同上，见 D-01 | | |
| D-04 | 三个方向的最大速度分别是多少？ | 软件限速必须小于等于电控限速，否则命令会被电控拒绝或截断 | **待实测**：最大速度和加速度不写死在协议里，整车实测后确定 | | |
| D-05 | 三个方向的最大加速度分别是多少？ | 加速太猛车轮可能打滑或方块掉落 | 同上，见 D-04 | | |
| D-06 | 电控是否会对上位机发来的速度做二次限幅？ | 如果电控也限速，软件应该知道实际限速值 | **已确认**：STM32 端保留二次限幅和加速度限制，超限时以下位机限幅后值执行 | 电控组 | 2026-08-08 |
| D-07 | 速度命令期望的发送频率是多少？（20Hz / 50Hz / 其他） | 软件按这个频率发，太低电控可能认为通信断了 | **已确认**：50Hz。允许频率波动，下位机始终使用最近一帧有效指令 | 电控组 | 2026-08-08 |
| D-08 | 四轮编号和安装方向是怎样的？麦轮还是普通轮？ | 影响 vx/vy/wz 到各轮速度的转换公式 | **已确认**：麦轮。运动学解算在 STM32 内完成，上位机不直接发四轮转速。安装方向以最终装车为准 | 电控组 | 2026-08-08 |

## 四、通信失联与安全

### 为什么这一节重要

如果串口线松动、USB 被碰掉、或者上位机死机，小车必须自己停下来。
这个"自己停"的逻辑**必须在电控（MCU）上实现**，不能依赖软件发停止命令——因为软件已经死了。

**实际场景**：
- 小车正在以 0.5 m/s 前进，突然 USB 线被扯掉。上位机不再发送任何东西。
- 电控必须在极短时间内（比如 0.15 秒）检测到"收不到命令了"，然后主动把所有轮子速度归零。
- 如果电控不这样做，小车会保持最后一帧速度一直冲出去。

| 编号 | 问题 | 为什么需要知道 | 答案 | 确认人 | 日期 |
|---|---|---|---|---|---|
| C-01 | 电控连续多少毫秒没收到合法速度命令后，自动将速度归零？ | 越短越安全，但太短可能因正常通信抖动误触发。建议 ≤150ms | **已确认**：300ms。逻辑在 STM32 内独立完成，不依赖上位机 | 电控组 | 2026-08-08 |
| C-02 | 通信恢复后，电控会不会自动执行断线前的旧命令？ | 必须不能。否则插回 USB 后小车可能突然冲出去 | **已确认**：重连后需握手，握手完成前不接受运动命令。用 boot_id 区分重连/重启 | 电控组 | 2026-08-08 |
| C-03 | 硬件急停是否直接切断底盘电机和机构电源？（不经过软件判断） | 必须直接切断。这是安全链的最后一层，不能依赖任何代码 | **已确认**：急停硬件切断执行器动力电源。STM32 只读取急停反馈，通信仍在线时状态包主动上报 ESTOP | 电控组 | 2026-08-08 |
| C-04 | 急停按下后，上位机还能不能收到状态数据？ | 如果能收到，软件可以记录急停事件；如果不能，软件会看到通信中断 | **已确认**：若通信仍在，状态包主动上报 ESTOP | 电控组 | 2026-08-08 |
| C-05 | 电控收到 NaN、无穷大、超限速度或 CRC 校验失败的帧时怎样处理？ | 必须丢弃该帧，不能尝试执行 | **已确认**：CRC 错误帧直接丢弃，不更新控制目标。持续异常→看门狗触发停车 | 电控组 | 2026-08-08 |
| C-06 | 上电后、收到第一个合法命令前，电机是否默认锁定不能动？ | 必须锁定。防止上电瞬间的随机信号导致意外运动 | _待填_ | | |
| C-07 | 电控上是否有看门狗？看门狗复位后怎样报告原因？ | 看门狗是电控自己的保护：程序跑飞后自动重启。上位机需要知道是否发生过复位 | **已确认**：boot_id 变化表示 MCU 复位。上位机通过 boot_id 判断 | 电控组 | 2026-08-08 |

## 五、里程计（轮式编码器反馈）

### 为什么这一节重要

里程计告诉软件"小车实际走了多远、转了多少"。这是定位的基础。
如果不知道每个编码器脉冲对应多少米，或者正负号反了，定位会快速漂走。

**关键区别**：里程计是**测量值**（轮子实际转了多少），不是**命令值**（软件让轮子转多少）。
电控必须回传真实编码器数据，不能用上位机下发的目标速度反算一个假里程计。
否则软件看到"定位很准"，但实际上车轮在打滑，小车根本没动。

| 编号 | 问题 | 为什么需要知道 | 答案 | 确认人 | 日期 |
|---|---|---|---|---|---|
| O-01 | 电控回传的是四个轮子的原始编码器值，还是已经算好的 vx/vy/wz？ | 如果是原始值，上位机需要自己做运动学解算 | **已确认**：同时返回四轮累计编码器计数+四轮实际转速+解算后 vx/vy/wz。编码器单位为定时器计数值 | 电控组 | 2026-08-08 |
| O-02 | 编码器每圈脉冲数是多少？轮子直径是多少米？ | 用于把"脉冲数"换算成"走了多少米" | **待机械组**：轮径由机械组按实车实测后给定。换算系数由 PPR+减速比+轮径统一配置 | | |
| O-03 | 麦轮的轮距（左右轮间距）和轴距（前后轮间距）是多少？ | 用于 vy 和 wz 的解算 | **待机械组**：前后轮中心距和左右轮中心距需机械组按实车实测 | | |
| O-04 | 里程计数据的回传频率是多少？ | 影响定位更新的平滑度 | **已确认**：建议 100Hz。每帧带 seq 序号和 CRC | 电控组 | 2026-08-08 |
| O-05 | 里程计数据的时间戳是电控采样时刻还是上位机收到时刻？ | 如果时间戳不准，定位融合会有偏差 | **已确认**：MCU 采样时刻的单调递增 tick（ms/us）。首版不做绝对时钟同步，上位机记录 MCU tick↔本机时间对应关系用于时间对齐 | 电控组 | 2026-08-08 |
| O-06 | 上电或复位后里程计是否自动归零？ | 软件需要知道初始值 | **已确认**：MCU 上电/复位时归零；USB 重连不归零。通过 boot_id 变化判断是否复位 | 电控组 | 2026-08-08 |

## 六、IMU（惯性测量单元）

### 为什么这一节重要

IMU 测量旋转速度。轮式里程计在打滑或颠簸时会误判旋转，IMU 可以提供独立的角速度参考。
但 IMU 容易漂移（静止时也输出一个小数值），而且安装方向可能和车体坐标系不一致。

| 编号 | 问题 | 为什么需要知道 | 答案 | 确认人 | 日期 |
|---|---|---|---|---|---|
| I-01 | IMU 型号和量程是什么？ | 不同型号精度和漂移特性差异很大 | **已确认**：MPU6500 + IST8310。量程以固件初始化配置为准 | 电控组 | 2026-08-08 |
| I-02 | IMU 芯片在车上的物理安装方向是什么？（平放/竖放/倒装） | 安装方向决定 xyz 三轴和车体前后左右上下的对应关系 | **已确认**：固件统一转换到底盘坐标系后上传，上位机不直接接触芯片安装坐标 | 电控组 | 2026-08-08 |
| I-03 | 输出的角速度是原始值还是已换算为 rad/s？ | 如果是原始值，需要乘以比例系数 | **已确认**：三轴角速度(rad/s) + 三轴线加速度(m/s²) + 姿态四元数(x,y,z,w)。首版 MCU 不上传协方差 | 电控组 | 2026-08-08 |
| I-04 | 输出频率是多少？最坏情况下的延迟是多少？ | 影响融合算法的时间对齐 | **已确认**：建议 200Hz。正常延迟 <20ms（采样到上位机收到） | 电控组 | 2026-08-08 |
| I-05 | 是否做上电零偏校准？需要静止多久？ | 零偏是静止时的虚假读数。校准期间机器人不能动 | **已确认**：上电后静止零偏校准约 2s。CALIBRATING 标志，完成后置 IMU_VALID | 电控组 | 2026-08-08 |
| I-06 | 校准未完成时，IMU 数据是否可用？ | 如果不可用，定位应回退到纯里程计 | **已确认**：校准未完成时 IMU 标记 invalid，不参与融合。IMU 通信/自检失败置 IMU_FAULT | 电控组 | 2026-08-08 |
| I-07 | IMU 数据的时间戳来自 MCU 采样时刻还是上位机接收时刻？ | 同里程计，影响融合精度 | **已确认**：同里程计，MCU 采样时刻 tick。USB 重连不重新校准，仅 MCU 复位才重校准 | 电控组 | 2026-08-08 |

## 八、统一错误码

### 为什么这一节重要

当机构出问题时，电控应该返回一个数字（错误码），软件根据数字决定：重试、跳过、还是停车。
如果每方用自己的文字描述错误，软件无法自动判断严重程度。
