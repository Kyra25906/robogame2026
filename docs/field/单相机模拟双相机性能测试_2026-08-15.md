# 单相机模拟双相机性能测试

日期：2026-08-15（待执行）

## 1. 这份测试是做什么的

在决定"前后双相机"方案之前，先用**手头唯一的一个相机**测出树莓派能否扛住"两个检测节点同时运行"的算力压力。

双相机方案的真实压力 = **两个 `cube_perception` 节点同时跑 HSV+轮廓检测**。瓶颈在树莓派 CPU 跑检测算法，不在"插了几个物理相机"。因此用一个相机 + 两个检测节点（都订阅同一路图像），可以高保真近似双相机的 CPU 压力。

这份测试只回答一个问题：**树莓派 4B 跑两份检测，每份能否达到 ≥20 FPS（`docs/vision/VISION_MODULE.md` 的验收门槛）？**

## 2. 前置条件

- [ ] 树莓派已部署仓库代码并 `colcon build --symlink-install` 成功（`docs/field/RASPBERRY_PI_REAL_CAR_AGENT_HANDOFF_2026-08-12.md` 记录过：9 包 1min41s，333 项测试 OK）；
- [ ] `python3-opencv` 已安装（`docs/guides/GETTING_STARTED.md` 第 6 行列出）；
- [ ] 一个 GF100 USB 相机已插入并枚举成功（`/dev/video*` 可见；型号记录见 `docs/field/REAL_CAR_HARDWARE_PRELIMINARY_INVENTORY_2026-08-09.md`）；
- [ ] **已用 `v4l2-ctl --device=/dev/video0 --list-formats-ext` 枚举相机格式能力**。不要轻信标称帧率：GF100 实测 YUYV 下 1280×720 只有 10 fps（硬件限制），MJPG 下可达 60 fps。必须确认相机驱动实际用的是最优格式（优先 MJPG），否则测出来的是格式瓶颈不是算力瓶颈；
- [ ] 测试期间执行器不供电、车不动（只测算力，不测运动）；
- [ ] 相机通电后等待约 30 秒，曝光和白平衡稳定后再测（`docs/vision/GF100_DATA_COLLECTION_GUIDE_2026-08-11.md`）。

## 3. 测法原理

```text
树莓派 4B CPU
  ├── 节点 A：cube_perception（读相机图像）──→ /cubes        （模拟前相机）
  └── 节点 B：cube_perception（读同一图像）──→ /cubes/rear   （模拟后相机）

两个节点代码同构、参数同源，CPU 计算量与"两个相机各自一路"基本一致。
区别仅在图像解码份数（单相机只有一份），但解码比 HSV/轮廓检测轻，影响有限。
```

## 4. 测试步骤

### 步骤 1：基线——只跑一个检测节点

终端 1：

```bash
cd ~/robogame/ros2_ws
source /opt/ros/$ROS_DISTRO/setup.bash
source install/setup.bash

ros2 run cube_perception cube_perception \
  --ros-args \
  --params-file src/cube_perception/config/vision_gf100_1280x720_bench.json
```

> 若相机图像话题不是 `/camera/image_raw`（例如用了重映射的相机驱动），在命令里加：
> `--remap /camera/image_raw:=<实际图像话题> --remap /camera/camera_info:=<实际相机信息话题>`

终端 2（观察）：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source ~/robogame/ros2_ws/install/setup.bash

ros2 topic hz /cubes          # 记录检测发布频率（目标 ≥20 Hz）
top -d 1                      # 记录 python3 进程 CPU 占用
```

记录到结果表（第 6 节）：单节点 FPS、单节点 CPU%。

### 步骤 2：双节点——同一相机，第二个检测节点

在终端 1 **保持节点 A 运行**，开终端 3：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source ~/robogame/ros2_ws/install/setup.bash

ros2 run cube_perception cube_perception \
  --ros-args \
  --remap /cubes:=/cubes/rear \
  --params-file ~/robogame/ros2_ws/src/cube_perception/config/vision_gf100_1280x720_bench.json
```

> 注意：两个节点订阅同一 `/camera/image_raw`，所以第二个节点**不需要**重映射图像话题，只需把输出话题改成 `/cubes/rear` 以区分。

终端 4（观察）：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source ~/robogame/ros2_ws/install/setup.bash

ros2 topic hz /cubes /cubes/rear   # 同时看两个话题频率
top -d 1                           # 看总 CPU 占用和每个 python3 进程
```

### 步骤 3：记录并判定

对照第 5 节判定表。若双节点每路 <20 FPS 或 CPU 打满，按第 7 节降级决策处理。

### 步骤 4：收尾

- `Ctrl+C` 停止全部节点；
- 结果填入第 6 节表格，保存本文件或复制到 `results/`（不进入普通 Git）。

## 5. 判定标准

| 结果 | 判定 | 结论 |
|---|---|---|
| 双节点各自 ≥20 FPS，总 CPU 有余量 | ✅ PASS | 双相机方案算力可行 |
| 双节点各自 ≥20 FPS，但总 CPU ≥90% | ⚠️ 临界 | 可行但无余量，建议后相机降规格（见第 7 节） |
| 任一节点 <20 FPS | ❌ FAIL | 双相机需降级：后相机降分辨率/帧率，或阶段互斥只跑一个 |

> 20 FPS 门槛来源：`docs/vision/VISION_MODULE.md` 验收 gate "Average processing rate at least 20 FPS on the chosen upper computer"。

## 6. 结果记录表

### 6.1 实测结果（2026-08-15，树莓派 4B，GF100）

| 项目 | 值 | 备注 |
|---|---|---|
| 树莓派型号 | 4B（4 核） | 主机名 `robogame-t26-rpi4` |
| 相机型号 | GF100（USB 2.0，UVC） | `v4l2-ctl` 确认：MJPG 1280×720 最高 60fps；YUYV 1280×720 只有 10fps |
| 相机驱动 | usb_cam（`ros-jazzy-usb-cam`） | `pixel_format:=mjpeg2rgb`（v4l2_camera 的 MJPG 支持有 bug，不可用） |
| 分辨率 1280×720（YUYV，v4l2_camera） | 图像 10.0 fps，检测 10.0 fps | 相机 YUYV 硬件上限就是 10fps，非算力问题 |
| 分辨率 1280×720（MJPG，usb_cam） | 图像 12.7 fps | 瓶颈转移为算力：解压 119% + 检测 150% ≈ 270% CPU |
| **分辨率 640×480 @ 30fps（MJPG）** | **图像 ~30 fps，检测 30.0 fps** | **✅ 达标（>20fps 门槛）**；解压 26.5% + 检测 87.3% ≈ 114% CPU |
| 结论 | **PASS（640×480）** | 1280×720 FAIL，640×480 达标 |

### 6.2 关键推论

1. **单相机可用配置**：640×480 @ 30fps，检测 30fps、总 CPU ~114%，达到 `VISION_MODULE.md` 的 20fps 验收门槛；
2. **1280×720 不达标**：总 CPU 270%（解压 119% + 检测 150%），帧率被算力卡在 ~13fps——不是相机问题，是树莓派 4B 算力上限；
3. **双相机估算**：640×480 同时跑两个检测 ≈ 228% CPU，4 核内"放得下"但只剩 ~170% 给其他节点（定位/导航/任务/串口），接近满负荷，稳定性有风险；
4. **推荐双相机姿势**：阶段互斥——抓取阶段只跑前相机节点、回退阶段只跑后相机节点，任何时候只跑一个检测，CPU 等同单相机（~114%）；
5. **分辨率降级后焦距必须缩放**：检测从 1280×720 降到 640×480，`focal_px` 需从 2550 改为 ~1275（按分辨率比例减半），否则距离估算错误（本次只测性能未测距，接任务前必须处理）。

### 6.3 降分辨率 ≠ 重新标定（重要澄清）

降低工作分辨率后，**不是所有标定都要重做**，分三层：

| 层 | 之前做了什么 | 降分辨率后 | 需要重做吗 |
|---|---|---|---|
| **内参**（fx/fy/cx/cy/畸变） | ✅ 棋盘格标定过（`docs/vision/GF100_CAMERA_CALIBRATION_CANDIDATE_REPORT_2026-08-12.md`：fx≈2526.98, fy≈2539.21, cx≈620.62, cy≈355.66，RMS 0.82px；`focal_px=2550` 为台架候选值） | 相机/镜头/对焦没变，只是像素密度变了：1280→640 像素，每毫米像素数减半 | ❌ 不用重标，**按比例换算**：`focal_px = 2550 × (640/1280) = 1275` |
| **外参**（高度/俯角/安装位置） | ⚠️ **从未标定过**（一直标注"待现场确认"，见 `FIELD_DAY1_EXECUTION_ORDER.md:393-396`） | 若相机安装位置没动则不变 | 装车后必须现场实测记录（本来就欠着的活） |
| **颜色/形状参数**（HSV/面积阈值） | ⚠️ 台架值，未装车标定 | HSV 不随分辨率变；但 `min_area_px`/`min_side_px` 是像素值，分辨率减半后方块像素面积变为 1/4，**必须调** | 装车后现场调（`TODO_AND_ISSUES.md` P0 项） |

**为什么内参"换算"而不是"重标"**：内参（fx）描述的是镜头物理性质（每毫米多少像素），随"镜头+对焦"变，不随"输出分辨率"变。降分辨率只是把同一张图像用更少的像素表示——**相机没变，像素密度变了**。所以 2550→1275 是纯数学换算，不是重新做棋盘格标定。

**之前标定的意义（正面确认）**：证明了测距原理可行（0.5–1.0m 误差 0.45%）、HSV 颜色分割可行（橙/紫 30/30 检出）、建立了标定与验收工具链。它从来不是"装车标定"——文档一直诚实标注 `focal_px=2550` 为"台架候选值，非正式"。本次性能测试只是把"装车时用哪个分辨率"提前定了下来（640×480），不推翻之前的标定成果。

## 7. 若 FAIL 的降级决策

按代价从低到高：

| 优先级 | 手段 | 做法 | 保留什么 |
|---|---|---|---|
| 1 | 后相机降分辨率 | 后相机节点 `--width 640 --height 360`（或改配置），只做近距回退 | 20 FPS 门槛对主相机保留 |
| 2 | 后相机降帧率 | 后相机 15 fps（近距回退不需要 30） | 同上 |
| 3 | 阶段互斥 | 抓取阶段只跑前相机节点，回退阶段只跑后相机节点，不同时跑（任务阶段互斥，见 `manipulator_client` 的阶段设计） | 双相机功能全保留，代价是切换延迟 |
| 4 | 放弃双相机 | 回到单相机 + 掉头纠偏方案 | 需要巡线/标签代码 |

## 8. 本测试测不到的东西（诚实边界）

| 测不到 | 原因 | 风险评估 |
|---|---|---|
| 双路 USB 带宽/中断压力 | 一个相机只有一路 USB 流 | 低（2 路 720p MJPEG ≈10-20 Mbps，远小于 USB 2.0 的 480 Mbps） |
| 双路图像解码压力 | 两节点读同一份图像，解码只有一份 | 低（解码比检测轻） |
| 阶段互斥逻辑正确性 | 这是代码逻辑问题，不是性能问题 | 用代码测试覆盖，不属于本性能测试 |

## 9. 结论怎么写

### 9.1 本测试实际结论（2026-08-15 已填）

**树莓派 4B + GF100，单相机 640×480 @ 30fps（MJPG）达标：检测 30fps、总 CPU ~114%，满足 20fps 验收门槛。** 视觉工作分辨率建议定为 640×480。

**1280×720 不达标**（~13fps、CPU 270%），原因有二：相机 YUYV 硬件上限 10fps、MJPG 下树莓派解压+检测算力饱和。二者都非相机故障。

**双相机**：640×480 同时跑约 228% CPU 放得下但余量紧；推荐阶段互斥（任何时候只跑一个检测节点），CPU 等同单相机。

**后续必做**：`focal_px` 按分辨率缩放（2550 → ~1275）；如需双相机，按阶段互斥设计并单独验证切换逻辑。
3. 是否据此确认"前后双相机"方案，或回到单相机+纠偏。

> 本测试只回答算力可行性。双相机方案的完整决策还要看：后相机安装几何、`CubeDetection` 消息是否需要来源字段（建议用 `/cubes/front` + `/cubes/rear` 分话题，不改消息）、机械组能否提供第二台相机。
