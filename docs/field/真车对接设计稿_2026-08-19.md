## 1. 一句话真车模型

> **无横移、无升降、机械臂全开环（无反馈）的麦轮小车：鼻朝前开到材料区，前向相机对准，右侧抓取，云盘转 90° 放进车尾框，开到搭建区出库，在车尾搭方块——相机永远只看前方，其余靠转车和传感器。**

| 项 | 值 |

## 3. 任务流程与状态机

### 3.1 现版流程（定稿）

```
巡线 → 车停（材料区在正前方）→ 相机对准（S-1/S-3）
→ 右侧抓取（底盘锁死）
→ 云盘转 90° 入库车尾框（入库 = 第二个物理动作）
→ 行驶到搭建区（爪收回安全姿势）
→ 出库（从车尾框取出 = 第三个物理动作）
→ 车尾搭建（单层地面放置）
→ 转车 180° 回头验证
→ 撤退
```

### 3.2 状态机（基于现有 `MissionState`，新增 3 个状态）

现有状态：`WAIT_FOR_COMMUNICATION / SELF_CHECK / WAIT_FOR_PHYSICAL_START / GO_TO_* / PICK_* / PLACE_* / RETREAT / VERIFY_BUILD / SAFE_STOP / COMPLETE / FAILED`（✏️ 2026-09-18 补：还有 B1 起新增的 **`ROUTE_RUNNING`**——比赛主状态，绑定 `RoutePlan` 后走它，未绑定才走下面的旧演示流程，`robogame_core/mission.py:20`）

| 新增状态 | 含义 | 谁动 | 说明 |
|---|---|---|---|
| `APPROACH_ALIGN` | 视觉对准：方块"走到"画面 ☆ | 车 | S-3 闭环；或 S-1 前向对准后转 90° |
| `STOW` | 云盘转 90° + RELEASE 入车尾框 | 臂 | 替代原"车载记账"，真实入库动作 |
| `UNSTOW` | 云盘转出库位 + GRAB 抓车尾框方块 | 臂 | 真实出库动作 |

现有 `PLACE_*` 语义改为：云盘转搭建位 + RELEASE + 停留 + 相机复核（无升降，`place_heights_m` 退化为单层地面值）。`PICK_*` 语义改为：车锁死后云盘转抓取位 + GRAB。

> ⚠️ 未来 D-1 前抓方案落地时：只改「对准模块 + 配置参数（grab_side / swing_deg）」，状态机骨架不变——抓取方向/云盘摆动角必须做成配置参数而非硬编码。

## 4. 动作序列与互锁

### 4.1 铁律

> **车动臂不动，臂动车不动。**

### 4.2 动作序列

| 阶段 | 谁动 | 动作 | 互锁 |
|---|---|---|---|
| 导航/巡线 | 车 | 巡线+标签矫正 | 臂保持「安全收回姿势」（待机械给） |
| APPROACH_ALIGN | 车 | S-3 视觉闭环开向 ☆（或 S-1 前向对准） | 臂不动 |
| PICK | 臂 | 车锁死 → 云盘转抓取位 → GRAB → 等待 → 相机复核 | **抓取时底盘速度必须为 0**（电控硬要求） |
| STOW | 臂 | 云盘转 90°（右侧弧）→ 车尾框上方 → RELEASE → 停留 | 车不动 |
| GO_TO_BUILD | 车 | 行驶 | 臂收回安全姿势 |
| UNSTOW | 臂 | 车锁死 → 云盘转出库位 → GRAB | 车不动 |
| REAR_PLACE | 臂 | 云盘转搭建位 → RELEASE → 停留 | 车不动 |
| VERIFY_BUILD | 车 | 转 180° 回头，相机复核 | 臂收回 |
| RETREAT | 车 | 回安全区 | 臂收回 |

### 4.3 软件互锁清单（必须实现）

1. 底盘运动期间禁止一切机构动作；
2. GRAB/UNSTOW 前底盘速度必须为 0（C-5/C-8，电控硬要求）；
3. VY 恒 0（C-6）——**⚠️ 尚未实现**：软件仍会下发 vy，见文末「2026-09-18 更正（软件侧事实）」（2026-09-18 核对）；
4. LIFT 禁用（C-3）；
5. 云盘角度只在「右侧↔车尾」工作弧内下发，越界拒绝（C-10）。

## 6. 相机方案决策链（汇总）

### 6.1 候选对比（8 个）

| 候选 | 原理 | 优 | 劣 | 生死判据 |
|---|---|---|---|---|
| **D-4 云盘随动相机 ★** | 相机与臂同向装云盘/臂上：行驶朝前（导航/标签）、抓取朝右（正对抓取点，无 49° 几何）、搭建朝后（复核/验证） | **单相机、零新增机构（云盘即云台）、三个方向全覆盖、抓取 ☆ 在画面中心、比 D-2/D-3 少机构少穿线** | 判据①（行驶臂朝前）**✓ 已确认（C-18，云盘可转任意角度）**；剩② 安装点不被臂挡 ③ 走线穿云盘；云盘开环→三固定姿势各一次性标定；行驶振动 | 问机械：安装点/遮挡？走线可行？ |
| A 固定+转车（S-1） | 前方对准→转90°→开环抓 | 零硬件；改动小 | 转后开环；依赖转向精度 | S-2：转90° 误差 ≤ ±2° 且转后方块 ≤ 270mm+爪长 |
| **B 对角线伺服（S-3）** | ☆标定+视觉伺服，方块走到☆就停 | **零硬件；全程闭环；不依赖转向** | ☆ 必须在视野——**普通前向安装看不到**（夹角 ≈49°，需 ≥100~120° 视场=广角/偏转安装/抓取姿势前倾）；逼近不能出画；近距对焦 | 拍照：抓取点在画面内、远到近看得见、不糊、不被挡；不在→广角/偏转安装/E/D |
| C 广角（S-4） | 加宽视野让☆入画 | 无运动件；单相机 | 边缘畸变砸中☆；每度像素减半；重标定一串活 | 广角照片跑检测器，抓取点位置误差 ≤ 容差 |
| D-2 舵机云台 | 单相机转前/右/后 | **一相机看三方向**；可重复±1°；免转车验证 | 新机构；挡臂摆动路径；振动；坐标标定 | A/B 失败后能装机构+标定（D-4 出现后优先级下降：云盘即云台） |
| E 眼在手（单相机版） | 相机搬腕部，臂视觉伺服对准抓取 | **不依赖转车精度、不依赖抓取点在固定相机视野**（腕相机近距直接看）；车只粗定位；精度最高 | ① 臂视觉伺服闭环性能待实测（开环臂的重复性/响应）② 预定位交接（臂先摆到"方块大概在那"让相机看到）③ 走线穿旋转云盘 ④ 导航角色：腕相机能否兼职前视（否则放弃标签矫正或回双相机） | arm.c 就绪后实测视觉伺服能否稳定收敛 |
| F 半盲抓取（兜底） | 地图停车+固定偏移开环抓 | 抓取段不用视觉 | 停车横向误差无法修正；成功率低 | 停车横向偏差 ≤ 容差窗口 |
| G 双相机（对照） | 前+后/侧各一颗 | 简单直接 | 推翻单相机决定；两套标定；Pi 负载翻倍 | 不建议 |

> 几何结论（定死，无需测量）：正前安装的普通相机（60~90° 视场）看不到垂直正右侧抓取点（车中心→右侧 270mm、相机→车头 237mm，夹角 ≈49°）。**固定相机家族（A/B/C 固定版）在抓取段出局**——除非广角/偏转安装/抓取姿势前倾。

### 6.2 决策树（判据驱动）

```
① 问机械：D-4 可行吗？（行驶臂朝前 + 相机安装点不被臂挡 + 走线穿云盘）
├─ 行 → D-4 定案：单相机随臂，全部视角解决，抓取 ☆ 在画面中心
└─ 不行 ↓
② 拍照：固定相机视野里能看到抓取点吗？
├─ 看得见 → B（S-3）★ 零硬件闭环（闭环在车）
└─ 看不见 ↓
③ 愿意把闭环放在臂上（相机搬腕部，臂视觉伺服）吗？
├─ 愿意 → E 眼在手（车粗停+臂细对；判据=arm.c 就绪后视觉伺服收敛实测）
└─ 不愿意 ↓
④ S-2 实测：原地转 90° 误差
├─ ≤ ±2° → A（S-1）转车开环抓
└─ > ±2° ↓
⑤ 愿意加硬件吗？
├─ 接受畸变标定 → C 广角 + B
├─ 能装舵机云台 → D-2 云台
└─ 都不愿意 → F 半盲兜底（成功率低，跑得了的底线）
```

> 注：B 与 E 是两种闭环落点（闭环在车 vs 闭环在臂），非竞争关系，可组合（B 粗逼近 + E 精抓取 = 工业标准，代价是双相机）。arm.c 未就绪对全部候选一视同仁，不构成任何候选的专属降级理由。

### 6.3 风险最小路径

默认按 **B** 设计（零硬件、闭环、判据最容易测）；**A** 作 B 失败的备用（也零硬件，先过 S-2）；**F** 作双失败底线（保比赛能跑）；C/D 是升级选项，E/G 是未来选项，现在都不投入。

### 6.4 原则链（P-1 → S-5）

```
P-1 误差预算：开环节误差加总 < 容差窗口即可用；可重复开环可标定；测量链路上的开环误差×距离放大
  → S-5 相机只看前方（巡线→红外，抓取→S-1/S-3，验证→转车回头）
  → S-2 实测转车精度 → 决策树 6.2
```

## 11. 2026-09-18 更正（软件侧事实）：硬件「不能横移」≠ 软件不输出 vy

> 本节由 2026-09-18 只读代码核对追加，**不改动上文任何冻结结论**；对应上文 §2.1 表的「左右平移」行与 §4.3 互锁第 3 条。

- **硬件结论保留**：真车**左右平移不可用**（偏差过大，C-6，机械当面确认）——它是设计依据，本节不动它。
- **但软件侧并没有照它做到**（本次核对的代码事实）：
  - `navigation.py:135` 位姿控制器按车体系横向误差算 `vy = clamp(ky*ey, max_vy*scale)`，`motion_control/node.py:231` 把它写进 `/cmd_vel.linear.y` 发出去；
  - `robot.yaml:32,38` 的 `ky: 1.2`、`max_vy: 0.30` 都**没有**被约束成 0；`robogame_core/config_validation.py:64` 只检查 `max_vy` 这个键**存在**，不检查它是否为 0；
  - `cmd_vel_arbiter.py:91` 只按授权来源放行、**不滤 vy**（"横向命令被忽略"只对 ALIGN 那一路成立，见 `tests/test_cmd_vel_arbiter.py:93`）。
- **而且当前路线已经用到横向位移**：
  - `mission_route.py:952-972` `S11_SHIFT_TO_BUILD`（N05 → W04，0.32 m 侧向平移，自注 `heading="free"`）；
  - `mission_route.py:1063-1084` `S14_RETURN_TO_LINE`（`rounds > 1` 时的返回段，"横移 0.3 m 回到主路"）；
  - `work_sequence.py:43-45` 作业序列的侧移步（取块槽间 0.15 m、搭建同层 0.11 m）。
  这些段/步都经 `/motion/goal` → 位姿控制器 → vy；网页手动 A/D 也发 vy（`field_dashboard.py:788`）。
- **结论**：这是一个**冲突**（硬件不可用 vs 软件未屏蔽），不是"已实现"——含横移的路径（S11、S14 与作业序列的侧移步）在真车上属于**未验证且可能出错**，现场必须逐条盯着。
- **待拍板（当前没有做）**：是否在 `robot.yaml` 或仲裁器里把 vy 钳到 0，或在 `config_validation` 加一条"真车配置不得为非零横移"的检查。
