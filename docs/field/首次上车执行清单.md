## 附录 A：网页上到底能操作什么（手动联调优先顺序）

> 原则（也是本项目的约定）：**能在网页上做的，不要在终端做**；
> 但要知道哪些事网页做不到，别在现场现找。

### A1 能发命令的控件（都有门控，不满足会直接告诉你原因）

| 面板/控件 | 实际动作 | 前提 | 该看到什么 |
|---|---|---|---|
| 顶部「**全部停止**」 | 底盘归零+释放授权、停所有进程、机构 `chassis_stop`+`stop` | 无 | 一键回到安全状态；任何异常先按它 |
| 进程「**启动底盘链路**」 | 起 `robot_bridge`（参数层：`robot.yaml` **+ `robot_field.yaml`**——`mock_mode: false` 与串口来自 field 层）+ `localization` + `motion_controller`（这两个只带共用层） | 串口在位 | 安全总览出现通信/物理授权状态 |
| 进程「**启动巡线**」 | 起 `line_follow_controller`（只带共用层 → 不要求授权） | — | 「状态与巡线」开始有 8 路读数 |
| 进程「**启动机械臂**」 | 起 `manipulator_client` | — | 机械臂服务状态从「未知」变可用 |
| 底盘手动「**接管/释放**」 | 进入/退出手动模式（接管前会检查有没有别的速度发布者） | 无机构动作在执行 | 模式显示 `MANUAL` |
| 底盘手动 **W/A/S/D/Q/E**（按住才动） | 直接发 `/cmd_vel`；松开即停、失焦/断线 300 ms 自动归零 | 已接管 | 车按按钮方向动，速度由滑块（0.02–0.30 m/s）决定 |
| 底盘**定距测试** | 保持朝向直行固定距离后停车（直接发 `/cmd_vel`） | 手动已释放、巡线已停 | 结果区给出里程计位移、耗时 |
| 里程计「**记录本次 / 清空**」 | 把一次定距记成样本（尺量可留空），给「开环/自洽/标度」三行结论 | 刚跑完一次完整定距 | 3 组后给标度与波动 |
| 机械臂「**夹取/释放/回零/机构停止/升降到目标高度**」 | 调机构服务 | 底盘不在运动模式、机构不忙 | 结果区显示成功/超时/失败 |
| 「**标定白底/黑线**」（按住 2 s）→「**应用标定**」 | 采集基准 → 推送给巡线节点**并落盘** | 车在真实黑白面上 | 状态显示已生效+保存路径；节点 `calibration_ready=true` |
| 抓取对准「**跑对准仿真**」 | 纯计算，不碰硬件 | 无 | 直接看收敛过程（用来先验证控制律，再上车） |
| 日志「暂停/清空/筛选」 | 只影响显示 | 无 | —— |

> ✏️ **2026-09-18 更正（参数层事实）**：上表「启动底盘链路」一行原写「bridge + localization + motion_controller（**只带共用层**）」，与 `tools/field_console.json` 不符——
> - `bridge`（`:7`）实际带 **`robot.yaml` + `robot_field.yaml`**：`mock_mode: false` 与 `serial_port` 都来自 field 层；
> - `localization`（`:13`）、`motion`（`:19`）确实**只**带 `robot.yaml`（共用层）——这也是 `robot.yaml` 里**不设** `require_authorization` 的原因（否则手动联调时那个节点会永远不动、也不报警）。
> - ⚠️ **不要照旧文档把它"修正"成纯共用层**：`robot_bridge` 节点默认 `mock_mode=True`（`robot_bridge/node.py:124`），去掉 field 层后它会以 **mock 模式**启动 = **假数据**（安全总览会显示"通信正常"，但车根本没接固件）。

### A3 手动联调的顺序（建议照这个走，每步都留证据）

```text
① 架空（轮子离地）：启动底盘链路 → 手动接管 → 低速点动
   → 只看「方向对不对、松手停不停」。**架空不能验距离**。
② 落地（前方留 1.5 m）：定距测试 0.50 m @ 0.05 m/s ×3 + 尺量 → 记录本次
   → 看三行结论：开环准不准 / 里程计自不自洽 / 标度是多少。
③ 标定：白底 2 s → 黑线 2 s → 应用标定 → 重启巡线节点确认仍是「可用」。
④ 巡线：启动巡线 → 手推车左右压线，看 dev 符号与回正方向
   → 确认「线在左 → dev 负、wz 正」（反了就是黑白接反，回 ③ 重标）。
⑤ 机构：夹取 → 释放 → 回零 → 升降到实测高度（先空夹，确认行程与开口）。
⑥ 以上都过了，才进「阶段 3B 起整栈、不给开赛信号」→ 再进阶段 4 全自动。
```

### A4 网页**做不到**的事（这些要 SSH 终端）

| 事情 | 为什么 |
|---|---|
| 起整栈 `ros2 launch robogame_bringup hardware.launch.py` | 整栈是**比赛模式**入口，网页按钮是**手动联调**入口，两者不要混用 |
| 发 `/motion/goal`（位姿目标）、`/mission/turn`、`/mission/line` | 网页没有这些控件（它们是任务层的内部接口） |
| `ros2 param get` 核对参数最终生效值（清单阶段 1.4–1.8） | 目前只能命令行 |
| 跑测试与审计（`run_tests.py` / 三个审计 / 预演 / 故障矩阵） | 网页只显示运行时状态，不跑离线工具 |
| 看 launch 自己的日志（`SOURCE_GUARD_FAIL` 等） | 那属于 launch 进程，不在面板的模块日志里 |

> ⚠️ **不要同时用两条路**：整栈（`hardware.launch.py`）已经在跑 `line_follow_controller`
> 和 `motion_controller` 了，这时再点网页「启动巡线」会起**第二个实例**——
> `runtime_source_guard` 会因「同一话题有多个发布者」而**关掉整个 launch**。
> 手动联调时用网页按钮；跑全自动时只用 `hardware.launch.py` + 网页观察。

## 阶段 3：分步上车（先别直接跑整栈）

### 3A 只验巡线链路（无任务层）

```bash
ros2 launch robogame_bringup line_follow_hardware.launch.py
```

| 观察 | 期望 | 失败判据 |
|---|---|---|
| `ros2 topic hz /robot/status` | 稳定 ~50 Hz | 无数据 / 频繁断 |
| 网页「状态与巡线」8 路读数 | 随车在黑白面之间移动而变化 | 读数不动 → 探头/供电 |
| 网页/`/line_follow/status` 的 `state` | 压在黑线上 `ON_LINE`，抬起 `LOST` | 一直 `LOST` → 标定反了或阈值不对 |
| `dev`（偏差） | 车往左压线时符号固定一个方向 | 符号与直觉相反 → 归一化反了（检查黑白基准方向） |

**这张图故意关掉了任务层授权**（`require_authorization: false` 内联覆盖）。所以它只能验
「巡线能不能跟线」，**不能**验「任务层会不会授权」。别在这张图里下「授权没问题」的结论。

### 3B 起整栈但**不给开赛信号**（验的是「不该动」）

```bash
ros2 launch robogame_bringup hardware.launch.py
```

| 观察 | 期望 | 失败判据 |
|---|---|---|
| launch 日志 | `runtime_source_guard` 打印 `PASS: runtime sources are exclusively field` | 打印 `SOURCE_GUARD_FAIL: …` 后**整个 launch 退出** → 见阶段 5 第一条 |
| 网页「全流程路线」 | 第一行出现、段号 `0/13`、`✅ 巡线标定可用` | `⛔ 不能开赛` → 回阶段 2 |
| 网页「安全总览」 | 通信正常 / 急停未触发 / 机构正常 / `physical_start` **false** | 通信异常 → 别继续 |
| **车** | **完全不动** | 车动了 → 立刻急停，这属于严重问题（授权面/接线面） |

**为什么敢要求「完全不动」**：任务状态机停在 `WAIT_FOR_PHYSICAL_START`；巡线节点虽然有
读数，但底盘授权由任务层给（`require_authorization: true`），任务层没授权 = 巡线节点保持
沉默。这条是被测试覆盖的设计约定，但**真车上仍然要亲自确认一次**。

## 阶段 4：整栈自主（第一次完整跑）

**前提**：阶段 0–3 全过，且记录已写好。

```text
1. 车放回启动区（车体中心投影完全在启动区黑框内，规则 3.2.5）
2. 电池 → STM32 → 树莓派上电
3. ros2 launch robogame_bringup hardware.launch.py
4. 另开窗口：python3 tools/field_dashboard.py --calibration-file ~/robogame_line_calibration.json
5. 网页对照「阶段 4 观察表」（下）确认就绪
6. 所有人退到场地外 → 给开赛信号（STM32 上报 physical_start）
7. 全程只允许一个动作：急停
```

### 阶段 4 观察表：每一段网页上该出现什么

这一段是**本轮新加的可见性**：网页「全流程路线」第一行会显示当前段、授权来源、转弯阶段、
本段限速、坡道状态、作业步进度、剩余时间。下表是「每段该看到什么」（由路线数据直接导出，
不是凭印象写的）。

| 段 | 做什么 | 底盘授权（网页显示） | 另需看到 |
|---|---|---|---|
| S01_LINE_START | 出线巡线到 N02 | `line_follow` | 本段限速 0.20；到 N02 时 `转弯阶段 TURNING` |
| S02_LINE_MAIN | 主路巡线到 N06 | `line_follow` | 本段限速 0.25；`转弯阶段` 走 APPROACH→TURNING→SETTLE→DONE |
| S03_RAMP_APPROACH | N06 → 坡前 N07 | `line_follow` | 退出判据是**位移**（依赖里程计标定！） |

## 阶段 5：常见失败与处置（都对应真实代码机制）

| 现象 | 先看 | 机制（为什么会这样） | 处置 |
|---|---|---|---|
| launch 起来几秒后**整体退出**，日志有 `SOURCE_GUARD_FAIL` | 具体是哪条 issue | `runtime_source_guard` 采样 3 s 后校验：`/robot/status`、`/wheel_odom`、`/imu/data` 必须**各只有一个发布者**且都是 `robot_bridge`，且 `RobotStatus.detail` 必须表明 field 来源；不通过就关掉整个 launch | ①`ps aux \| grep -E 'robot_bridge\|mission_manager\|line_follow'` 找**残留实例**并 kill（双实例是首要嫌疑）；②确认没在跑 mock；③确认串口能开 |
| 按下开赛后立刻 FAILED，`detail` 含「标定不可用」/「未上报」 | 网页「状态与巡线」的 `calibration_status` | 开赛门（B4）：开赛那一拍检查 `calibration_ready`，`false` 或断流都拒绝 | 补标定并确认落盘，重启巡线节点后重新上电 |
| 车不动，但网页显示授权正确 | `/line_follow/status` 的 `blocked`/`stale`、`/cmd_vel` | 未授权/授权断流 >0.5 s → 节点停车；巡线读数过期 → 节点停车且段不推进 | 看 `authorized_source` / `authorization_required` 与 `reading_stale`（状态 JSON 的真实键名，见 `motion_control/line_follow_node.py:616-617`；没有叫 `authorization` 的键），别急着改参数 |
| 到路口不转弯 | `转弯阶段` 停在哪一阶段 | 转弯阶段机 `APPROACH→TURNING→SETTLE→DONE`；`SETTLE` 卡住 = 居中判定没过 | 调 `center_tolerance`（占位 0.35）；转弯 FAILED 后节点**保持零速不回退巡线**（安全设计） |
| 坡上打滑/停住 | `坡道 SLIPPING/STUCK` | 用轮速判「轮速跟不上命令」；连续 3 次 STUCK → 按失败重试本段 | 降速、清地面；**注意**轮速看不到「轮子空转车不走」 |
| 作业段没有机构动作 | `第 k/5 步` 与 `work_step_kind` | 机构命令与车体侧移是**两种**结果来源，来源不匹配时任务层会忽略该结果 | 看 `/manipulator/command` 与 `/manipulator/result` 是否成对 |
| 6 分钟到，车停下 | 网页 `剩余 0:00`、状态 `SAFE_STOP` | 比赛总时钟到点即安全停车并释放授权（规则 3.2.1） | 正常行为，不是 bug |
| 终态 `COMPLETE` 但 `detail` 里写着「降级 N 次」 | 网页 `已降级 N 次`、段号 | 降级会让任务**继续走到终点**，所以终态仍是 COMPLETE/SUCCESS | **COMPLETE ≠ 全部作业都做成了**，按降级原因复盘（哪一段、为什么） |
| 自检期就 FAILED，原因含「机制故障」 | `/robot/status` 的 `mechanism_fault` | 自检期机构故障立即判死（不再等 60 s 超时） | 复位机构后重新上电；这是**设计行为** |
| 急停后想继续 | — | `SAFE_STOP` 是**终态**，不支持热恢复 | 复位急停后重启节点，重新走一遍自检 |

## 阶段 6：每次上车要留下的证据（模板）

```text
日期/时间：

配置 SHA（robot.yaml / robot_field.yaml / field_layout.yaml）：
标定：white_ref=… black_ref=… 落盘路径=… calibration_ready=…

阶段 3A/3B 观察：逐行填「期望 vs 实际」
阶段 4：段号→耗时→重试→降级→异常（表格）

结论（必须分两栏写）：
  能证明：这次在真车上直接观察到的现象（写清版本、参数、位置）
  不能证明：没测的场景、仍依赖的假设、需要下一轮验证的东西
```

> ⚠️ 只写「能证明」那一栏、或者把「没有观察到失败」写成「已经验证」，
> 这次上车的数据就不能用于任何结论。

## 阶段 7：明确不要做的事

- ❌ 不要照 `docs/field/FIELD_DAY1_EXECUTION_ORDER.md` 执行（已过期）。
- ❌ 不要在真车上为了「跑通」把 `route_enabled` 改回 false 或改 mock——那样证明的是演示流程。

- ❌ 不要把虚拟预演的耗时当成真车耗时（预演无动力学、无打滑、无通信延迟）。
