# RoboGame2026：从远程开发到现场推进的大白话总结

适合阅读的人：刚接触项目、编程基础不多、需要同时推进任务和提升能力的本科生。  
生成日期：2026-08-08  
用途：个人复习、现场执行、开会推进和向队友解释项目。

---

## 一句话说明我们在做什么

我们要让小车能够：

```text
看到方块
→ 开到合适位置
→ 对准方块
→ 抓住方块
→ 抬起来并搬运
→ 放到目标位置
→ 小车和机械臂撤开
→ 观察方块是否稳定 3 秒
→ 明确报告成功、失败或无法判断
```

真正困难的地方不是写出一个“抓取”函数，而是让视觉、底盘、定位、机械、电控和任务流程都说同一种语言，并且任何一层出问题时，小车都不能乱动。

---

# 第一部分：从开始到现在，我们做了什么

## 1. 先把大项目拆成多个小模块

项目被分成九个 ROS2 功能包，大白话职责如下：

| 模块 | 大白话职责 |
|---|---|
| `cube_perception` | 从相机画面里找橙色和紫色方块 |
| `localization` | 判断小车现在在哪里、朝哪个方向 |
| `motion_control` | 根据目标位置算出应该怎么走，并负责限速和停车 |
| `manipulator_client` | 对准方块后，组织抓、抬、放、撤退和验证 |
| `mission_manager` | 决定先找谁、抓谁、放哪里以及失败后怎么办 |
| `robot_bridge` | 把 ROS2 命令翻译给 MCU，也把 MCU 状态翻译回来 |
| `robogame_interfaces` | 规定模块之间消息和服务长什么样 |
| `robogame_core` | 保存不依赖 ROS2 和硬件的算法，方便直接测试 |
| `robogame_bringup` | 保存参数，并统一启动模拟或真实系统 |

### 为什么要拆开

如果所有代码都写在一个文件里，现场出现“抓取失败”时，我们不知道是：

- 相机没看见；
- 小车没对准；
- 夹爪没执行；
- MCU 没回状态；
- 任务状态机走错了。

拆开以后，每个模块能单独测试。现场也能快速回答：“问题到底在哪一层？”

---

## 2. 先完成不依赖真车的软件模拟闭环

因为远程阶段拿不到小车、机械臂和现场方块，我们先建立模拟机构和模拟视觉，让软件能够跑完：

```text
PICK
→ GRAB
→ 验证抓取
→ LIFT
→ PLACE
→ RELEASE
→ RETREAT
→ 稳定观察
```

模拟中覆盖了四种放置结果：

| 结果 | 意义 |
|---|---|
| `STABLE` | 证据持续满足要求，认为放置稳定 |
| `FAILED` | 明确看到放置失败 |
| `INCONCLUSIVE` | 证据不足，不能说成功，也不能说失败 |
| `CANCELLED` | 人工或上层取消了任务 |

### 为什么先做模拟

模拟不能证明真车会成功，但能提前证明：

- 流程顺序基本正确；
- 模块之间能通信；
- 成功、失败、取消和无法判断都有出口；
- 现场接入真实硬件时，不需要同时调所有东西。

这相当于演出前先在空舞台走一遍流程。它不能代替正式演出，但能避免演员上台后才发现剧本顺序不对。

---

## 3. 把“流程状态”和“机构动作”分开

机构动作是：

```text
GRAB / LIFT / RELEASE / STOP / RETREAT
```

流程状态是：

```text
等待目标 / 对准 / 正在抓取 / 验证抓取 / 正在放置 / 验证稳定 / 完成 / 失败
```

### 为什么必须分开

“正在抓取”不等于夹爪只有一个动作。抓取流程里可能包含对准、闭合夹爪、等待状态、检查方块是否存在等多个步骤。

以后机械组更换机构动作时，我们只需要修改动作适配部分，不必重写整个任务流程。

---

## 4. 建立抓取成功和放置成功的“证据框架”

不能因为服务返回一句 `success=true`，就直接认为方块真的抓住或放稳了。

软件现在支持组合证据，例如：

- 夹爪已经闭合；
- 载荷或方块存在传感器有信号；
- 相机仍能看到方块在合理位置；
- 释放后方块已经离开夹爪；
- 机械臂或车体已经撤退；
- 放置证据保持足够长时间。

### 为什么这样做

电机执行了动作，不代表物理结果一定发生：

- 夹爪可能闭合了，但抓空；
- 方块可能抓到了，但中途掉落；
- 释放动作执行了，但方块卡在夹爪上；
- 方块已经放好，但机械臂遮挡相机，视觉暂时看不见。

所以“动作完成”和“任务成功”必须分开判断。

---

## 5. 加入撤退、稳定 3 秒和可调间隔

放置后不能立刻开始计时，因为夹爪和车体可能还挡着方块。因此流程是：

```text
释放通过
→ 请求撤退
→ 收到新的撤退完成状态
→ 开始稳定观察
→ 累计足够证据
```

稳定时间、总观察超时和短暂证据间隔都做成了可调参数。

### 为什么不把规则写死

我们还不知道真实相机安装位置和遮挡关系。允许一个很短的证据空缺，可以容忍偶发丢帧；但空缺太久就必须重新计时，避免把断断续续的画面拼成假的“连续稳定”。

如果现场发现相机根本看不到放置区，系统应该返回 `INCONCLUSIVE`，不能为了流程好看而伪造 `STABLE`。

---

## 6. 加入人为取消和安全停止语义

模拟中已经验证：稳定观察期间发出 CANCEL，会得到 `CANCELLED`，不会继续等满 3 秒。

### 为什么取消不是简单退出程序

客户端停止等待，不等于真实电机停止。现场还必须确认：

- 有没有独立 STOP 命令；
- STOP 最长多久生效；
- 如何确认执行器真的停了；
- 如果停不下来，返回什么错误；
- CANCEL 后能不能马上接受下一条动作。

这也是为什么真实机构接入前，我们没有假设“软件取消就等于硬件停止”。

---

## 7. 建立视觉离线验收工具

远程拿不到实时相机，但可以让队友录视频。我们建立了完整流程：

```text
提交新视频
→ 逐帧运行检测
→ 保存 detections.jsonl
→ 网页播放视频
→ 人工标注 start_time / end_time
→ 保存 vision_acceptance.json
→ 生成 HTML 报告
```

还处理了：

- 手机 HEVC/H.265 视频浏览器黑屏；
- 自动转换 H.264 预览；
- 处理进度显示；
- 中途取消；
- 半成品清理；
- 再次打开工作目录时恢复已有结果；
- 防止把历史预览重新当成原视频处理。

### 为什么需要人工标注

算法输出是“程序认为看见了什么”，人工标注是“人确认这段时间实际应该有什么”。两者必须分开，否则相当于拿程序自己的答案给自己打分。

HTML 报告的价值是让团队能看到：哪段通过、哪段误检、哪段漏检，而不是只听一句“视觉看起来差不多”。

---

## 8. 把模拟配置和现场配置分开

现在配置分为：

```text
robot.yaml        公共算法参数
robot_mock.yaml   模拟环境参数和模拟证据
robot_field.yaml  真实串口和保守证据策略
```

field 模式会拒绝 `mock_qualified` 和 `mock_failed` 等模拟证据。

### 为什么必须这样做

最危险的情况不是程序直接报错，而是真车运行时偷偷用了模拟成功证据，让系统在没有真实证据时报告成功。

所以我们不仅把配置文件分开，还让代码主动拒绝危险组合。安全不能只依赖“使用者记得选对文件”。

---

## 9. 给通信和 MCU 接入建立失败安全边界

电控已经确认外层帧结构和消息类型，但还没有给出 ODOM、IMU、STATUS 的完整逐字节布局。

我们已经完成：

- 帧头、版本、长度、序号和 CRC；
- 分片、粘包、噪声、截断和错误恢复测试；
- ODOM、IMU、STATUS 的类型路由骨架；
- HELLO → ACK → READY 握手状态机；
- `boot_id` 变化时识别 MCU 重启；
- 握手完成前门控速度命令；
- 没有可信 STATUS 时保持 `communication_ok=false`。

### 为什么没有直接猜字段

收到合法串口帧，只能证明线上有数据，不代表急停、故障、夹爪和电池字段都解码正确。

如果字段未知，系统宁可报告“不可信并拒绝动作”，也不能用默认值假装健康。这叫失败安全。

---

## 10. 建立单动作验收、故障注入和时间预算

我们准备了：

- `mechanism_acceptance.py`：单独测试 GRAB、LIFT、RELEASE、STOP；
- CSV 记录：请求、耗时、响应、动作前后 RobotStatus；
- 一行现场摘要：通信、急停、校准、IMU 和机构故障；
- 故障注入卡片：状态过期、服务不可用、急停、机构故障等；
- `TIME_BUDGET.csv`：列出抓取和放置各阶段的时间预算。

分析发现，原来的总超时 12 秒可能小于各步骤最坏时间之和，现场建议先使用较保守的 18 秒，再用真实数据收紧。

### 为什么不一上来跑完整任务

如果完整任务失败，很难判断是哪一步。单动作验收可以先回答：

- 服务能不能调用；
- 机构有没有实际动作；
- 状态有没有更新；
- 失败时错误码对不对；
- STOP 和 CANCEL 是否真的安全。

---

## 11. 测试运动控制的安全边界

我们增加了限速、反向加减速、异常时间步、角度跨越 ±π、到达目标归零和结束前停车测试。

测试发现一个真实问题：`RobotStatus.mechanism_fault` 已经存在，但 `motion_control` 调用安全函数时漏传了这个字段。现在已经修复。

### 为什么这个例子重要

安全字段只在消息里存在还不够，它必须经过完整链路：

```text
MCU 状态
→ RobotStatus
→ motion_control
→ 安全判断
→ 零速度和失败结果
```

中间漏掉一次传递，后面正确的安全代码也不会生效。

---

## 12. 建立 Windows 到 Ubuntu 的干净验收流程

我们没有继续覆盖 Ubuntu 中带残留文件的旧目录，而是按 Git 提交号创建独立验收仓库：

```text
Windows 提交并推送
→ Ubuntu 克隆指定 commit
→ 构建 ROS2
→ 运行测试、模拟闭环或单动作验收
→ 保存结果
→ 自动清理后台进程
```

### 为什么版本必须看提交号

文件夹修改时间和大小会受构建产物影响，不能证明代码版本。Git commit 才能准确回答：“这次测试的到底是哪份代码？”

当前主要软件证据：

```text
Windows：185 项测试通过
Ubuntu：9 个 ROS2 包构建通过
配置检查：0 errors，0 warnings
模拟闭环：STABLE / FAILED / INCONCLUSIVE / CANCELLED 已覆盖
field 无硬件：保持不可信并拒绝危险动作
```

这些证明软件准备充分，但仍不等于真车闭环完成。

# 第二部分：我们为什么一直强调“小步推进”

项目里同时有视觉、通信、底盘、定位和机构。如果一次修改五个模块，即使结果变好，也不知道是哪项修改起作用；如果结果变坏，也不知道该退回哪一步。

因此每一小步都按照下面的方式推进：

```text
目的是什么
→ 为什么现在必须做
→ 只修改一个小边界
→ 先写或运行测试
→ Ubuntu 验收
→ 更新 TODO 和学习记录
→ 创建 Git 检查点
```

这种节奏看起来比“直接写完”慢，但现场会快很多，因为每个阶段都有已知起点和退出方法。

---

# 第三部分：到现场以后具体要干什么

## 总体顺序

```text
先确认硬件事实
→ 再确认通信状态可信
→ 再确认底盘能动且一定能停
→ 再确认机构单动作
→ 再确认相机和证据
→ 最后才跑完整单方块闭环
```

不能反过来。急停和 STOP 都没验证，就运行完整自动任务，会把一个软件问题变成机械碰撞问题。

---

## 第一天：不追求演示，只拿到真实信息

### 要做什么

- 测轮径、轮距、夹爪开口、升降行程和三层高度；
- 记录相机型号、分辨率、帧率、安装高度和角度；
- 拍抓取区、放置区以及机械臂不同姿态下的遮挡画面；
- 向电控拿 ODOM、IMU、STATUS 的逐字节表和真实十六进制样例；
- 向机械确认动作命令、完成证据、错误码、超时和 STOP/CANCEL；
- 只确认串口、心跳、RobotStatus、急停和物理启动；
- 备份所有照片、视频、协议和测量数据。

### 为什么第一天不跑完整任务

因为当前很多参数仍是软件假设。先用尺子、样例帧和真实状态把假设变成事实，后续调试才有意义。

---

## 第二阶段：真实状态和底盘低速安全

### 要做什么

- 按冻结协议实现 STATUS、ODOM、IMU 完整解码；
- 检查单位、方向、时间戳和值域；
- 架空车轮或清空场地；
- 用很低限速确认前后、左右和旋转方向；
- 测试 STOP、急停、拔线、状态过期和握手未完成；
- 测量实际停车距离、消息频率和延迟。

### 通过条件

- 方向正确；
- 急停一定能停；
- 拔线后一定能停；
- 状态不可信时不会继续运动；
- 没有异常电机声、过热和明显冲击。

---

## 第三阶段：机构单动作

### 推荐顺序

```text
STOP
→ 空载 GRAB
→ 空载 RELEASE
→ 空载 LIFT
→ 带载 GRAB
→ 带载 LIFT
→ 带载 RELEASE
→ 动作中 CANCEL / STOP
```

### 为什么 STOP 第一个测

只有先知道怎么停，才有资格测试怎么动。

每个动作都记录：

- 发了什么请求；
- 多久开始；
- 多久完成；
- 真实机构做了什么；
- 状态字段怎么变化；
- 超时或失败时怎么恢复。

---

## 第四阶段：真实相机和视觉证据

### 要做什么

- 固定相机位置，避免调参期间相机又被移动；
- 固定分辨率、帧率和曝光；
- 采集橙色、紫色、空场景、不同距离、不同角度和遮挡视频；
- 用网页工具人工标注并生成 HTML 报告；
- 调 HSV、ROI、面积和连续帧参数；
- 确认撤退后相机是否看得到放置区；
- 明确抓取证据和放置证据来自视觉、传感器还是两者组合。

### 为什么先录数据再调参数

现场凭肉眼调到“现在看起来可以”，换个光照就可能失效。保存视频后，可以反复用同一批数据比较参数，才能知道修改是真的提高稳定性，还是碰巧适合当前画面。

---

## 第五阶段：第一个单方块物理闭环

在运行完整闭环前，逐项确认：

- [ ] RobotStatus 可信；
- [ ] 急停和失联停车通过；
- [ ] 底盘方向正确；
- [ ] GRAB、LIFT、RELEASE、STOP 单独通过；
- [ ] CANCEL 能真实停止；
- [ ] 相机能看到抓取区；
- [ ] 撤退后能看到放置区，或系统能诚实返回 INCONCLUSIVE；
- [ ] 有人在旁边负责急停；
- [ ] 日志、视频和 CSV 正在记录。

然后才低速运行：

```text
寻找
→ 接近
→ 对准
→ 抓取
→ 验证
→ 抬升
→ 搬运
→ 释放
→ 撤退
→ 稳定观察
```

第一次跑通只能说明“在这个条件下成功了一次”，还不能宣布项目完成。

---

## 第六阶段：重复性和异常恢复

要重复多次并统计：

- 成功率；
- 平均耗时；
- 最慢耗时；
- 最常见失败阶段；
- 重试是否有效；
- 急停、掉线、超时和重启后能否恢复。

真正可用的系统不是永远不失败，而是失败时安全、原因清楚、能够恢复。

---

# 第四部分：现场可能遇到什么问题，以及怎么办

## 1. ROS2 构建失败

### 常见原因

- 没有 source ROS2 环境；
- 当前目录不是正确提交；
- 使用了旧 `install/`；
- 依赖没安装；
- Ubuntu 目录混入旧改动。

### 应对

```text
先看 git rev-parse --short HEAD
→ 确认提交号
→ 使用一键干净验收副本
→ 重新 source /opt/ros/jazzy/setup.bash
→ 再构建
```

不要一失败就到处改代码。先确认环境和版本。

---

## 2. 串口打不开

### 可能原因

- 设备路径变化；
- USB 没插好；
- 用户没有串口权限；
- 其他程序占用串口；
- 波特率错误。

### 应对

- 查看设备是否存在；
- 确认权限和用户组；
- 关闭串口调试工具；
- 对照电控确认波特率；
- 系统保持 `communication_ok=false`，禁止动作。

不要为了“先跑起来”把通信检查关掉。

---

## 3. 收到数据但 RobotStatus 一直不可信

### 可能原因

- 只收到了心跳，没有收到 STATUS；
- STATUS 长度或 CRC 不对；
- 字节偏移、大小端或单位理解错；
- 状态频率低于过期阈值；
- 电控固件和协议文档版本不一致。

### 应对

- 保存原始十六进制帧；
- 对照一字节一字节检查；
- 记录固件版本；
- 用固定样例写解码测试；
- 在完整校验成功前保持不可信。

---

## 4. 小车方向反了或速度太大

### 可能原因

- 坐标系定义不同；
- 电机方向或轮子编号错误；
- 单位把 m/s 当成 mm/s；
- 真实 MCU 限幅与软件不同。

### 应对

- 架空车轮；
- 一次只发一个轴的小速度；
- 先确认方向，再提高速度；
- 记录每个轮子的响应；
- 由电控修底层方向映射或明确统一接口，不在多个模块重复取反。

---

## 5. 急停或拔线后没有及时停车

这是立即停止后续测试的 P0 问题。

### 应对

- 人工断开动力或使用硬急停；
- 不再发送新的运动命令；
- 和电控确认看门狗和底层独立停车；
- 测量从异常发生到停车的时间；
- 修复并重新从低速、架空条件验证。

不能依赖上位机“下一次发零速度”。底层必须能在上位机失联时独立停车。

---

## 6. 机构服务返回成功，但夹爪没抓到

### 可能原因

- 服务成功只表示命令收到；
- 夹爪开口或位置不合适；
- 没有载荷/方块存在传感器；
- 状态更新比动作完成慢；
- 方块滑落。

### 应对

- 查看动作前后 RobotStatus；
- 检查夹爪闭合和 `cube_present`；
- 录视频；
- 调整对准和机械参数，而不是直接把验证关掉；
- 把“命令完成”和“抓取成功”继续分开。

---

## 7. CANCEL 后机械还在动

### 原因

客户端只是停止等待，没有向硬件发送真正 STOP。

### 应对

- 立即使用硬急停；
- 暂停自动流程；
- 和机械、电控冻结 STOP/CANCEL 协议；
- 必须等到新的“已停止”状态后，才允许下一条动作。

如果硬件取消还没有实现，软件界面必须明确提示“不能保证执行器停止”。

---

## 8. 视觉看不到方块或误检很多

### 可能原因

- 光照变化；
- 相机曝光自动漂移；
- HSV 范围不合适；
- ROI 包含了车体或场地同色区域；
- 方块太小、太远或被遮挡；
- 相机位置改变。

### 应对

- 不在现场连续盲调十几个参数；
- 先保存原始视频和当前参数；
- 区分漏检和误检；
- 每次只改一组参数；
- 用同一批标注数据生成新旧报告对比；
- 如果相机安装本身不可用，先解决安装问题。

---

## 9. 方块其实稳定了，但系统一直 INCONCLUSIVE

### 可能原因

- 机械臂或车体遮挡；
- 撤退距离不够；
- 相机视野没有覆盖放置区；
- 证据间隔阈值太严格；
- 检测器偶发丢帧。

### 应对

- 查看撤退前后视频；
- 确认相机安装和撤退责任；
- 统计证据中断时长；
- 在有数据后调整允许间隔；
- 必要时引入夹爪/载荷传感器作为组合证据。

不要简单把 3 秒改成 0.5 秒来掩盖看不见的问题。

---

## 10. 偶尔成功、偶尔失败

### 应对方式

不要用“玄学”“可能卡了”结束讨论。把失败分类：

```text
视觉
定位
运动
通信
机构
成功证据
超时
人为操作
```

每类统计出现次数和共同条件，例如距离、光照、电量、动作时长。先解决出现频率最高且阻断闭环的问题。

---

## 11. 队友同时修改代码导致冲突

### 应对

- 每个人使用自己的功能分支；
- 开始前同步最新 main；
- 一次提交只做一个目的；
- 不直接覆盖别人的工作目录；
- 冲突由理解两个模块的人一起解决；
- 合并后重新测试，不把“冲突标记消失”当作功能正确。

---

# 第五部分：怎么在开会中保持节奏

## 1. 会议不是让每个人汇报所有细节

会议只需要回答五个问题：

```text
今天唯一目标是什么？
目前证据是什么？
卡在哪个明确问题？
谁在什么时间前提供什么？
什么条件满足后才能进入下一步？
```

如果讨论内容不能帮助回答这五个问题，就先记录到停车场清单，不在会上无限展开。

---

## 2. 开会前准备一张状态表

| 项目 | 当前状态 | 证据 | 阻塞 | 负责人 | 下一次检查时间 |
|---|---|---|---|---|---|
| MCU STATUS | 等逐字节表 | 已有外层帧定义 | 缺字段偏移和样例 | 电控 | 明天 10:00 |
| 机构 STOP | 未冻结 | 只有模拟实现 | 缺真实停止方式 | 机械+电控 | 明天 11:00 |
| 底盘低速 | 未现场验证 | 软件限速测试通过 | 等真车 | 算法+电控 | 到场后 |
| 视觉证据 | 离线工具完成 | HTML 报告链可用 | 缺紫色和遮挡数据 | 视觉负责人 | 采集后 |

状态只使用：

```text
未开始 / 进行中 / 等待输入 / 可验收 / 已完成 / 阻塞
```

不要使用“应该差不多”“可能没问题”作为状态。

---

## 3. 会议建议控制在 20～30 分钟

### 前 5 分钟：确认目标

主持人先说：

> 今天会议只解决一个问题：我们是否具备进入下一阶段的条件。

### 中间 15 分钟：逐项看证据和阻塞

每个人按照固定格式说：

```text
我负责什么
→ 我完成了什么
→ 证据在哪里
→ 还缺什么
→ 需要谁在什么时候给我什么
```

### 最后 5 分钟：复述决定

主持人逐条确认：

- 谁负责；
- 交付物是什么；
- 截止时间；
- 验收条件；
- 如果做不到，采用什么替代方案。

会后立即把决定写入 TODO，而不是只留在聊天记录里。

---

## 4. 如何阻止会议跑题

可以直接用这些句子：

> 这个问题重要，但不影响今天的唯一目标，先放到待办，闭环后再讨论。

> 我们现在缺的是数据，不是更多猜测。请明确由谁采集什么数据。

> 先不要讨论完整任务，我们还没有通过 STOP 和失联停车。

> 这个结论有没有日志、视频、CSV 或协议样例支持？

> 现在有两个方案，请明确选择哪个，以及选择依据。

> 如果今天无法获得硬件，我们就执行备用任务，不空等。

这些话不是否定队友，而是保护团队的时间和安全顺序。

---

## 5. 如何在推进任务的同时照顾学习

每完成一个小任务，要求自己回答：

1. 这个问题在系统的哪一层？
2. 为什么原来的做法不够？
3. 修改前后的数据流是什么？
4. 怎样证明它真的好了？
5. 这个方法还能用到什么项目？

不要只复制命令。每次至少理解一个知识点，例如：

- 为什么状态要有新鲜度；
- 为什么通信收到数据不等于状态可信；
- 为什么 mock 和 field 必须分离；
- 为什么取消必须清理真实工作；
- 为什么 Git commit 能代表测试版本；
- 为什么边界测试比只测成功更重要。

每天结束时，在学习日志中用自己的话写 5～10 行，比一次读完大量教程更有效。

---

## 6. 如何避免自己被大量任务压垮

任何时候只保留三个层级：

```text
今天唯一目标
本周关键目标
以后再做
```

例如现场第一天：

- 今天唯一目标：拿到可信接口和硬件数据；
- 本周关键目标：完成单方块物理闭环；
- 以后再做：多方块策略、界面美化、架构重构。

如果有人临时提出新功能，先问：

> 它是否阻止我们完成今天的唯一目标？

如果不是，就记下来，不立即切换任务。

# 第七部分：什么时候必须停止测试

出现以下任意情况，立即停止当前阶段：

- 急停无效；
- 拔线后底盘或机构继续运动；
- 速度方向与预期相反；
- 机构撞限位、异常抖动、过热或发出异响；
- 状态显示正常但物理状态明显异常；
- 不知道当前运行的是哪个 Git 提交；
- 没有人负责急停；
- 日志和视频都没有记录；
- 团队对命令单位或方向没有一致结论。

停止测试不是失败。及时停止说明团队在保护设备、人员和后续调试时间。

---

# 第八部分：怎样判断项目真的完成了一个闭环

不能只看终端打印 `PASS`。单方块物理闭环至少需要：

- 相机真实看到方块；
- 小车真实接近并对准；
- 夹爪真实抓住；
- 有新的抓取成功证据；
- 方块在搬运过程中没有掉落；
- 真实释放；
- 车体或机械臂真实撤退；
- 放置证据满足稳定要求，或诚实报告无法判断；
- 整个过程中急停、超时、取消和通信失联都不会造成继续乱动；
- 有提交号、参数、日志、视频和结果记录；
- 重复运行后能统计成功率和失败原因。

最重要的判断标准是：

> 系统不仅知道什么时候成功，也知道什么时候没有成功；不仅能开始动作，也能安全停止动作。

---

# 最后的提醒

我们现在完成的是“软件上已经尽量把未知问题变成明确接口、测试和清单”。这不是绕远路，而是在为现场节省时间。

到现场后不要急着证明机器人能跑完整任务。先证明：

```text
信息是真的
动作是可控的
异常时能停
结果有证据
失败能定位
```

这些成立以后，完整闭环只是把已经通过的小步骤按顺序连起来。反过来，如果这些基础没有通过，即使偶然跑通一次，也无法知道下一次为什么失败。
