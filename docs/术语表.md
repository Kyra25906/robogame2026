## 一、ROS 2 软件架构

### ROS 2
- **定义**：Robot Operating System 2，机器人开发中间件框架，用「节点—话题—服务—参数」把功能模块解耦，支持跨进程/跨机器通信。本项目用 Jazzy 发行版。
- **白话**：机器人的「操作系统 + 消息总线」。各程序不直接互相调用，而是通过统一消息通道收发数据。
- **源码对照**：
  - 位置：`ros2_ws/` 下九个功能包，入口都在各自 `node.py` 的 `main()` 里 `rclpy.init(args=args)` → `rclpy.spin(node)` → `rclpy.shutdown()`。
  - 关键代码：`motion_control/node.py:180` `def main(args=None): rclpy.init(args=args); node = MotionControllerNode(); ... rclpy.spin(node)`。
  - 分析：每个包是一个可独立 `ros2 run <包名> <程序名>` 的进程；`robogame_bringup/launch/*.launch.py` 负责一次性拉起多个进程。

### 节点（Node）
- **定义**：ROS 2 中一个独立执行单元，负责单项功能，通过 `rclpy.spin()` 循环处理回调。
- **白话**：一个「小工」进程，各干各的活，靠收发消息协作。
- **源码对照**：
  - 位置：`motion_control/node.py:25` `class MotionControllerNode(Node)`，`:27` `super().__init__("motion_controller")` 注册节点名。
  - 数据流：九个节点——`cube_perception`（读相机发 `/cubes`）、`localization`（订阅 `/wheel_odom`+`/imu/data` 发 `/pose`）、`motion_control`（订 `/pose` 发 `/cmd_vel`）、`mission_manager`（编排）、`manipulator_client`（抓取）、`robot_bridge`（串口桥接）。

### 话题（Topic）与发布/订阅（Publisher / Subscriber）
- **定义**：话题是单向、多对多的异步数据通道；发布者写消息，订阅者收回调，适合持续高频数据流。
- **白话**：「广播电台 + 收音机」，发布者不停广播，订阅者挑关心的话题收听。
- **源码对照**：
  - 位置：`motion_control/node.py:65` `self.cmd_pub = self.create_publisher(Twist, "/cmd_vel", 20)`；`:67` `self.create_subscription(Odometry, "/pose", self._on_pose, 20)`。
  - 数据流：`robot_bridge` 发 `/wheel_odom` → `localization` 订它、发 `/pose` → `motion_control` 订 `/pose`、发 `/cmd_vel` → `robot_bridge` 订 `/cmd_vel` 编码后写串口给 STM32。
  - 分析：队列深度 `20` 是「历史缓冲条数」，用 20 表示尽量不丢最新消息。

### 服务（Service）与客户端/服务端（Client / Server）
- **定义**：服务是「请求—应答」式调用，一问一答，适合「抓一下」「升到某高度」这类有明确结果的命令。
- **白话**：「打电话下单」，发出请求必须等对方回结果。
- **源码对照**：
  - 服务端：`robot_bridge/node.py:148` `self.create_service(ExecuteMechanism, "/gripper/grab", self._mechanism, callback_group=...)`；`/lift/set_height` 在 `:172` 用 `SetLiftHeight`。
  - 客户端：`manipulator_client/node.py:63` `self.grab = self.create_client(ExecuteMechanism, "/gripper/grab")`，`:250` `future = self.stop.call_async(request)` 异步调用。
  - 分析：`.srv` 文件用 `---` 分隔请求/响应（见 `ExecuteMechanism.srv`：上段 `command`+`timeout_s`，下段 `success`+`error_code`+`duration_s`+`detail`）。

### 消息与接口（Message / Interface，`.msg` / `.srv`）
- **定义**：接口是通信双方的「数据合同」，定义字段名/类型/单位。`.msg` 定义话题消息，`.srv` 定义服务请求+响应。
- **白话**：事先签好的「表格格式」，保证双方对每个数字理解一致。
- **源码对照**：
  - 位置：`ros2_ws/src/robogame_interfaces/msg/RobotStatus.msg`（14 个字段：`communication_ok`、`emergency_stop`、`physical_start`、`gripper_closed`、`cube_present`、`battery_voltage`、`boot_id` 等）；`srv/SetLiftHeight.srv` 请求 `height_m`+`timeout_s`。
  - 分析：`RobotStatus.msg` 里的 `bool imu_valid`、`uint16 boot_id` 直接对应 `serial_protocol.py` STATUS 载荷位和 `0x12` 里的 `boot_id`；`robot_bridge/node.py:938-994` 逐字段把串口 STATUS 填进这条消息。

### 参数（Parameter）与参数文件（params-file / YAML）
- **定义**：运行时配置值，常经 YAML 批量加载，避免把阈值写死。
- **白话**：把「旋钮」抽到配置文件里，不重编译就能调。
- **源码对照**：
  - 位置：`motion_control/node.py:28-39` `for name, default in {"kx": 1.2, ...}.items(): self.declare_parameter(name, default)`；读取 `:41` `float(self.get_parameter("kx").value)`。
  - 配置：`robogame_bringup/config/robot.yaml`、`hardware.yaml` 集中保存；`hardware.yaml:4` `serial_port: /dev/serial/by-id/...`、`:5` `baud_rate: 115200`。
  - 分析：`robot_bridge` 在启动时用 `:116-142` 做参数合法性检查（timeout 必须有限正数、covariance 必须正），非法直接 `raise ValueError` 拒绝启动，避免带坏参数上真车。

### 启动（Launch）与构建（colcon / package.xml / setup.py）
- **定义**：launch 文件一次启动多节点；colcon 是 ROS 2 构建工具；`package.xml` 声明包元数据与依赖；`setup.py`/`setup.cfg` 登记可执行入口。
- **白话**：「一键开机脚本」+「编译打包工具」+「说明书」。
- **源码对照**：
  - 位置：`robogame_bringup/launch/mock_demo.launch.py`、`hardware.launch.py`；每个包的 `setup.py` 里 `entry_points={'console_scripts': ['motion_controller = motion_control.node:main']}`。
  - 命令：README 反复出现 `source /opt/ros/jazzy/setup.bash && colcon build --symlink-install && source install/setup.bash`。
  - 分析：`robogame_interfaces/CMakeLists.txt` 调 `rosidl_generate_interfaces` 生成消息的 Python/C++ 代码，所以改接口后必须重新 colcon build。

### 坐标变换（TF / TF2，frame_id）
- **定义**：TF 维护机器人各坐标系（地图、底盘、传感器）之间的变换关系；`frame_id` 是坐标系名。
- **白话**：统一「谁在谁前面、转多大角度」的账本，让不同传感器报告对齐到同一张地图。
- **源码对照**：
  - 位置：`localization/node.py:43` `self.tf_broadcaster = TransformBroadcaster(self)`；`:187-194` 构造 `TransformStamped()` 填 `child_frame_id = "base_link"`，`:194` `self.tf_broadcaster.sendTransform(transform)`。
  - 数据流：`localization` 把融合位姿既发 `/pose`（`frame_id="map"`，见 `:86` `fused.header.frame_id = "map"`），又广播 `map -> base_link` 变换。
  - 分析：`robot_bridge` 发的轮式里程计 `frame_id` 是 `"odom"`、`child_frame_id="base_link"`（`robot_bridge/node.py:885-886`），`localization` 把它重标为 `"map"`。

### 四元数（Quaternion）
- **定义**：四维数 (x, y, z, w) 表示三维旋转，避免欧拉角万向节死锁；ROS 位姿朝向默认用它。
- **白话**：一种「不会卡死」的旋转记法，人眼难读，需转成角度。
- **源码对照**：
  - 转偏航：`motion_control/node.py:21` `quaternion_to_yaw(x,y,z,w) = math.atan2(2.0*(w*z+x*y), 1.0-2.0*(y*y+z*z))`。
  - 反向构造：`robot_bridge/node.py:68` `yaw_to_quaternion(yaw) = (0, 0, sin(yaw/2), cos(yaw/2))`（绕 Z 轴旋转）。
  - 拦截无效值：`localization/node.py:159` 拒绝 `qx==qy==qz==qw==0` 的全零四元数。
  - 分析：全零四元数不是合法旋转，是未初始化/异常数据，直接放行会让下游 TF 崩。

### Twist（速度消息）
- **定义**：`geometry_msgs/Twist` 表示线速度与角速度，底盘用 `linear.x/y` 与 `angular.z`。
- **白话**：给底盘的「速度命令」：前后多快、横移多快、转多快。
- **源码对照**：
  - 位置：`motion_control/node.py:175-176` `msg = Twist(); msg.linear.x, msg.linear.y, msg.angular.z = command.vx, command.vy, command.wz`。
  - 停车即全零：`motion_control/node.py:138` `self.cmd_pub.publish(Twist())`（默认构造全零）。
  - 消费端：`robot_bridge/node.py:317` `self.velocity = Velocity2D(msg.linear.x, msg.linear.y, msg.angular.z)`，再编码成 VELOCITY 帧写串口。

### 里程计消息（nav_msgs/Odometry）
- **定义**：标准消息，含位姿（pose）、速度（twist）及各自协方差，表示机器人自身运动估计。
- **白话**：机器人「我在哪、正往哪动、有多不确定」的标准报表。
- **源码对照**：
  - 位置：`robot_bridge/node.py:883-911` 构造 `Odometry()`，填 `pose.pose.position`、用 `yaw_to_quaternion` 填朝向、`:892-906` 填 `pose.covariance`/`twist.covariance`。
  - 分析：协方差数组是 6×6 展平成 36 个元素，对角下标 `0/7/14/21/28/35` 对应 (x,y,z,roll,pitch,yaw) 的方差；`robot_bridge` 用 `covariance["odom_pose_xy_variance"]` 等填对角线，用 `unavailable_variance`（1e6）表示「未知」，这是 `nav_msgs/Odometry` 的约定。

## 二、串口与通信协议

### UART / USB CDC 虚拟串口
- **定义**：UART 是异步串行接口（TX/RX 按位传）；USB CDC 把 USB 模拟成虚拟 COM 口，让上位机当串口用。
- **白话**：树莓派和单片机之间「一根线上按节奏传字节」的电话线；USB 口假装自己是串口。
- **源码对照**：
  - 位置：`robot_bridge/node.py:231` `_open_serial()` 里 `self.serial = serial.Serial(port, baud, timeout=0.0)`（用 `pyserial` 打开）。
  - 硬件路径：`hardware.yaml:4` `serial_port: /dev/serial/by-id/usb-STMicroelectronics_STM32_Virtual_ComPort_307A39653433-if00`——STM32 用 USB 虚拟串口（VCP），靠 `by-id` 固定设备。
  - 分析：`timeout=0.0` 表示非阻塞读，配合 `robot_bridge/node.py:293` 的 `self.serial.in_waiting` 判断有无数据，避免阻塞 ROS 主循环。

### 波特率（Baud rate）与 8N1
- **定义**：波特率是每秒符号数（此处即 bit/s）；8N1 = 8 数据位、无校验、1 停止位。
- **白话**：双方约定「说多快」和「每个字怎么断句」，说错速度就乱码。
- **源码对照**：
  - 位置：`hardware.yaml:5` `baud_rate: 115200`；`robot_bridge/node.py:235` `baud = int(self.get_parameter("baud_rate").value)` 传给 `serial.Serial`。
  - 协议依据：`docs/树莓派_STM32机械机构通信协议_v1.0.md` 第 2 节规定 `115200 bit/s，8N1，无流控`。
  - 分析：波特率由 `pyserial` 自动配置数据位/停止位默认值，代码里未显式传 8N1，靠协议文档固化。

### 帧（Frame）与帧头 SOF
- **定义**：帧是通信基本数据包，含帧头、类型、长度、载荷、校验；SOF 是固定起始标志，用于在字节流里定位帧起点。
- **白话**：给字节串包「信封」，收信方靠开头的固定记号找到每封信边界。
- **源码对照**：
  - 位置：`serial_protocol.py:8` `SOF = b"\xAA\x55"`；`:11` `HEADER = struct.Struct("<2sBBHH")` 定义 `sof(2)+version(1)+message_type(1)+sequence(2)+payload_length(2)`。
  - 编码：`serial_protocol.py:128` `encode_frame()` 组装 `header + payload + crc16`；`:140` `decode_frame()` 校验 `sof`、`version`、长度、CRC。
  - 分析：总帧长 `10 + payload_length`（协议第 2 节），`MAX_PAYLOAD = 512`（`:10`）作为安全上限，防止声明超大长度撑爆内存。

### 小端序（Little-endian）与二进制补码
- **定义**：小端序 = 多字节整数「低字节在前」；有符号数用二进制补码表示负数。
- **白话**：数字拆成字节后「个位先放」，负数有固定编码，双方必须一致才不读错。
- **源码对照**：
  - 位置：`serial_protocol.py:11-20` 所有 `struct.Struct` 都用 `<` 前缀，如 `HEARTBEAT_PAYLOAD = struct.Struct("<I")`、`MECHANISM_COMMAND_PAYLOAD = struct.Struct("<HBBiI")`。
  - 具体：`encode_mechanism_command` 里 `_int32(command.parameter)` 校验 int32 范围 `-(1<<31) <= v < 1<<31`（`:310`），负数按补码由 `struct` 打包。
  - 分析：协议文档第 2 节明确「小端；有符号数二进制补码」，第 16 节给的 payload 示例 `02 00 03 00 78 00 00 00 A0 0F 00 00` 里 `78 00 00 00` 就是小端 int32 的 `120`。

### CRC 校验（CRC-16/CCITT-FALSE）
- **定义**：循环冗余校验，对数据做多项式运算生成校验码，接收端重算比对发现传输错误。
- **白话**：给数据算「指纹」，收到再算一遍，对不上就说明数据坏了。
- **源码对照**：
  - 位置：`serial_protocol.py:119-125` `crc16_ccitt(data, initial=0xFFFF)`，循环里 `crc ^= byte << 8` 后 8 轮 `crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF`。
  - 校验：`decode_frame():153-156` `expected_crc = CRC.unpack_from(data, len(data)-2)[0]`，`crc16_ccitt(data[:-2]) != expected_crc` 就抛 `ProtocolError("CRC mismatch")`。
  - 分析：`0x1021` 是 CRC-16/CCITT-FALSE 多项式，`init=0xFFFF、不反射、xorout=0` 与协议文档第 2 节完全一致；CRC 覆盖 `AA` 到 payload 末字节，不含 CRC 自身。

### 心跳（Heartbeat）
- **定义**：周期性发送的保活信号，让对方判断通信链路是否正常。
- **白话**：隔一会儿喊一声「我还活着」，太久没听到就知道断线了。
- **源码对照**：
  - 位置：`robot_bridge/node.py:78` `_HEARTBEAT_INTERVAL_S = 0.05`（50ms）；`:342` `_send_heartbeat()` 判断 `now - self._last_heartbeat_tx < _HEARTBEAT_INTERVAL_S` 则跳过。
  - 载荷：`:352` `host_tick_ms = int(now * 1000.0) & 0xFFFFFFFF`，`:353` `encode_frame(MSG_TYPE_HEARTBEAT, self.sequence, encode_heartbeat(host_tick_ms))`。
  - 分析：STM32 侧 150ms 未收到心跳即判通信中断（协议第 4 节）；心跳的「看门狗」语义在固件 `rpi_protocol.c` 的 `RPI_IsWatchdogStop()` 体现——心跳只保活、不授权运动。

### HELLO 与握手（Handshake）
- **定义**：会话建立前的问候消息，双方确认协议版本和会话就绪后才允许执行命令。
- **白话**：先「对暗号」确认彼此能听懂、版本一致，再谈正事。
- **源码对照**：
  - 位置：`robot_bridge/node.py:644` `_run_handshake()` 周期性发 HELLO，`:656` `encode_frame(MSG_TYPE_HELLO, hello_sequence, encode_hello())`；`encode_hello()` 返回单字节 `[VERSION]`（`serial_protocol.py:166`）。
  - 收 ACK 判定：`robot_bridge/node.py:672` `_accept_frame_for_handshake()` 只接受「acknowledged == 最近发的 HELLO sequence 且 result==0」的 ACK 才置 `_HANDSHAKE_READY`。
  - 重试/超时：`:72-77` `_HANDSHAKE_HELLO_INTERVAL_S=0.5`、`_HANDSHAKE_TIMEOUT_S=3.0`、`_HANDSHAKE_MAX_RETRIES=3`，超过进 `UNAVAILABLE`。
  - 分析：握手未完成时 `_on_cmd_vel` 会拦截并告警（`:301`），所以没握手成功前速度命令不会下发。

### ACK（确认应答）
- **定义**：接收方对收到帧的确认，仅表示「帧收到、格式对」，不表示动作成功。
- **白话**：收到信回一句「收到」，但「收到」不等于「事情办成了」。
- **源码对照**：
  - 位置：`serial_protocol.py:278` `encode_ack(acknowledged_sequence, result=0)` 打包 `(sequence, result, VERSION)`，载荷固定 4 字节。
  - 处理：`mechanism_transport.py:77` `handle_ack()` 匹配 `acknowledged_sequence == awaiting_sequence`，`result != 0` 直接失败。
  - 分析：协议第 5 节明确 ACK 与动作成功解耦——`0x20` 命令长度对就回 `ACK_OK`，但语义错误靠 `0x21 REJECTED` 表达；`robot_bridge` 的 `_execute_real_mechanism` 必须等到 `SUCCEEDED` 才算成功。

### 序列号与命令编号（frame_sequence / command_id）
- **定义**：`frame_sequence` 是每帧递增的传输序号，用于 ACK 对应；`command_id` 是业务层逻辑命令编号，用于去重和状态查询。
- **白话**：帧序号是「信封编号」，命令编号是「订单号」；重发换新信封号、订单号不变。
- **源码对照**：
  - 帧序号：`robot_bridge/node.py:181` `self.sequence = 0`，每次写成功后 `:322` `self.sequence = (self.sequence + 1) & 0xFFFF`（回绕）。
  - 命令编号：`robot_bridge/node.py:206` `self._next_mechanism_command_id = 1`，`:472-473` 发命令时 `command_id = self._next_mechanism_command_id` 再 `(command_id + 1) & 0xFFFF`。
  - 分析：`mechanism_transport.py` 重试时 `mark_sent()` 更新 `awaiting_sequence` 但 `command.command_id` 不变，`handle_status()` 靠 `command_id`+`operation` 匹配（`:92`），实现「重发不重复驱动」。

### 幂等（Idempotent）
- **定义**：同一操作重复执行多次，结果与执行一次相同，无副作用。
- **白话**：「重复点不会出事」——再发一遍同样命令，不会重复抓第二次。
- **源码对照**：
  - 位置：`mechanism_transport.py:89` `handle_status()` 里 `if status.command_id != self.command.command_id or status.operation != self.command.operation: return False`——只认匹配的命令。
  - 协议依据：协议第 10 节「相同 command_id 且 payload 相同不得重复驱动，返回缓存状态」；STM32 缓存「当前命令 + 最近 16 条终态」。
  - 分析：`robot_bridge` 用 `MechanismCommandTracker` 单实例互斥（`node.py:466-471` 已有未完成 tracker 就返回错误码 6），保证同一时刻只有一条普通机械命令。

### 粘包 / 拆包 / 半帧（Stream framing / resynchronization）
- **定义**：串口是字节流，多帧可能粘一起、一帧被拆多段、或只剩半帧，接收端靠 SOF+长度重新定位边界。
- **白话**：信被撕碎或粘成团，收信人按「信封记号」重新拼回完整的一封封。
- **源码对照**：
  - 位置：`serial_protocol.py:329` `class StreamDecoder`，`:335` `feed(chunk)` 把字节追加到 `bytearray`，`:339` `start = self._buffer.find(SOF)` 找帧头，`:348-359` 按 `HEADER.size + length + CRC.size` 拼完整帧后 `decode_frame`，失败就 `del self._buffer[0]` 丢弃一个字节重同步。
  - 使用：`robot_bridge/node.py:836-839` `data = self._safe_serial_read()`，`for _frame in self.decoder.feed(data): self._dispatch_frame(_frame, now)`。
  - 分析：`find(SOF)` 找不到时只保留最后 1 字节（`:341`），防止 `AA` 跨 chunk 被误删；CRC 错误帧静默丢弃且不触发任何执行器动作（协议第 15 节）。

### 状态机（State Machine / FSA）
- **定义**：系统建模为有限状态及合法迁移，任何时刻处于一个确定状态。
- **白话**：把复杂流程画成「状态 + 能走的路」，保证不乱跳。
- **源码对照**：
  - 机械命令：`mechanism_transport.py:13` `class CommandPhase(str, Enum)`（`WAITING_ACK → WAITING_STATUS → SUCCEEDED/FAILED`）；`handle_status():98-108` 里 `ACCEPTED/RUNNING` 续等，`SUCCEEDED/FAILED/CANCELLED/REJECTED` 收尾。
  - 倒退保护：`mechanism_transport.py:100-104` 若状态从 `RUNNING` 倒退到 `ACCEPTED` 判 `9006` 失败。
  - 任务：`mission.py:10` `class MissionState(str, Enum)` 列 14 个状态，`_advance_after_success():106` 写死每个状态的下一跳。
  - 分析：机械状态机的合法转换在协议第 8 节固定为 `ACCEPTED -> RUNNING -> SUCCEEDED|FAILED|CANCELLED`，`REJECTED` 是直接进入的终态。

### 看门狗（Watchdog / IWDG）
- **定义**：独立硬件定时器，程序须周期「喂狗」；卡死未喂则强制复位。
- **白话**：「防死机闹钟」，程序卡住不续命就自动重启。
- **源码对照**：
  - 位置：`_inspect_four_motor/.../safety.c:58` `Safety_IWDGStart()` 启动 LSI、写 `IWDG->KR = 0xCCCCU`；`:264` `Safety_WatchdogRefresh()` 写 `IWDG->KR = 0xAAAAU` 喂狗。
  - 超时：`safety.c:19-20` `SAFETY_IWDG_PR_DIV64=4`、`SAFETY_IWDG_RELOAD=249`，注释给出 `(249+1)*64/32000 ≈ 0.5s`。
  - 分析：`safety.h:35-38` 强调「只在真正完成一次速度控制周期后喂狗，不放主 while(1) 末尾」，避免程序卡在半路还继续喂狗、掩盖故障。

### boot_id
- **定义**：STM32 每次启动/复位都变化的标识，让上位机发现「单片机重启了」。
- **白话**：单片机每次开机换「工号牌」，上位机看到牌子变就知道它重启过、旧命令作废。
- **源码对照**：
  - 固件侧：`rpi_protocol.h:24` `void RPI_SetBootId(uint16_t boot_id)`；boot_id 由 `_inspect_four_motor/.../boot_id.c` 维护。
  - 上位机检测：`robot_bridge/node.py:701` `_on_status_boot_id(boot_id)`，`:711` 若 `boot_id != self._last_boot_id` 则 `_cancel_pending_mechanism(9004, ...)` 并重置里程计、强制重新握手。
  - 分析：协议第 4 节「树莓派发现 0x12 中 boot_id 改变，废弃所有未完成命令并重新 HELLO，升降视为未回零」；`boot_id` 存在 `0x12` STATUS 载荷里（`serial_protocol.py:95` `StatusSample.boot_id`）。

## 三、STM32 嵌入式与电机控制

### STM32 / MCU
- **定义**：ST 公司 32 位微控制器，运行固件直接控电机、读传感器、处理急停。
- **白话**：车上「底层大脑」，负责所有「手要快、不能死机」的实时活。
- **源码对照**：
  - 位置：`_inspect_four_motor/Four_Motor_PID_Test/` 是 STM32F4 HAL 工程，`Core/Src/main.c`、`Core/Src/chassis_control.c`、`Core/Src/rpi_protocol.c` 等。
  - 分析：协议文档第 1 节明确「STM32 拥有执行器最终安全控制权」，树莓派不得直接下发电机 PWM/方向/电流；所有安全上限在 STM32 本地，树莓派参数不能覆盖。

### HAL（硬件抽象层）
- **定义**：芯片厂商提供的库，把寄存器操作封装成统一 API（GPIO/TIM/USART/IWDG）。
- **白话**：芯片厂商给的「标准工具箱」，不用手写寄存器也能驱动外设。
- **源码对照**：
  - 位置：`motor.c:129` `HAL_GPIO_WritePin(...)`、`:274` `HAL_TIM_PWM_Start(&htim9, TIM_CHANNEL_1)`；`safety.c:58` `SET_BIT(RCC->CSR, RCC_CSR_LSION)`（HAL 之上直接操作 RCC 寄存器启动 LSI）。
  - 分析：头文件 `stm32f4xx_hal_conf.h` 配置 HAL 模块开关；`tim.c`/`usart.c`/`gpio.c` 由 STM32CubeMX 生成。

### PWM（脉宽调制）与占空比 / ARR
- **定义**：PWM 用固定频率下高电平占比等效调节输出功率；ARR 是定时器自动重装载值，决定计数上限（占空比分辨率）。
- **白话**：像快速开关灯，开得久就「更亮」；ARR 决定「亮度有几档」。
- **源码对照**：
  - 位置：`motor.h:29` `#define MOTOR_PWM_MAX 419`，注释说明 TIM3/TIM9 的 `ARR = 419`，所以 PWM 有效范围 `0~419`。
  - 写比较值：`motor.c:207` `__HAL_TIM_SET_COMPARE(&htim9, TIM_CHANNEL_1, pwm)`（M1 用 TIM9_CH1，M3/M4 用 TIM3）。
  - 分析：`+419=正100%、+210≈正50%、0=停、-419=反100%`（`motor.c:318-323` 注释）；占空比 = `compare/ARR`。

### 编码器（Encoder）与 PPR / 倍频 / 减速比
- **定义**：编码器测电机轴转角；PPR=每圈脉冲数，倍频把脉冲细分，减速比=电机轴到输出轴减速倍数。
- **白话**：给电机装「计步器」，数脉冲就知道轮子转多少圈、多快。
- **源码对照**：
  - 位置：`encoder.h:18` `#define ENCODER_COUNTS_PER_REV 1404.0f`，注释 `13 PPR × 4 倍频 × 27 减速比 = 1404`，并注明「实车以后需要验证」。
  - 接口：`encoder.h:45` `float Encoder_GetRPM(Motor_ID motor)`、`:51` `int32_t Encoder_GetDelta(Motor_ID motor)`、`:61` `void Encoder_SetDirection(Motor_ID motor, int8_t direction)`。
  - 分析：`Encoder_Update(float dt)` 按实际经过时间（如 10ms→0.010）算速度，卡顿时 dt 变大仍能正确算 RPM。

### RPM
- **定义**：每分钟转数，电机/轮子转速单位。
- **白话**：轮子「一分钟转几圈」。
- **源码对照**：
  - 位置：`四轮同步PID模块/wheel_sync.h:23-26` 三个数组 `base_target_rpm[4]`、`actual_rpm[4]`、`corrected_target_rpm[4]` 全用 RPM。
  - 流程：`接入说明.md` 第 6 节 `actual_rpm[MOTOR_1] = Encoder_GetRPM(MOTOR_1)`，第 7 节 `PID_Update(&pid_m1, corrected_target_rpm[MOTOR_1], actual_rpm[MOTOR_1], control_dt)`。
  - 分析：同步模块默认参数全是 RPM 量纲（`enable_min_rpm=10`、`target_tolerance_rpm=3`、`max_correction_rpm=8`）。

### PID 控制（比例-积分-微分）
- **定义**：经典闭环控制，误差的当前值（P）、累计（I）、变化率（D）加权求和得输出，使实际值逼近目标。
- **白话**：不断「看差多少、差多久、变多快」调油门，让速度贴住目标。
- **源码对照**：
  - 位置：`pid.c:145` `PID_UpdateCore()` 是统一核心，`:167` `error = target - measurement`，`:208` `p_term = kp * error`，`:209` `d_term = kd * derivative_filtered`，`:246-249` `output = p_term + ki*integral + d_term` 后 `PID_Clamp`。
  - 入口：`pid.c:304` `PID_Update()`（无跟踪）与 `:320` `PID_UpdateTracked()`（带跟踪），都调 `PID_UpdateCore`。
  - 分析：接入说明第 9 节给单轮速度环参数 `Kp=1.5、Ki=0.3、Kd=0`、输出范围 `±150`。

### 速度环（Velocity loop）
- **定义**：以转速为被控量的闭环，PID 输出直接给 PWM，是最常用电机内环。
- **白话**：只管「转多快」这一层闭环。
- **源码对照**：
  - 位置：`接入说明.md` 第 7 节：每 10ms 控制周期，单轮 `PID_Update(&pid_m1, corrected_target_rpm[MOTOR_1], actual_rpm[MOTOR_1], control_dt)` 输出 `motor_pwm[MOTOR_1]`。
  - 分析：目标是 RPM、反馈是编码器 RPM，输出是 PWM 比较值——这是典型速度环结构；更内层电流环由驱动器（WSDC2412D）自身处理。

### 抗积分饱和（Anti-windup / integral windup）
- **定义**：执行器到上限、误差仍持续时积分项无限累加导致超调/振荡；抗饱和策略在输出受限时抑制积分累积。
- **白话**：油门踩到底还继续「记账」，松开会猛冲；要防账越记越离谱。
- **源码对照**：
  - 位置：`pid.c:215-240` 条件积分——先算 `candidate_integral = integral + error*dt` 和 `candidate_output`，只有当 `candidate_output` 在 `[output_min, output_max]` 内，或「输出已超上限但 `ki*error < 0`（误差在拉回）」时才接受新积分。
  - 分析：这保证积分只在「输出尚未饱和」或「正在退出饱和」时累加，避免饱和方向继续累积；`PID_SetTunings` 里 Ki 为 0 时也清积分（`:84-88`）。

### 微分滤波（Derivative filter）
- **定义**：对微分项做一阶低通滤波，抑制测量噪声被微分放大的抖动。
- **白话**：D 项爱放大毛刺，先磨平再算，输出才不抖。
- **源码对照**：
  - 位置：`pid.c:181-202` `derivative_raw = -(measurement - prev_measurement)/dt`（对测量值求导），再 `alpha = dt/(tau+dt)`，`derivative_filtered += alpha*(derivative_raw - derivative_filtered)`。
  - 时间常数：`pid.h:25` `float derivative_filter_tau`（默认 `PID_DEFAULT_D_TAU = 0.020f`，即 20ms，见 `pid.c:5`）。
  - 分析：注释 `:169-172` 说明 D 项改为「对测量值求导」而非对误差求导，这样目标值阶跃时不会产生 derivative kick（微分冲击）。

### 跟踪抗饱和增益（Tracking gain）
- **定义**：把「期望输出与实际施加输出的差」按增益反馈回积分项，主动把积分拉回可执行范围。
- **白话**：发现油门卡在上限，悄悄把积分退回来，避免憋住后猛冲。
- **源码对照**：
  - 位置：`pid.c:266-298` `if (use_tracking && PID_KiEnabled)` 时 `integral += tracking_gain * (applied_output - output) * dt / ki`，再把 `ki*integral` 限幅后反解回 integral。
  - 增益：`pid.h:28` `float tracking_gain`（默认 `PID_DEFAULT_TRACK_K = 5.0f`，见 `pid.c:6`）。
  - 分析：`applied_output` 是 `Motor_GetAppliedOutput()` 的「真实施加 PWM」，与 PID 目标 `output` 有差异（因 PWM 斜坡），差异反向喂回积分器，防止 PWM 爬升期错误积大量积分。这是 `PID_UpdateTracked()` 相对 `PID_Update()` 的关键增强。

### PWM 斜坡（PWM ramp）
- **定义**：让 PWM 输出在若干周期内逐步逼近目标，而非瞬间跳变或直接换向。
- **白话**：给电机「缓加油缓刹车」，防大电流突跳和突然换向。
- **源码对照**：
  - 位置：`motor.c:23` `#define MOTOR_PWM_RAMP_STEP 15`（每控制周期最多改 15 个计数）；`:362` `Motor_SetOutput()` 三段式（正/反/零）分别朝目标逐周期加/减 `MOTOR_PWM_RAMP_STEP`。
  - 换向安全：`motor.c:403-446` 当前正方向时新目标反方向，先 `next_output -= RAMP_STEP` 降到 0，`:565-587` 只有 `next_output==0` 才切 `Motor_SetDirection(0)`（制动），再反向升。
  - 分析：注释 `:326-361` 明确「换向前 PWM 先降到 0、PWM=0 后才改 INA/INB、换向后 PWM 再逐渐升」；`150/15×10ms≈100ms` 完成从 150 到 0。

### 限位（Limit switch）
- **定义**：装在行程两端的开关/传感器，触发表示机构到极限，用于回零和防越界。
- **白话**：轨道的「安全挡板 + 感应开关」，走到头就知道不能再走。
- **源码对照**：
  - 位置：协议文档第 11 节 HOME 流程「检测底部回零条件 → 立即停止制动 → 高度设 0」；错误码 `2005 限位信号异常`、`2007 回零失败`。
  - 分析：协议第 11 节还规定「上下限位同时有效或堵转时立即停止并失败」「越界命令在电机通电前拒绝」，这是 STM32 本地安全逻辑，不在树莓派侧。

### 堵转（Stall）
- **定义**：电机被机械卡住无法转但仍通电，电流升高、转速为零。
- **白话**：轮子被卡死还在硬推，电机憋住。
- **源码对照**：
  - 位置：协议文档错误码 `1002 夹爪堵转`、`2003 升降堵转`；第 11 节「回零超时、方向与限位矛盾、上下限位同时有效或堵转时立即停止并失败」。
  - 分析：堵转判据（电流阈值×持续时间）属于「冻结参数」之一（协议第 17 节「升降堵转和过流判据 ____」），须固化在 STM32 配置中，不通过串口下发。

### 过流（Overcurrent）
- **定义**：电流超安全阈值，可能烧电机/驱动，需立即保护。
- **白话**：电流「超载」会烧东西，必须马上断。
- **源码对照**：
  - 位置：协议文档错误码 `1003 夹爪过流`、`2004 升降过流`；第 17 节把「夹爪/升降堵转和过流判据」列为冻结参数。
  - 分析：过流保护在 STM32 本地闭环内完成（读电流 → 超阈值即停），树莓派只能看到 `0x21` 里的对应错误码终态。

### 急停（Emergency stop / E-stop）
- **定义**：最高优先级安全停机，立即切断/停止所有执行器，需人工复位才能解除。
- **白话**：红色「全停」按钮，一键让所有能动的停下，且不能靠软件偷偷恢复。
- **源码对照**：
  - 上位机：`stop_transport.py:24` `dispatch_stop_frames()` 先发零速度帧（`encode_velocity(0,0,0, mode=0)`）再发 `MSG_TYPE_EMERGENCY_STOP` 帧，两帧都成功才算 success。
  - 状态位：`serial_protocol.py:33` `STATUS_EMERGENCY_STOP = 1 << 0`；`robot_bridge/node.py:779` 收到带该位的 STATUS 就 `_cancel_pending_mechanism(9001, ...)`。
  - 固件：`chassis_control.c:238` `if (RPI_IsEmergencyStopActive() || ...)` 置 `CHASSIS_CONTROL_SAFE_STOP` 并停所有电机。
  - 分析：`rpi_protocol.h:40-44` 注释「软件急停只能由本地重新授权流程显式清除，通信恢复本身不会自动清除」——即急停锁存，HELLO/心跳/普通命令不能解除。

### 锁存（Latch）
- **定义**：某状态一旦触发就保持，直到显式复位，防止信号消失后自动恢复。
- **白话**：「按下去就卡住」，不会因松手或信号消失自己弹回来。
- **源码对照**：
  - 位置：`safety.c:29` `volatile uint8_t safety_armed = 0U`（急停/授权锁存）；`chassis_control.c:16` `volatile uint8_t chassis_manual_takeover_latched = 0U`（手动接管锁存）。
  - 复位：`chassis_control.c:154` `ChassisControl_ReleaseManualTakeover()` 显式清 `chassis_manual_takeover_latched` 并回 `BOOT_SAFE`。
  - 分析：锁存保证急停/接管不会因为「信号短暂消失」就解除，必须走明确的复位流程。

### 回零（Homing）
- **定义**：让机构运动到已知原点（通常限位处），把当前位置标定为 0，建立绝对坐标基准。
- **白话**：让升降台「先摸到底」，从此知道自己在多高。
- **源码对照**：
  - 位置：协议文档第 11 节 HOME 流程 `低速向下 → 检测底部回零条件 → 立即停止制动 → 当前高度设 0 mm → SUCCEEDED`。
  - 未回零保护：协议第 11 节「未回零时 LIFT_ABS 返回 REJECTED/2001」；第 6 节操作表 operation=6 HOME。
  - 分析：`robot_bridge/node.py:528` 把 `"HOME"` 映射到 `ProtocolOperation.HOME` 下发；上电/复位后升降一律「未回零」，boot_id 变化时也视为未回零（协议第 4 节）。

### 麦轮与运动学（Mecanum wheel / Kinematics）
- **定义**：麦轮是带斜向小滚轮的轮子，四个配合实现全向移动；运动学把「期望车体速度」换算成「四轮目标转速」。
- **白话**：斜着装的特殊轮子让车能横着走；运动学是「车要怎么动 → 每个轮子转多快」的换算。
- **源码对照**：
  - 位置：`wheel_sync.h:22` 注释「base_target_rpm：麦轮运动学产生的原始四轮目标」；`chassis_control.c:361` `Chassis_SetVelocityPhysical(vx, vy, wz, target_rpm)` 调 `chassis.c` 的逆运动学。
  - 车身速度回传：`chassis_control.c:75` `Chassis_GetBodyVelocity(actual_rpm, &vx, &vy, &wz)` 是正运动学（四轮 RPM → 车体速度），`:82` `RPI_SendOdom(vx, vy, wz)`。
  - 分析：运动学分正/逆两个方向——逆运动学把 `/cmd_vel` 的 `vx/vy/wz` 转成四轮 RPM 下发，正运动学把四轮编码器 RPM 转回车体速度发给树莓派做里程计。

### 四轮同步（Wheel synchronization）
- **定义**：四轮目标转速接近时，以四轮实际平均速度为基准，用比例修正让各轮实际速度一致，减少横移偏转。
- **白话**：四轮「转速不一致会让车走偏」，这个模块把它们拉齐。
- **源码对照**：
  - 位置：`四轮同步PID模块/wheel_sync.c:72` `WheelSync_Update()`——先按各轮目标方向归一化实际速度（`:150-155` `normalized_actual[i] = actual_rpm[i] * direction[i]`），算平均（`:157`），再 `correction = kp * (average - normalized_actual[i])`（`:165-166`）后限幅 `±max_correction_rpm`。
  - 启用条件：`:109-141` 四轮理论目标绝对值都要 ≥ `enable_min_rpm`（10 RPM），且 `target_abs_max - target_abs_min <= target_tolerance_rpm`（3 RPM）才同步；否则原样返回。
  - 参数：`wheel_sync.c:52-56` `kp=0.15、max_correction_rpm=8、enable_min_rpm=10、target_tolerance_rpm=3`。
  - 分析：接入说明第 9 节「先用 60 RPM 纯右移测试」，若交替快慢/抖动就减小同步 Kp；同步修正经常顶到 8 RPM 上限说明底层单轮 PID/供电/机械差异过大。

### 陀螺仪（Gyroscope）与航向闭环（Heading loop）
- **定义**：陀螺仪测角速度，积分得朝向变化；航向闭环用陀螺仪反馈修正车体朝向漂移。
- **白话**：给车装「指南针 + 陀螺」，知道它有没有偷偷转向。
- **源码对照**：
  - 串口：`serial_protocol.py:89` `ImuSample(gyro_z_radps, valid)`，`MSG_TYPE_IMU=0x11`；固件 `rpi_protocol.h:57` `RPI_SendImu(gyro_z, valid)`。
  - 上位机：`robot_bridge/node.py:926-930` 把 `gyro_z_radps` 填进 `Imu.angular_velocity.z` 发 `/imu/data`。
  - 分析：接入说明第 11 节「若四轮 RPM 已一致车体仍持续旋转，需增加陀螺仪航向闭环」——四轮同步只能让轮速一致，无法测地面打滑导致的整车旋转，那是陀螺仪航向闭环的职责。

### 物理启动授权（Physical start / Arm）
- **定义**：需人工建立的「允许运动」状态，未授权时一切运动被禁止。
- **白话**：上电后车默认「锁死」，人工确认后才允许动，防误启动。
- **源码对照**：
  - 状态位：`serial_protocol.py:34` `STATUS_PHYSICAL_START = 1 << 1`；`robot_bridge/node.py:447` `_real_mechanism_ready()` 里 `if not status.flags & STATUS_PHYSICAL_START: return False, 5, "physical start is not authorized"`。
  - 固件：`chassis_control.c:251` `if (!physical_start) { 置 BOOT_SAFE; 停所有电机; return; }`——这是任何控制源（含遥控器）运动的前提。
  - 分析：`Safety_IsArmed()`（`safety.h:28`）返回 `safety_armed`，长按 USER KEY 触发重新授权请求（`safety.c:210-219`）。

### 手动接管（Manual takeover）
- **定义**：遥控器介入时手动控制权覆盖自动控制，且接管状态锁存直到显式释放。
- **白话**：人一抢遥控器，程序就退到一边，直到人明确交还。
- **源码对照**：
  - 位置：`chassis_control.c:265` `if (Remote_IsOnline())` 立即 `chassis_manual_takeover_latched = 1U`，`:271-274` 把树莓派新命令取出并丢弃，进入 `CHASSIS_CONTROL_REMOTE_MANUAL`。
  - 掉线保护：`:306-312` 遥控器刚掉线时 `ChassisControl_ReleaseManualTakeover(); ChassisControl_Stop()`，不能瞬间恢复自动。
  - 分析：注释 `:234-236` 说明树莓派「通信看门狗」只禁自动模式，不能把在线遥控器人工接管一起封死——人工接管优先级高于 watchdog。

## 四、视觉与感知

### OpenCV
- **定义**：开源计算机视觉库，提供图像读取、颜色转换、滤波、形态学、轮廓提取等算法。
- **白话**：图像处理的「瑞士军刀」。
- **源码对照**：
  - 位置：`cube_perception/cube_perception/opencv_detector.py:5` `import cv2`，`detect()` 里密集调用 `cv2.cvtColor/inRange/morphologyEx/findContours/contourArea/convexHull` 等。
  - ROS 图像转换：`cube_perception/node.py:4` `from cv_bridge import CvBridge`，`:111` `frame = self.bridge.imgmsg_to_cv2(msg, desired_encoding="bgr8")` 把 ROS `Image` 消息转成 OpenCV 的 BGR 矩阵。

### HSV 颜色空间
- **定义**：用色相（H）、饱和度（S）、明度（V）描述颜色，比 RGB 更贴近人眼且抗光照变化，便于按颜色分割。
- **白话**：换一种「说颜色」的方式，让「找橙色」更好写。
- **源码对照**：
  - 位置：`opencv_detector.py:132` `hsv = cv2.cvtColor(frame, cv2.COLOR_BGR2HSV)`；阈值 `:14-15` 默认 `orange_hsv=[5,100,80,25,255,255]`、`purple_hsv=[125,60,50,165,255,255]`。
  - 分析：OpenCV 的 HSV 范围 H∈[0,179]、S/V∈[0,255]（`DetectorConfig.validate()` 里 `limits=[179,255,255]` 校验，见 `:81`）；六元数组是 `[Hmin,Smin,Vmin,Hmax,Smax,Vmax]`。

### 阈值分割与二值图（Thresholding / Binary mask）
- **定义**：把像素按阈值分成「目标/背景」两类，生成黑白 mask。
- **白话**：把画面变成「符合颜色的地方白、其他黑」的遮罩。
- **源码对照**：
  - 位置：`opencv_detector.py:151` `mask = cv2.inRange(hsv, lower, upper)`，`:152` `mask = cv2.bitwise_and(mask, roi_mask)` 与 ROI 求交。
  - 分析：`inRange` 返回单通道 8 位图（0/255），后续 `findContours` 只在这张黑白图上找白块边界。

### 形态学操作（Morphology，开/闭运算）
- **定义**：用结构元素对二值图膨胀/腐蚀；开运算去孤立噪点，闭运算填小空洞。
- **白话**：给黑白图「打磨」——去小噪点、补小洞，让色块更干净。
- **源码对照**：
  - 位置：`opencv_detector.py:134` `kernel = cv2.getStructuringElement(cv2.MORPH_RECT, (kernel_size, kernel_size))`，`:153` `cv2.morphologyEx(mask, cv2.MORPH_OPEN, kernel)`，`:154` `cv2.morphologyEx(mask, cv2.MORPH_CLOSE, kernel)`。
  - 分析：`morph_kernel=5`（`node.py:26`）是核边长，越大去噪越狠但可能把目标也磨掉；先 OPEN 去噪、再 CLOSE 填洞，最后再和 ROI 求交（`:155`）。

### ROI（Region of Interest，感兴趣区域）
- **定义**：只在画面指定子区域处理，忽略无关背景。
- **白话**：只盯着画面某一块找，其他地方不看。
- **源码对照**：
  - 位置：`opencv_detector.py:124` `roi_bounds()` 用 `roi_*_ratio * image_width/height` 算像素范围；`:140-143` 用 `cv2.rectangle` 画一个白色 ROI mask。
  - 参数：`node.py:32-35` `roi_x_min_ratio` 等默认 `0.0/1.0`（即全画面）；`vision_demo_roi.json` 提供带演示 ROI 的样例。
  - 分析：ROI 归一化到 0~1，与分辨率无关；`DetectorConfig.validate():99-105` 强制 `0 <= low < high <= 1`。

### 轮廓（Contour）
- **定义**：二值图白色区域边界点集合，用于提取形状/面积/外接矩形。
- **白话**：把白块外形描边，好量面积和形状。
- **源码对照**：
  - 位置：`opencv_detector.py:157` `contours, _ = cv2.findContours(mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)`，`:168` `contour_area = cv2.contourArea(contour)`。
  - 分析：`RETR_EXTERNAL` 只取最外层轮廓，`CHAIN_APPROX_SIMPLE` 压缩共线点；`:184` `cv2.minAreaRect` 取最小外接旋转矩形，`:188` `cv2.convexHull` 取凸包。

### 矩形度（Rectangularity）
- **定义**：轮廓面积与最小外接矩形面积之比，接近 1 说明形状接近矩形。
- **白话**：「这坨白块有多像长方形」的评分。
- **源码对照**：
  - 位置：`opencv_detector.py:187` `rotated_area = short_side * long_side`，`:189` `rectangularity = contour_area / max(rotated_area, 1e-6)`；`:193-197` 低于 `min_rectangularity`（默认 0.35）就丢弃。
  - 分析：方块被斜视时投影仍是平行四边形，`minAreaRect` 的外接矩形面积近似真实面积，矩形度接近 1；不规则形状矩形度明显偏低。

### 凸包与实心度（Convex hull / Solidity）
- **定义**：凸包是包含轮廓的最小凸多边形；实心度 = 轮廓面积/凸包面积，反映「多实、有没有大缺口」。
- **白话**：看白块是「实心完整」还是「破洞缺口」。
- **源码对照**：
  - 位置：`opencv_detector.py:188` `hull_area = cv2.contourArea(cv2.convexHull(contour))`，`:190` `solidity = contour_area / max(hull_area, 1e-6)`；`:193-197` 低于 `min_solidity`（默认 0.50）丢弃。
  - 分析：实心方块 solidity≈1；被遮挡或形状怪异的色块 solidity 明显 <1，借此剔除。

### 长宽比（Aspect ratio）
- **定义**：轮廓长边与短边之比，衡量是否被拉长。
- **白话**：看这坨东西是不是「细长条」，方块应接近 1:1。
- **源码对照**：
  - 位置：`opencv_detector.py:185-186` `short_side = min(raw_width, raw_height)`、`long_side = max(...)`，`:191` `aspect_ratio = long_side / max(short_side, 1e-6)`；`:193-197` 超过 `max_rotated_aspect_ratio`（默认 3.2）丢弃。
  - 分析：斜视角下方块的成像长宽比会偏离 1，所以阈值放宽到 3.2 而不是 1.2；真正的细长条（线、杆）会被滤掉。

### 针孔模型（Pinhole model）与焦距 / 像素焦距
- **定义**：把相机近似小孔成像，像高与物高、物距、焦距成比例；像素焦距（focal_px）用像素表示焦距。
- **白话**：用三角形相似算距离——知道物体真实大小和镜头焦距就能反推距离。
- **源码对照**：
  - 位置：`perception.py:61` `distance = cube_size_m * focal_px / candidate.width_px`；`opencv_detector.py:218` 同样 `distance_m = cube_size_m * focal_px / short_side`。
  - 焦距来源：`cube_perception/node.py:106-108` `_on_camera_info()` 若 `msg.k[0] > 0` 就用 `CameraInfo` 的内参 `k[0]`（fx），否则用 `fallback_focal_px`（默认 700，见 `node.py:25`）。
  - 分析：`k[0]` 是相机内参矩阵左上角 fx（x 方向焦距，单位像素）；GF100 1280×720 台架候选值 2550 单独存在 `config/vision_gf100_1280x720_bench.json`。

### 相机内参（Intrinsics）与标定（Calibration）
- **定义**：内参是焦距、主点、畸变系数等固有参数；标定通过已知图案求取这些参数。
- **白话**：给相机「量准焦距和畸变」，测距才准；换镜头/分辨率/对焦都得重量。
- **源码对照**：
  - 位置：`cube_perception/node.py:52` `self.create_subscription(CameraInfo, "/camera/camera_info", self._on_camera_info, 10)`，`:107` `self.detector.config.focal_px = float(msg.k[0])`。
  - 分析：README 强调「改变分辨率、镜头或对焦后必须重新标定」；当前用 `focal_px` 兜底、尚未做畸变矫正（README 第 7 节明确列为现场待办）。

### 单目测距（Monocular distance estimation）
- **定义**：只用单相机，借助已知物体尺寸和成像比例估算距离。
- **白话**：一只眼也能估距离——前提是知道那东西真实多大。
- **源码对照**：
  - 位置：`perception.py:50` `estimate_from_candidate()` 汇总，`:61-64` 同时算 `distance`、`lateral`、`yaw_error`。
  - 分析：`cube_size_m=0.1`（方块边长 10cm）是测距关键假设（`node.py:24`）；README 注明「视觉估距假设方块尺寸已知」，斜视时误差会增大。

### 畸变矫正（Distortion correction）
- **定义**：用标定的畸变系数修正广角镜头的桶形/枕形畸变。
- **白话**：把镜头「鱼眼变弯」的画面掰直。
- **源码对照**：
  - 位置：当前**未实现**，README 第 7 节明确「代码尚未进行畸变矫正、透视/仿射矫正，也没有 ToF 融合」。
  - 分析：只有真实视角证明误差影响抓取时再加矫正，避免盲目增加复杂度（README 原话）。

### 连续帧确认（Temporal filtering / multi-frame confirmation）
- **定义**：连续多帧都检测到同一目标才对外发布，避免单帧误检；短暂丢失若干帧内仍保留跟踪。
- **白话**：「多看一眼再确认」，一闪而过的误检不算数。
- **源码对照**：
  - 位置：`temporal_filter.py:54` `TemporalDetectionFilter`，`:98` `matched = track is not None and _pixel_distance(...) <= match_distance_px`，`:107` `if track.streak >= confirm_frames: confirmed.append(...)`。
  - 丢帧：`:78-85` 没候选时 `track.missed += 1; track.streak = 0`，`:83` `missed > max_missed_frames` 就删除该跟踪。
  - 参数：`confirm_frames=3、max_missed_frames=3、match_distance_px=80.0`（`node.py:28-30`）。
  - 分析：`_choose_candidate()`（`:113`）对同一颜色多候选时，若附近恰好一个就匹配，多个则标记 ambiguous 不确认——防止两个相近方块互相串扰。

### 目标跟踪与平滑（Tracking / Smoothing，EMA）
- **定义**：跨帧匹配同一目标并对其位置/距离做指数平滑，减少数值抖动。
- **白话**：给连续检测配对成同一目标，并把数据「抹平」。
- **源码对照**：
  - 位置：`temporal_filter.py:41` `_smooth()` 用 `keep = 1 - alpha`，对 `confidence/lateral_m/distance_m/yaw_error/pixel_x/pixel_y` 全做 `keep*prev + alpha*cur`。
  - 参数：`smoothing_alpha=0.4`（`node.py:31`），越大越跟手、越小越平滑。
  - 分析：这是指数滑动平均（EMA），`alpha` 是新值权重；`:103` 只有匹配上才平滑并 `streak += 1`，新目标直接建 track 不继承旧值。

### 召回率（Recall）
- **定义**：真实目标中被正确检出的比例，衡量「该看到的有没有都看到」。
- **白话**：100 个该抓的方块，抓到几个——衡量「漏没漏」。
- **源码对照**：
  - 位置：`cube_perception/README.md` 第 4 节 `vision_report --min-detection-ratio 0.90` 做逐帧检测比例验收；README 第 7 节要求「统计至少 30 段/张每种颜色的召回率」。
  - 分析：`report.py` 计算「检测帧比例、最长连续检测、置信度/距离统计」，只有目标每帧都在画面时检测比例才可近似当召回率，目标本不在画面的帧不能算漏检（README 第 4 节明确）。

### 横向偏差（Lateral offset）
- **定义**：目标中心相对相机光轴（画面中线）的水平偏移，换算成真实米数。
- **白话**：方块在画面里偏左还是偏右了多远，用来横向对齐。
- **源码对照**：
  - 位置：`perception.py:62-63` `pixel_error = center_x - image_width/2`，`lateral = pixel_error * distance / focal_px`；`opencv_detector.py:219-223` 同公式。
  - 消费：`manipulator_client/node.py:520` `calculate_alignment_command(lateral_m=..., kp_lateral=1.2, ...)`，`manipulator.py:320` `linear_y = -kp_lateral * lateral_m` 用横向偏差做 P 控制对准。
  - 分析：横向偏差和 `yaw_error_rad = pixel_error/focal_px`（`perception.py:64`）都基于针孔几何，单位分别是米和弧度。

### JSONL
- **定义**：每行一个 JSON 对象的文本格式，适合逐帧流式写检测结果。
- **白话**：一行一条记录的「流水账」，程序好读。
- **源码对照**：

  - 分析：`timestamp_kind: media` 表示时间来自原录像（可用 `--start-s/--end-s` 选区间），`monotonic` 表示实时时钟；`report.py` 拒绝旧格式（`error: legacy JSONL is not supported`）。

## 五、定位与导航

### 定位（Localization）
- **定义**：估计机器人在世界坐标系中的位置与朝向。
- **白话**：回答「我在哪、朝哪边」。
- **源码对照**：
  - 位置：`localization/node.py:23` `class LocalizationNode`，订阅 `/wheel_odom`、`/imu/data`、`/robot/status`，发布 `/pose` 和 TF。
  - 数据流：`robot_bridge` 发 `/wheel_odom`（轮式里程计）+ `/imu/data` → `localization` 融合 → 发 `/pose` → `motion_control` 订 `/pose` 做导航。

### 里程计积分 / 航位推算（Odometry integration / Dead reckoning）
- **定义**：对速度随时间积分推算位移与朝向，误差随时间累积。
- **白话**：靠「知道自己每刻往哪动多快」一步步累加出现在的位置，越走越不准。
- **源码对照**：
  - 位置：`navigation.py:108` `class OdometryIntegrator`，`:113` `update(body_velocity, dt, imu_wz)`，`:119-122` `mid_yaw = yaw + 0.5*wz*dt`，`dx = (cos(mid_yaw)*vx - sin(mid_yaw)*vy)*dt`，再归一化 yaw。
  - 融合：`:116-118` `wz = (1-imu_yaw_weight)*body_velocity.wz + imu_yaw_weight*imu_wz`（默认 `imu_yaw_weight=0.15`）。
  - 使用：`robot_bridge/node.py:177` `self.integrator = OdometryIntegrator(...)`，`:880` `pose = self.integrator.update(measured_velocity, dt, measured_velocity.wz)`。
  - 分析：`dt > 0.5` 直接返回旧位姿（`:114`），防长时间无数据时积分出荒谬跳变；README 注明是「冲刺期简化模型」。

### 传感器融合与 EKF（Sensor fusion / Extended Kalman Filter）
- **定义**：把多传感器信息按各自噪声统计合并得到更准估计；EKF 是处理非线性系统的主流卡尔曼滤波变体。
- **白话**：让多个「各有误差」的传感器互相校正，得出更靠谱的结果。
- **源码对照**：
  - 当前简化实现：`localization/node.py:100` `wz, used_imu = choose_yaw_rate(wheel_wz, imu_wz, imu_age, stale_after, status_valid=...)`——IMU 有效且新鲜时用 IMU 角速度，否则回退轮式里程计。
  - 协方差：`robot_bridge/node.py:892-906` 用 `odom_pose_xy_variance` 等填 `Odometry.covariance`，`:936` 用 `covariance[0]=-1` 表示 IMU 测量不可用（`sensor_msgs/Imu` 约定）。
  - 分析：README 后续计划「替换为 `robot_localization`（EKF）当单块任务通过后」，当前只是「IMU 偏航 + 轮式里程计」的门控融合，非真正的卡尔曼滤波。

### 位姿（Pose）与偏航角（Yaw）
- **定义**：位姿是位置 (x, y) + 朝向角；偏航角是绕竖直轴的旋转角（航向）。
- **白话**：「站在哪 + 朝哪」；偏航就是「车头朝哪」的角度。
- **源码对照**：
  - 位置：`models.py:40` `@dataclass(frozen=True) class Pose2D: x, y, yaw`；`navigation.py:9` `normalize_angle(angle) = math.atan2(sin, cos)` 把角度规约到 (-π, π]。
  - 提取：`motion_control/node.py:102` `Pose2D(p.x, p.y, quaternion_to_yaw(q.x,q.y,q.z,q.w))` 从 Odometry 消息取位姿和偏航。
  - 分析：`GoToPoseController.errors()`（`navigation.py:82-89`）把世界系误差 `dx,dy` 用 `cos_yaw/sin_yaw` 旋转到机体坐标系，得到前后误差 `ex` 和横向误差 `ey`。

### P 控制（Proportional control）与比例增益
- **定义**：输出与误差成正比的最简单反馈控制，增益决定响应强弱。
- **白话**：「差多少补多少」，旋钮调「补多猛」。
- **源码对照**：
  - 位置：`navigation.py:101-105` `command()` 返回 `clamp(kx*ex, max_vx*scale)`、`clamp(ky*ey, max_vy*scale)`、`clamp(kyaw*eyaw, max_wz)`。
  - 增益：`motion_control/node.py:29` `kx=1.2, ky=1.2, kyaw=1.8`。
  - 分析：`motion_control/README.md` 第 6 节明确「当前是适合固定路点的 P 控制，不是 Nav2，没有障碍物规划和避障」。

### 到点控制（Go-to-pose）
- **定义**：把机器人导航到目标位姿，在到达容差内判定完成。
- **白话**：给个目标点，自己算怎么过去、到了就停。
- **源码对照**：
  - 位置：`navigation.py:91` `at_goal()` = `hypot(ex,ey) <= position_tolerance and abs(eyaw) <= yaw_tolerance`；`:95` `command()` 先判到点返回零速度。
  - 容差：`motion_control/node.py:31` `position_tolerance=0.05`（米）、`yaw_tolerance=radians(5°)`。
  - 触发：`motion_control/node.py:164` `if self.controller.at_goal(self.pose, self.goal): self._finish("SUCCESS")`。

### 减速半径（Slow radius）
- **定义**：距目标小于该半径时按比例降低允许最大速度，实现接近时平滑减速。
- **白话**：快到目标时「自动减速」，别冲过头。
- **源码对照**：
  - 位置：`navigation.py:100` `scale = min(1.0, max(0.2, distance / slow_radius))`，`:101-102` 用 `max_vx * scale` 限速。
  - 参数：`slow_radius=0.35`（`motion_control/node.py:32`）。
  - 分析：`distance` 接近 0 时 `scale` 压到下限 0.2，保证接近目标时最多只能以 20% 最大速度移动。

### 加速度限制（Acceleration / slew-rate limit）
- **定义**：限制速度指令每秒最大变化量，避免速度突跳导致打滑/冲击。
- **白话**：给速度命令「限速爬坡」，不能一下从 0 飙到满。
- **源码对照**：
  - 位置：`navigation.py:29` `limit_velocity_rate()`，`:42-45` `move_toward(previous.vx, target.vx, max_ax*dt)` 逐方向限步进。
  - 使用：`motion_control/node.py:168-173` `dt = min(max(0, now-last_control_time), max_control_dt)`，再 `command = limit_velocity_rate(...)`。
  - 参数：`max_ax=0.8、max_ay=0.8、max_awz=2.0、max_control_dt_s=0.1`（`motion_control/node.py:33-34`）。
  - 分析：`max_control_dt_s` 防止控制循环偶发卡顿后恢复时 `dt` 过大导致速度突跳（README 第 5 节）。

### 角速度分歧（Yaw rate divergence）
- **定义**：轮式里程计推算角速度与 IMU 陀螺仪角速度差异过大，通常提示打滑或传感器异常。
- **白话**：两个「测转向」的传感器说得对不上，多半轮子打滑了。
- **源码对照**：
  - 位置：`localization/node.py:125` `divergence, is_divergent = detect_yaw_divergence(wheel_wz, active_imu_wz, threshold=0.5)`，`:130-135` 超阈就 `warn`。
  - 参数：`localization/README.md` `divergence_threshold: 0.5`（rad/s）。
  - 分析：分歧只打 warning 不拒绝发布（README 质量检查表「不拒绝，仅提示可能打滑」），因为分歧不等于数据非法，只是提示需要关注。

### 位姿跳变（Pose jump）
- **定义**：相邻两帧位姿变化对应速度超过物理极限，判定为异常数据。
- **白话**：车不可能「瞬移」，位置突然跳一大截就是数据错了。
- **源码对照**：
  - 位置：`localization/node.py:165-180` `detect_pose_jump(prev_x, prev_y, curr_x, curr_y, dt, max_speed=3.0)`，超限则 `return`（拒绝发布该帧 `/pose`）。
  - 参数：`localization/README.md` `max_speed_mps: 3.0`。
  - 分析：拒绝发布的同时也不广播 TF，保证下游 `motion_control` 不会拿到跳变位姿导致猛打方向。

### NaN / Inf 拦截
- **定义**：浮点异常值（非数/无穷）在传感器或计算中产生，进入控制器会引发灾难性行为，需在边界拦截。
- **白话**：把「坏数字」挡在门外，别污染后面计算。
- **源码对照**：
  - 位姿：`navigation.py:17` `pose_is_finite()`；`motion_control/node.py:103` 位姿含 NaN/Inf 就忽略该帧。
  - 里程计：`localization/node.py:137-153` 把 x/y/z、四元数、线/角速度全塞进 `odometry_is_finite()`，任一非有限就拒绝发布。
  - 串口：`serial_protocol.py:299` `_require_finite()` 在编码 ODOM/IMU/Velocity 前拒绝 NaN/Inf 载荷。
  - 分析：`mission.py` 和 `motion_control` 的目标 `Pose2D` 也做 `pose_is_finite` 检查（`motion_control/node.py:123`），防止 NaN 目标下发底盘。

## 六、机械机构与任务

### 夹爪（Gripper）
- **定义**：抓取/释放物体的执行机构，通常电机驱动开合。
- **白话**：机器人的「手」，负责抓方块、放方块。
- **源码对照**：
  - 服务：`robot_bridge/node.py:148-151` 注册 `/gripper/grab`、`/gripper/release`（`ExecuteMechanism`），都路由到 `_mechanism`。
  - 协议：`serial_protocol.py:46-52` `MechanismOperation.GRAB=1、RELEASE=2`；协议文档操作表第 6 节。
  - 判据：协议 GRAB 成功 =「夹爪达到抓取条件 + 方块存在判据成立」，状态位 `STATUS_GRIPPER_CLOSED`（`serial_protocol.py:37`）和 `STATUS_CUBE_PRESENT`（`:38`）。

### 升降（Lift）
- **定义**：把夹爪/负载在竖直方向移动的机构，需绝对高度定位和回零。
- **白话**：机器人的「升降台」，把方块送到不同高度楼层。
- **源码对照**：
  - 服务：`robot_bridge/node.py:172` `SetLiftHeight, "/lift/set_height", self._lift`；`_lift():610` 把 `height_m` 转 `parameter=int(round(height_m*1000))` 下发（米→毫米）。
  - 协议：`serial_protocol.py:49` `MechanismOperation.LIFT_ABS=3`；`robot_bridge/node.py:626` 用 `ProtocolOperation.LIFT_ABS`。
  - 判据：协议 LIFT_ABS 成功 =「位置进入本地容差并稳定规定时间」。

### 绝对定位（Absolute positioning）
- **定义**：给定目标绝对坐标（如高度 mm）的定位，区别于相对增量运动；依赖回零建立原点。
- **白话**：「升到离地 120 mm」，而不是「再升 30 mm」。
- **源码对照**：
  - 位置：协议文档第 6 节 `LIFT_ABS` 的 parameter 是「目标高度 mm」；第 16 节示例 `operation=3, parameter=120, timeout_ms=4000` 即升到 120mm。
  - 转换：`robot_bridge/node.py:627` `parameter=int(round(height_m * 1000.0))`。
  - 分析：`SetLiftHeight.srv` 请求 `height_m`（米），`robot_bridge` 负责转成协议要求的毫米 int32，符合「接口用米、协议用毫米」的分层约定。

### 任务状态机（Mission state machine）
- **定义**：把整场任务拆成有序状态，按反馈迁移。
- **白话**：比赛的「流程脚本」，走到哪步、下一步干啥、失败怎么办都有规定。
- **源码对照**：
  - 位置：`mission.py:10` `MissionState` 枚举 14 个状态（`SELF_CHECK → WAIT_FOR_PHYSICAL_START → GO_TO_ORANGE → PICK_ORANGE → ... → COMPLETE`）；`mission.py:62` `tick()` 每周期驱动。
  - 迁移：`mission.py:106` `_advance_after_success()` 用 `if/elif` 写死每状态的成功后跳转，如 `PICK_ORANGE` 成功后 `cargo.add(ORANGE)`，未满目标回 `GO_TO_ORANGE`，满则去 `GO_TO_BUILD`。
  - 异常：`mission.py:75` 急停立即 `SAFE_STOP`，`:80` 通信失联 `fail(COMMUNICATION_ERROR)`，`:84` 超时 `_retry_or_fail(TIMEOUT)`，`:97` 重试超 `max_retries` 才 FAILED。
  - 分析：`mission_manager/node.py:83-98` 按当前状态给 `tick()` 喂不同输入（`SELF_CHECK` 喂 `action_succeeded=not mechanism_fault`，`VERIFY_BUILD` 喂 `stable_for >= build_stability_s`）。

### 路点（Waypoint）
- **定义**：预定义机器人目标位姿 (x, y, theta)，作为导航中间/最终目标。
- **白话**：地图上提前标好的「目的地坐标」。
- **源码对照**：
  - 位置：`mission_manager/node.py:20-21` 参数 `orange_waypoint=[1.0,0.5,0.0]`、`purple_waypoint=[1.5,1.0,0.0]`、`build_waypoint=[0.5,1.5,1.57]`、`retreat_waypoint=[0.5,1.2,1.57]`。
  - 下发：`mission_manager/node.py:64-71` `_dispatch()` 按状态 `goal_pub.publish(self._waypoint("orange_waypoint"))` 发 `/motion/goal`。
  - 分析：`theta=1.57` 即 90°（π/2，弧度）；`_waypoint()`（`:56`）把参数数组转 `Pose2D`。

### 抓取 / 释放判据与方块传感器（Grasp/release criteria & cube sensor）
- **定义**：判断「确实抓到/放掉」的物理证据，来自方块存在传感器、夹爪到位、限位等。
- **白话**：不能只看「电机转了」，要拿到「方块真被夹住/真离开」的实锤才算成功。
- **源码对照**：
  - 状态位：`serial_protocol.py:37-38` `STATUS_GRIPPER_CLOSED`、`STATUS_CUBE_PRESENT`；`robot_bridge/node.py:951-960` 把它们映射进 `RobotStatus.gripper_closed/cube_present`。
  - 判据策略：`manipulator.py:39` `GrabVerificationPolicy`（`service_only / cube_present / gripper_and_cube`），`:169` `grab_verification_decision()` 按策略判断 `signal_satisfied`。
  - 分析：默认 `service_only`（只信服务返回成功），真车可切到 `gripper_and_cube`（要求夹爪闭合 + 方块存在，且证据要在动作之后更新，见 `manipulator.py:188-194`）；协议错误码 1001「未抓到方块」、1005「释放后方块仍未离开」。

### 掉块检测（Drop detection）
- **定义**：在搬运/放置过程中检测方块是否意外脱落。
- **白话**：搬着搬着东西掉了要能发现。
- **源码对照**：
  - 位置：`manipulator.py:75` `PlacementStabilityObserver`——放置后观察一段时间，`update():103` 收到 `PlacementEvidence.QUALIFIED` 持续 `stable_duration_s` 判 `STABLE`，`FAILED` 立即失败，超 `observation_timeout_s` 判 `INCONCLUSIVE`。
  - 证据策略：`manipulator_client/node.py:100-109` `placement_evidence_policy`（`mock_qualified / mock_failed / unavailable`），`hardware_readiness.py:40` `validate_runtime_evidence_policy` 拒绝「field 模式用模拟证据」。
  - 分析：README「仍需真实验证抓取证据、掉块检测」；当前放置稳定性用 mock 证据，真车需接真实「方块仍在/掉落」传感器信号。

## 七、部署与工具链

### 树莓派（Raspberry Pi）
- **定义**：单板计算机，作为机器人上位机运行 Linux/ROS 2，负责高层算法与串口通信。
- **白话**：车上「上层大脑」，跑 ROS 2 和视觉导航。
- **源码对照**：
  - 位置：`docs/field/RASPBERRY_PI_DEPLOYMENT_LOG_2026-08-10.md`；`robot_bridge` 运行在树莓派，`hardware.yaml:4` 串口指向 STM32 VCP。
  - 分析：树莓派通过 USB 连 STM32（USB CDC 虚拟串口），`robot_bridge` 用 `pyserial` 打开该口，把 ROS 话题/服务翻译成串口帧。

### Ubuntu 与 ROS Jazzy
- **定义**：Linux 发行版与 ROS 2 Jazzy 发行版，是上位机软件运行环境。
- **白话**：电脑/树莓派上装的操作系统和机器人框架版本。
- **源码对照**：
  - 位置：各 README 启动命令都先 `source /opt/ros/jazzy/setup.bash`（如 `robogame_interfaces/README.md:32`）。
  - 分析：`setup.bash` 注入环境变量让 ROS 2 命令行（`ros2 run/launch/topic/service`）和 Python 包能找到依赖。

### udev 与串口权限（/dev/serial/by-id、dialout）
- **定义**：udev 是 Linux 设备管理器；`/dev/serial/by-id/` 用设备身份固定串口路径；用户需加入 dialout 组才有串口读写权限。
- **白话**：让串口设备「按名字认领」而非「按插口顺序」，并给用户开门禁。
- **源码对照**：
  - 位置：`hardware.yaml:4` `serial_port: /dev/serial/by-id/usb-STMicroelectronics_STM32_Virtual_ComPort_307A39653433-if00`；`robot_bridge/README.md` 第 4 节 `ls -l /dev/serial/by-id/`、`groups`、提示 dialout 组。
  - 分析：`/dev/ttyACM0` 这类路径会随插拔顺序变，`by-id` 用芯片序列号固定，避免「换了插口就找不到车」。

### Keil（MDK）
- **定义**：ARM 微控制器常用 IDE，用于编译、烧录、调试 STM32 固件。
- **白话**：写单片机代码、烧进芯片、在线调试的「工作台」。
- **源码对照**：
  - 位置：`四轮同步PID模块/接入说明.md` 第 1-2 节要求把 `wheel_sync.c` 加入 `Core/Src`、`wheel_sync.h` 加入 `Core/Inc`，并在 Keil 工程里编译。
  - 分析：固件源码分 `Core/Src`（实现）和 `Core/Inc`（头文件），`safety.h`/`chassis_control.h` 里多处注释「方便 Keil Watch 直接观察/修改」，如 `chassis_control.h:22`。

### PTY（伪终端）模拟验收
- **定义**：用伪终端模拟串口对端，让上位机没有真实硬件时也能跑通协议逻辑。
- **白话**：用软件「假扮」单片机，先验证树莓派这边的协议对不对。
- **源码对照**：
  - 位置：`robot_bridge/README.md` 第 8 节「在 STM32 支持 0x20/0x21 前，只能使用 PTY 模拟验收」；`tests/test_robot_bridge_mechanism_integration.py` 用 PTY 套件覆盖正常操作、ACK/状态超时、重试、错误终态、急停、MCU 重启、命令互斥、STOP 抢占、串口断线重连。
  - 分析：`robot_bridge` 还有 `mock_mode`（`node.py:87` `declare_parameter("mock_mode", True)`），mock 模式下用 `MockMechanismState` 直接模拟机构，不走真实串口。

### 单元测试（unittest）
- **定义**：对单函数/模块的自动化测试，验证逻辑正确性，无需真实硬件。
- **白话**：给纯算法写「自动批改」，改动后一键知道有没有改坏。
- **源码对照**：
  - 位置：`tests/` 下 30 余个测试文件，`robogame_core/README.md` 第 4 节 `python3 -m unittest discover -s tests -v`。
  - 设计：`robogame_core` 把所有「不依赖 ROS/硬件」的纯逻辑（串口编解码、导航、任务、感知）独立出来，`tests/test_serial_protocol.py`、`test_navigation.py`、`test_mission.py` 直接测它们，不启动 ROS 节点。
  - 分析：`README.md` 开篇「自动测试和模拟流程通过不等于真车完成」，所以测试只保证逻辑正确，真车仍需实机验收。
