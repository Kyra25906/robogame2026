# 从少量编程基础到机器人项目开发：RoboGame2026 学习总结

适用对象：低年级本科生、只有少量 Python/C++ 基础、第一次参与较完整的机器人项目

总结范围：当前对话以及此前围绕视觉、机构控制、ROS2 模拟、测试和 Git 协作进行的开发

## 一、先认识我们真正完成了什么

这段开发经历最重要的成果，不只是“写了若干代码”，而是开始建立一个真实工程项目所需要的完整思维链：

```text
理解比赛任务
→ 拆分软件模块
→ 定义模块接口
→ 编写与修改代码
→ 构造模拟输入
→ 自动化测试
→ ROS2 集成验证
→ 发现问题并定位原因
→ 记录设计假设
→ Git 提交与远程协作
```

当前已经完成了一个单方块的 ROS2 模拟软件闭环：

```text
发现并对准目标
→ 抓取
→ 验证抓取成功
→ 抬升
→ 释放
→ 验证释放完成
→ 局部撤退
→ 确认撤退完成
→ 观察放置结果
→ STABLE / FAILED / INCONCLUSIVE / CANCELLED
```

它还不是现场物理闭环，因为相机位置、机械结构、真实方块和底层控制器尚未参与。但它已经具备了现场接入前应有的软件骨架。

## 二、项目开发方面学到了什么

### 1. 项目不是从“开始写代码”开始的

初学者很容易直接进入代码文件，看到哪里缺功能就在哪里增加几行。真实项目通常应该先回答：

1. 我们要解决什么问题？
2. 成功的标准是什么？
3. 哪些信息现在已经确定？
4. 哪些信息必须等机械组或现场确认？
5. 哪些部分可以先用模拟数据开发？

例如，“释放方块”不是最终目标，真正的目标是“方块被正确放置，并能证明它稳定”。因此流程不能停在 `RELEASE`，还需要撤退和稳定观察。

可迁移的方法是：每次开发前写下五项内容。

```text
目的
必要性
技术路线
需要补充的知识
验收方法
```

### 2. 大任务要拆成可验证的小步骤

这次没有一次性编写完整闭环，而是逐步完成：

```text
抓取证据框架
→ 机构服务模拟
→ 放置验证
→ 动作取消
→ 撤退完成证据
→ 稳定观察器
→ ROS2 流程接入
→ 正常与异常路径测试
```

每一步都能单独回答“是否工作”。这样出现错误时，排查范围不会覆盖整个项目。

适合初学者的原则：

- 一次只引入一个核心概念；
- 修改后立即测试；
- 没有验收标准的功能不算完成；
- 先实现清晰、可验证的版本，再考虑性能优化。

### 3. “暂时不知道”也必须进入设计

现场相机安装位置和机械臂遮挡关系尚未确定。错误做法是假设摄像头一定看得见；正确做法是：

- 明确记录当前假设；
- 为证据不足保留 `INCONCLUSIVE`；
- 制作现场确认清单；
- 把阈值设计为参数，而不是写死在代码里。

工程能力不仅是解决已知问题，也包括管理未知条件。

### 4. 完成软件闭环不等于完成现场闭环

应该准确描述项目成熟度：

| 阶段 | 说明 |
|---|---|
| 单元逻辑完成 | 独立算法可以运行 |
| 模拟软件闭环 | 模拟消息和服务可以串通 |
| ROS2 集成闭环 | 多节点真实通信可以跑通 |
| 半实物闭环 | 部分真实硬件接入 |
| 现场物理闭环 | 相机、机械臂、小车和方块共同验证 |

当前属于“ROS2 模拟集成闭环”。准确命名可以避免团队误以为项目已经具备上场条件。

## 三、软件架构方面学到了什么

### 1. 模块化：每个模块只承担清晰职责

项目中的主要模块有：

| 模块 | 主要职责 |
|---|---|
| `cube_perception` | 从图像中检测方块并输出视觉信息 |
| `manipulator_client` | 协调对准、抓取、抬升、释放和验证 |
| `robot_bridge` | 连接上层 ROS2 与模拟/真实底层硬件 |
| `robogame_core` | 保存不依赖 ROS2 的算法和状态逻辑 |
| `mission_manager` | 决定整个比赛任务下一步做什么 |
| `robogame_interfaces` | 定义节点之间传输的消息和服务 |
| `robogame_bringup` | 统一启动多个节点并进行集成测试 |

核心认识是：视觉不应该直接控制夹爪，任务管理器也不应该自己解析串口。模块之间通过明确接口协作。

### 2. 把纯算法与 ROS2 通信分开

稳定观察判定器被放在 `robogame_core`，它只接收：

```text
时间戳
当前证据
配置参数
```

它不需要知道 ROS2 topic、Node、相机驱动或串口。因此可以：

- 在 Windows 上直接运行单元测试；
- 在 Ubuntu ROS2 节点中复用；
- 以后在录像分析工具中复用；
- 更换通信方式时保留核心算法。

这是常见的“业务逻辑与基础设施分离”思想。

### 3. 流程状态与机构操作要分开

机构操作描述“硬件正在做什么”：

```text
GRAB
LIFT
RELEASE
```

流程状态描述“任务进行到哪里”：

```text
WAITING_TARGET
ALIGNING
EXECUTING
VERIFYING
RETREATING
WAITING_RETREAT_EVIDENCE
OBSERVING_STABILITY
```

同一个机构动作可以出现在不同流程中，一个流程状态也可能不对应具体机构动作。分开之后，修改机械结构不会迫使我们重写整个任务状态机。

### 4. 接口是一种团队合同

例如 `RobotStatus.msg` 中加入：

```text
bool retreat_complete
```

它不只是新增一个变量，而是在约定：

- 谁负责产生撤退完成信息；
- 什么情况下它必须为 `false`；
- 什么情况下允许变为 `true`；
- 上层如何判断它是否属于当前动作，而不是上一轮遗留状态。

修改 ROS2 接口后，需要重新构建接口包及依赖它的节点。这说明接口变化会影响系统多个部分，应当谨慎设计。

## 四、状态机和闭环控制方面学到了什么

### 1. 开环与闭环的区别

开环流程只关心命令是否发送：

```text
发送 RELEASE
→ 认为放置完成
```

闭环流程还会观察结果：

```text
发送 RELEASE
→ 检查夹爪与方块状态
→ 撤退
→ 观察场上结果
→ 根据证据决定成功或失败
```

闭环的核心不是“动作更多”，而是“结果会反馈到下一步决策”。

### 2. 服务成功不等于任务成功

服务返回 `success=true` 通常只代表底层接受并完成了命令。例如：

- `GRAB` 服务成功，不一定抓到了方块；
- `RELEASE` 服务成功，不一定放稳了方块；
- `RETREAT` 服务成功，不一定证明摄像头已经无遮挡。

因此需要额外的传感器证据和验证阶段。

### 3. 最终结果不能只有成功和失败

视觉系统可能看不清，但这不代表方块一定倒了。因此设计了：

| 结果 | 含义 |
|---|---|
| `STABLE` | 有足够证据确认稳定 |
| `FAILED` | 有明确证据确认失败 |
| `INCONCLUSIVE` | 证据不足，不能下结论 |
| `CANCELLED` | 用户或上层主动终止流程 |

这是一种重要的工程思维：不要用二值结果强行掩盖信息不足。

### 4. 终态应该保持不可逆

一旦判定为 `FAILED` 或收到 `CANCELLED`，后续晚到的合格消息不能再把结果改成 `STABLE`。这叫“终态保持”或“终态粘性”。

它可以防止异步系统中消息到达顺序变化造成错误翻转。

## 五、时间和传感器证据方面学到了什么

### 1. 使用时间戳，不用固定帧数代替时间

错误思路：

```text
30 FPS × 90 帧 = 3 秒
```

如果相机掉帧或虚拟机卡顿，90 帧不一定等于 3 秒。正确做法是使用同一种单调时钟：

```text
当前时间戳 - 开始时间戳 >= 3.0 秒
```

单调时钟只向前走，不受系统时间校准影响，适合计算持续时间。

### 2. 必须防止旧证据被新动作误用

如果上一轮 `retreat_complete=true` 没有清除，新一轮放置可能错误地认为撤退已经完成。因此：

- 新抓取和新释放会清除旧撤退证据；
- 上层只接受动作开始后更新的状态；
- 时间戳必须保持单调。

这类问题常被称为“陈旧数据”或“过期证据”。

### 3. 证据缺失不应计入稳定时间

允许短暂遮挡时，我们采用：

```text
短暂不可见
→ 可以保留此前进度
→ 但不可见时间本身不算稳定
```

这比简单忽略丢帧更可靠。如果遮挡时间也算进 3 秒，就可能只实际观察了 2.7 秒，却错误宣布稳定。

### 4. 安全错误通常高于任务结果

在一次 `INCONCLUSIVE` 测试中，机器人状态消息短暂过期，系统优先返回了 `COMMUNICATION_ERROR`。这符合安全优先级：

```text
通信失效
→ 无法确认机器人是否仍安全
→ 立即停止
→ 不继续等待普通视觉结果
```

## 六、视觉模块方面学到了什么

### 1. 视觉算法不只是“识别颜色”

方块检测流程还涉及：

- HSV 颜色阈值；
- 轮廓面积；
- 矩形度、实心度和宽高比；
- ROI 区域限制；
- 连续帧确认；
- 位置平滑；
- 距离估计；
- 错检与漏检统计。

视觉结果必须能被量化验收，而不是只凭“看起来能识别”。

### 2. 参数调优和验收数据必须分开

如果一边看同一段视频一边调参数，最后再用它证明准确率，会产生过拟合。合理流程是：

```text
训练/调参数据
→ 调整 HSV 和形状参数

独立验收数据
→ 只用于最终评价
```

### 3. 相机安装属于算法问题的一部分

算法不能独立解决所有遮挡。摄像头高度、俯仰角、视场角、机械臂收回路径和放置区位置共同决定视觉是否可用。

因此视觉开发也需要向机械组提出明确要求，而不是等硬件装完后再被动适配。

### 4. 远程开发需要可复现的录像验收工具

无法到现场时，最有价值的数据不是一句“识别效果不好”，而是：

- 原始视频；
- 相机参数；
- 算法配置；
- 每帧 JSONL 输出；
- 带标注输出视频；
- 时间段验收清单；
- 自动生成的 HTML/Markdown 报告。

这也是后续需要恢复视觉批量验收生成器的原因。

## 七、Python 和代码使用方面学到了什么

### 1. `dataclass` 适合表示结构化状态

项目使用数据类表示：

- 对准命令；
- 模拟机构状态；
- 稳定观察器状态；
- 配置与结果。

相比随意使用字典，数据类字段明确、便于类型检查，也更容易写测试。

### 2. `Enum` 适合表示有限状态集合

使用字符串枚举可以防止代码中到处出现拼写不同的状态字符串。例如：

```python
StabilityDecision.STABLE
```

比直接写 `"stable"`、`"STABLE"` 或 `"success"` 更安全。

### 3. 参数验证应尽早进行

例如：

- 稳定时间必须大于 0；
- 总观察时间不能短于稳定时间；
- 允许中断时间不能为负数；
- 时间戳不能倒退。

程序启动时尽早报错，比运行到比赛中途再出现不可解释行为更好。

### 4. 异步调用要考虑“晚到结果”

ROS2 服务通常是异步的。软件取消流程后，底层服务可能仍然完成。因此取消结果必须准确描述能力边界：

```text
软件流程已经停止
但正在执行的硬件动作可能仍然完成
```

真正让电机立即停止，需要底层控制器提供可确认的取消或急停协议。

### 5. 日志是远程调试接口

远程开发无法直接看到机器人，因此日志需要表达阶段变化：

```text
place verification passed
retreat service completed
retreat evidence confirmed
starting placement stability observation
placement remained stable
```

好的日志可以回答“系统现在在哪一步、为什么等待、为什么结束”。

## 八、测试方面学到了什么

### 1. 单元测试与集成测试解决不同问题

单元测试验证独立逻辑，例如：

- 3 秒后是否进入 `STABLE`；
- 短遮挡是否暂停计时；
- 长遮挡是否重置进度；
- 明确失败是否立即返回；
- 非法时间参数是否报错。

ROS2 smoke 集成测试验证：

- 节点能否启动；
- 消息和服务是否连通；
- 状态能否跨模块传播；
- 所有进程能否干净退出。

119 项 Windows 测试通过，并不自动证明 Ubuntu ROS2 一定能运行；Ubuntu 构建通过，也不自动证明算法边界正确。两者都需要。

### 2. 测试必须覆盖异常路径

本次不仅测试了 `STABLE`，还测试：

- `FAILED`；
- `INCONCLUSIVE`；
- `CANCELLED`；
- 通信状态过期；
- 服务不可用；
- 旧证据；
- 非法配置。

项目可靠性通常由异常路径决定，而不是由正常演示决定。

### 3. 集成测试会发现启动竞态

第一次 smoke 测试中，测试节点收到第一条状态后立即发出抓取命令，而 `manipulator_client` 还没收到自己的状态副本，于是安全检查拒绝动作。

正确修复不是关闭安全检查，而是在测试驱动中增加很短的状态同步窗口。这说明：

- 多节点收到同一消息的时间可能不同；
- “消息已经发布”不等于“所有订阅者都处理完了”；
- 并发系统必须考虑事件顺序和启动竞态。

### 4. 测试成功的含义要写清楚

在 `FAILED` 测试中，smoke 最后打印 `PASS`，意思是“系统正确地产生了预期的 FAILED”，不是“放置成功”。

测试结果和业务结果属于两个不同层次，命名和日志必须避免混淆。

## 九、ROS2 使用方面学到了什么

### 1. Topic、Service 和状态机的基本分工

- Topic：持续发布状态或检测结果，例如 `/robot/status`；
- Service：请求一次具体动作并等待响应，例如 `/gripper/grab`；
- 状态机：决定在什么条件下调用哪个服务以及下一步做什么。

不要用 Service 持续广播状态，也不要只靠 Topic 猜测动作请求是否被执行。

### 2. 修改消息接口后必须重新构建

加入 `retreat_complete` 后，Ubuntu 执行了：

```bash
colcon build --symlink-install
source install/setup.bash
ros2 interface show robogame_interfaces/msg/RobotStatus
```

`source install/setup.bash` 很重要，因为新终端默认不知道刚构建的包和接口。

### 3. Launch 用于复现完整运行环境

`manipulator_mock_smoke.launch.py` 一次启动：

- `robot_bridge`；
- `mock_perception`；
- `manipulator_client`；
- smoke 测试驱动。

它还允许从命令行调整证据策略、稳定时间、观察超时和取消参数。这样队友可以用同一条命令重复实验。

### 4. 模拟模式不是“假装完成”

合理的模拟模式用于验证：

- 软件接口；
- 流程状态；
- 超时与错误处理；
- 节点间通信；
- 自动化验收。

它不能证明真实物理效果，但可以在硬件到位前排除大量软件问题。

## 十、Git 和团队协作方面学到了什么

### 1. Git commit 是可恢复的项目检查点

本次先创建本地 commit，再推送功能分支。这样即使后续开发失败，也可以返回已验证状态。

重要检查点包括：

```text
c8140dc  模拟抓取/放置链路
917b328  撤退后稳定观察闭环
006708f  今日开发总结文档
```

### 2. 不要无意识使用 `git add .`

工作区存在：

- 录像帧；
- JSONL；
- HTML/Markdown 报告；
- Word 文档和临时文件；
- 课程实验输出。

本次使用明确文件白名单暂存，只提交源代码、测试和正式文档。这样可以避免仓库膨胀和隐私泄露。

### 3. 分支用于隔离未合并功能

开发分支为：

```text
codex/manipulator-mock-closed-loop
```

它已经推送 GitHub，但没有合并 `main`。队友可以查看和评审，而主分支继续保持稳定。

### 4. 推送分支不等于合并功能

需要区分：

```text
commit  保存本地历史
push    把分支备份到远端
PR      请求团队评审和合并
merge   将功能正式加入目标分支
```

### 5. 跨 Windows 和 Ubuntu 同步要防止覆盖

当两边都有修改时，正确流程是：

```text
检查 Git 状态
→ 备份 Ubuntu 文件
→ 只同步目标模块
→ SHA256 校验
→ 重新构建
→ 运行测试
```

不能看到文件名相同就直接认为内容相同。

## 十一、调试和问题定位方面学到了什么

### 1. 先判断错误属于哪一层

遇到失败时，可以按以下层次排查：

```text
输入数据是否存在？
→ 单个算法是否正确？
→ ROS2 接口是否一致？
→ 节点是否启动？
→ 消息是否发布？
→ 订阅者是否收到？
→ 状态机是否处于正确阶段？
→ 超时或安全规则是否抢先触发？
```

### 2. 不要看到失败就立刻放宽安全参数

一次虚拟机通信抖动触发了 `COMMUNICATION_ERROR`。我们先重复实验，第二次正常通过，因此没有马上把安全超时调大。

一般原则：

- 先复现；
- 收集时间戳和日志；
- 区分偶发环境抖动与稳定代码缺陷；
- 有数据后再修改阈值。

### 3. 修复原因，而不是绕过症状

启动竞态的症状是“通信状态缺失”。错误修复是允许没有状态也抓取；正确修复是让测试驱动等各节点完成状态同步。

安全检查没有错，不应该为了让测试变绿而删除。

## 十四、适合低年级本科生的学习路线

不要同时系统学习所有内容。建议按照项目需求分四阶段进行。

### 阶段 1：能读懂和运行（1～2 周）

目标：不追求独立设计，先能解释现有代码。

任务：

1. 阅读 `robogame_core/manipulator.py`；
2. 画出状态转换图；
3. 给每个枚举写一句中文解释；
4. 独立运行全部单元测试；
5. 修改一个时间参数并预测测试结果。

### 阶段 2：能写小功能和测试（2～4 周）

目标：独立实现一个纯 Python 小模块。

任务：

1. 为观察器增加统计字段，例如累计有效观察时间；
2. 先写测试，再写实现；
3. 模拟时间戳倒退、重复消息和长时间遮挡；
4. 使用 Git 创建自己的功能分支和 commit。

### 阶段 3：理解 ROS2 集成（3～6 周）

目标：能够定位节点之间的通信问题。

任务：

1. 使用 `ros2 node list`；
2. 使用 `ros2 topic list/echo/hz`；
3. 使用 `ros2 service list/call`；
4. 修改 launch 参数运行四种终态；
5. 记录一次 rosbag 并离线检查消息。

### 阶段 4：参与现场闭环（硬件到位后）

目标：用数据而不是感觉调整参数。

任务：

1. 测量相机视场和机械臂遮挡；
2. 采集不同光照和距离的视频；
3. 标注放置成功、失败和不可判断片段；
4. 计算检测率、误检率和响应时间；
5. 根据数据调整 ROI、阈值和遮挡容忍时间；
6. 保存配置、录像、报告和对应 Git commit。

## 十五、建议进行的练习

### 练习 1：手动画状态机

不用看代码，画出：

```text
PLACE_ORANGE
→ LIFT
→ RELEASE
→ VERIFYING
→ RETREATING
→ OBSERVING_STABILITY
→ 四种终态
```

再回到代码检查是否遗漏状态。

### 练习 2：预测参数效果

回答：

```text
stable_duration = 3.0
max_unavailable_gap = 0.2

合格 1.0 秒
→ 遮挡 0.1 秒
→ 再合格 2.0 秒
```

最终是否应该 `STABLE`？为什么？

正确理解是：遮挡不计时，因此总有效合格时间为 3.0 秒，可以稳定；总墙上时间为 3.1 秒。

### 练习 3：观察 ROS2 topic

在一个终端启动模拟 launch，在另一个终端执行：

```bash
ros2 topic echo /robot/status
ros2 topic hz /robot/status
```

观察抓取、释放和撤退时字段如何变化。

### 练习 4：阅读一次 Git commit

执行：

```bash
git show --stat 917b328
git show 917b328 -- ros2_ws/src/robogame_core/robogame_core/manipulator.py
```

尝试用自己的话解释每一组修改解决了什么问题。

### 练习 5：设计真实视觉证据接口

暂时不写代码，先列出判断一个方块稳定可能需要的字段：

- 是否检测到目标方块；
- 方块中心是否位于 ROI；
- 位置变化量；
- 置信度；
- 是否被遮挡；
- 时间戳；
- 相机数据是否新鲜。

然后思考哪些情况属于 `FAILED`，哪些属于 `UNAVAILABLE`。

## 十七、最终认识

对于低年级本科生，当前阶段不需要追求“所有代码都能独立从零写出”。更现实的成长顺序是：

```text
能运行
→ 能读懂
→ 能解释
→ 能修改小部分
→ 能写测试
→ 能定位问题
→ 能独立设计模块
→ 能与机械、电控和视觉队友协作完成现场闭环
```

这段开发中已经开始训练最关键的能力：面对一个信息不完整的真实项目，能够把问题拆小、保留证据、验证假设、记录边界，并让代码逐步走向可运行、可测试和可协作。
