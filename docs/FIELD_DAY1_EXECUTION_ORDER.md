## 阶段一：机械盘点（约 30 分钟）

### 简要清单

- [ ] 测量并记录 11 项关键尺寸
- [ ] 确认相机安装位置和视野
- [ ] 拍摄抓取区、放置区、撤退后的相机画面
- [ ] 确认机械臂运动范围

### 详细讲解

#### 1.1 为什么机械盘点必须最先做

软件里的参数 —— 比如 `target_distance_m: 0.24`、`place_heights_m: [0.10, 0.20, 0.30]` —— 全部是基于**假设**的。如果实际车轮直径比我们假设的大 20%，所有距离计算都偏移 20%。如果夹爪开口比方块窄，永远夹不住。

到现场第一件事不是通电，是**用尺子量**。因为尺子不会错，而参数文件可能全是错误的假设。

#### 1.2 需要测量的尺寸（逐项讲解）

| # | 测量项 | 为什么需要 | 怎么测 | 填入位置 |
|---|---|---|---|---|
| 1 | 轮子直径（mm） | 编码器脉冲→距离的换算系数需要这个值。差 5mm，走 1 米误差约 3cm，走 5 米误差 15cm | 用卷尺量轮胎外径（不是轮毂） | FREEZE_TABLE O-02 |
| 2 | 前后轮中心距（mm） | 旋转解算需要知道前后轮距离。差 10mm，转 90° 误差约 2° | 量前轮轴心到后轮轴心的水平距离 | FREEZE_TABLE O-03 |
| 3 | 左右轮中心距（mm） | 同上，差 10mm 转 90° 误差也约 2° | 量左轮轴心到右轮轴心的水平距离 | FREEZE_TABLE O-03 |
| 4 | 夹爪完全张开间距（mm） | 判断方块（边长~10cm）能不能进入夹爪开口。张开口 < 方块宽度 = 永远抓不到 | 让夹爪张开到最大，量两个爪尖内侧距离 | FREEZE_TABLE G-01 |
| 5 | 夹爪完全闭合间距（mm） | 判断能不能夹紧方块。闭合间距 > 方块宽度 = 夹不紧 | 让夹爪闭合到最小，量两个爪尖内侧距离 | FREEZE_TABLE G-02 |
| 6 | 夹爪基准点离地高度（mm） | 软件说的"高度"需要知道零点在哪。没有零点，0.1m 没有意义 | 夹爪降到最低，量爪中心到地面的垂直距离 | FREEZE_TABLE L-01 参考 |
| 7 | 升降有效行程（mm） | 知道最高能升多少，避免发"升到 1 米"这种不可能的指令 | 从最低升到最高，量行程 | FREEZE_TABLE L-03 |
| 8 | 第一层放置高度（mm） | 和机械组确认——软件里的 0.10m 只是估计 | 机械组给出或用实物塔实测 | FREEZE_TABLE L-06 |
| 9 | 第二层放置高度（mm） | 同上 | 同上 | FREEZE_TABLE L-06 |
| 10 | 第三层放置高度（mm） | 同上 | 同上 | FREEZE_TABLE L-06 |
| 11 | 相机到夹爪基准点的水平偏移 | 视觉检测到方块后，需要知道相机和夹爪的相对位置才能对准 | 量相机镜头中心到夹爪中心的水平距离（x 和 y 方向） | 相机安装文档 |

**记录方式**：每个人量一遍，拍照留底。数字不一致时取三次测量的平均值。

#### 1.3 相机安装确认

**不需要调任何视觉参数**。第一天只确认：

1. **拍一张抓取区照片**：相机在正常位置，拍到地面上的方块。这张照片用于回到住处后离线分析 HSV/ROI。
2. **拍一张放置区照片**：机械臂撤退后，相机能否完整看到放置区？如果不能，需要和机械组商量调整。
3. **拍一张机械臂遮挡情况**：机械臂在不同位置（收拢/抓取/抬升/撤退）时，分别拍一张，检查是否挡住了相机的视野。
4. **记录相机参数**：型号、分辨率（如 1280×720）、帧率（如 30fps）、视场角（如果相机说明书上有）。没有就写"未知，后续查"。

**为什么第一天不调视觉参数？** HSV 阈值、ROI 区域、面积过滤这些在现场调就像盲人摸象——你只能看到当前光照下的效果，换一个时间、换一个角度就可能失效。正确做法是录视频带回来，在住处用工具链慢慢调，有 JSONL 和 HTML 报告做证据，而不是凭"看起来还行"。

#### 1.4 机械臂运动范围确认

和机械组一起确认：

- 抓取时机械臂的最低和最远位置
- 撤退后机械臂的收缩位置（不能挡住相机看放置区）
- 三层放置时机械臂的高度范围

拍照记录每个关键位置。

#### 1.5 阶段一验收门槛

必须答出三个问题才能进入阶段二：
1. 关键尺寸都有数字了吗？（至少轮径、轮距、三层高度）
2. 相机能看见抓取区和放置区吗？
3. 机械臂撤退后是否仍有遮挡？

## 阶段二：通电与通信确认（约 20 分钟）

### 简要清单

- [ ] 确认串口设备名
- [ ] 启动 robot_bridge（真实模式）
- [ ] 检查 `/robot/status` 发布频率和字段
- [ ] 检查心跳和看门狗行为
- [ ] 确认 `communication_ok`

### 详细讲解

#### 2.1 为什么单独验证通信，不和动作测试一起做

通电之后 STM32 在做很多事：初始化外设、IMU 零偏校准（~2s）、加载参数。如果一通电就开始发速度命令，可能：
- 命令被 STM32 忽略（还在初始化）
- 命令被缓存在串口缓冲区，初始化完成后突然执行
- 握手还没完成，bridge 拒绝所有命令

更安全的方式：**只观察，不控制**。先确认 STM32 在正常发送状态数据，再尝试控制。

#### 2.2 确认串口设备

```bash
# 插上 USB 后查看新增的串口设备
ls /dev/ttyACM* /dev/ttyUSB* 2>/dev/null

# 如果没有 ttyACM0，用 dmesg 查看最近插入的设备
dmesg | tail -20 | grep -i "usb\|tty\|acm\|cdc"
```

预期：出现 `/dev/ttyACM0`（或 `/dev/ttyUSB0`）。**记下实际设备名**。

如果设计了 udev 别名（`/dev/robot_mcu`），确认别名存在：
```bash
ls -l /dev/robot_mcu 2>/dev/null
```

#### 2.3 启动 robot_bridge（真实模式）

```bash
source ~/robogame/ros2_ws/install/setup.bash

# 注意：用 hardware.yaml 覆盖 robot.yaml 中的 mock_mode
ros2 run robot_bridge robot_bridge --ros-args \
  --params-file ~/robogame/ros2_ws/src/robogame_bringup/config/robot.yaml \
  --params-file ~/robogame/ros2_ws/src/robogame_bringup/config/hardware.yaml
```

**预期**：
- 日志显示 `opened MCU serial port /dev/ttyACM0 at 115200`
- 日志显示 `handshake timeout, retry 1/3`（如果 STM32 还没就绪）
- 然后（如果 STM32 就绪）显示 `handshake complete（received type=0x12）`

**如果卡在握手重试**：
- 检查 USB 线是否插稳
- 检查 STM32 是否已上电（看板子上的灯）
- 如果多次重试后进入 UNAVAILABLE，检查 `hardware.yaml` 中的串口设备名是否正确

**为什么先启动 robot_bridge 而不是全套系统？**
robot_bridge 是通信的最低层。如果它连不上，其他 8 个节点都白启动。**逐级验证的意思就是在启动下游之前先确认上游正常。**

#### 2.4 检查状态话题

```bash
# 另一个终端
source ~/robogame/ros2_ws/install/setup.bash

# 看一次完整状态
ros2 topic echo /robot/status --once

# 看频率（持续 10 秒，Ctrl+C 停止）
ros2 topic hz /robot/status
```

**关键检查项**：

| 字段 | 预期值 | 如果不符 |
|---|---|---|
| `communication_ok` | `true`（握手完成后） | 串口有数据但 STATUS 帧无法解码 → 回住处分析 |
| `emergency_stop` | `false` | **立即停止！检查急停按钮是否被按下** |
| `calibrating` | 启动后一段时间 `true`，之后 `false` | 如果一直 `true`，IMU 可能故障 |
| `imu_valid` | `calibrating` 变 `false` 后应为 `true` | 如果一直 `false`，检查 IMU 连接 |
| `boot_id` | 一个数字（如 0, 1, 2...） | 应该是非零固定值；如果持续递增说明 STM32 反复重启 |
| `battery_voltage` | 约 24V | 如果太低（<20V），电池快没电了 |

**为什么先看字段再发命令？**
这些字段是 STM32 对自身状态的"自述"。如果 `emergency_stop=true`，说明硬件急停已触发 —— 你发任何速度命令都不会执行。先读状态可以避免"发了命令没反应，不知道哪里坏了"。

#### 2.5 确认话题频率

```bash
# /robot/status 预期：心跳 10Hz
ros2 topic hz /robot/status

# /wheel_odom 预期：100Hz（如果 STM32 已经发里程计）
ros2 topic hz /wheel_odom 2>/dev/null || echo "里程计话题暂无数据（可能 STM32 端还没发）"

# /imu/data 预期：200Hz（如果 STM32 已经发 IMU）
ros2 topic hz /imu/data 2>/dev/null || echo "IMU 话题暂无数据（可能 STM32 端还没发）"
```

**为什么要看频率？** 频率太低说明通信链路有瓶颈（串口波特率不够、USB 带宽被占用、STM32 负载过高）。频率不稳定说明系统有间歇性问题（可能是虚拟机调度抖动）。这些在模拟测试中永远不会出现。

#### 2.6 阶段二验收门槛

必须答出三个问题才能进入阶段三：
1. `/robot/status` 稳定发布吗？（hz 在预期范围内）
2. `communication_ok=true` 吗？
3. `emergency_stop=false` 吗？

**如果任何一个答案为否，不进入阶段三。**

## 阶段三：空载安全动作测试（约 30 分钟）

### 简要清单

- [ ] STOP 命令确认
- [ ] 低速前进/后退方向确认
- [ ] 低速左移/右移方向确认
- [ ] 低速旋转方向确认
- [ ] 通信中断自动停车确认（拔 USB）

### 详细讲解

#### 3.1 为什么空载 + 低速

**空载**：夹爪上没有方块，升降上没有负载。即使方向反了、速度不对，最多车跑歪，不会摔方块。

**低速**：用极低速度（`vx=0.05 m/s`，正常速度的 1/10）。即使失控，人也来得及按住急停。

**为什么需要一个一个方向测，而不是发一个综合运动？**
如果你同时发 `vx=0.05, vy=0.03, wz=0.1`，车动起来了，但你不知道哪个轴的方向是对的。先单独测 `vx`（前后），确认正负号正确；再单独测 `wz`（旋转），确认旋转方向正确。**每次只改变一个变量。**

#### 3.2 STOP 测试

```bash
# 已经启动了 robot_bridge（阶段二），现在直接发布 STOP
ros2 service call /chassis/stop robogame_interfaces/srv/ExecuteMechanism \
  "{command: STOP, timeout_s: 1.0}"

# 确认底盘没有在动，并且 /robot/status 仍然正常
ros2 topic echo /robot/status --once
```

**为什么 STOP 是最先测的？** 如果 STOP 不工作，后面任何测试出错时你都无法安全停下来。

#### 3.3 方向确认测试（逐方向）

**准备工作**：把车放在空旷地面上，旁边有人拿着急停按钮。设置一个明显的前方标记（比如地上贴胶带）。

每个测试执行后观察车实际运动方向是否和预期一致，**不符合立即按急停**。

```bash
# === 测试1：前进 ===
# 预期：车向车头方向移动
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"

# 发完后立即 STOP
ros2 service call /chassis/stop robogame_interfaces/srv/ExecuteMechanism \
  "{command: STOP, timeout_s: 1.0}"
```

```bash
# === 测试2：后退 ===
# 预期：车向车尾方向移动
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: -0.05, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
ros2 service call /chassis/stop robogame_interfaces/srv/ExecuteMechanism \
  "{command: STOP, timeout_s: 1.0}"
```

```bash
# === 测试3：左移 ===
# 预期：车向左平移（车头方向不变）
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0, y: 0.05, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
ros2 service call /chassis/stop robogame_interfaces/srv/ExecuteMechanism \
  "{command: STOP, timeout_s: 1.0}"
```

```bash
# === 测试4：右移 ===
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0, y: -0.05, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
ros2 service call /chassis/stop robogame_interfaces/srv/ExecuteMechanism \
  "{command: STOP, timeout_s: 1.0}"
```

```bash
# === 测试5：逆时针旋转（俯视） ===
# 预期：车逆时针旋转（从上往下看）
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.1}}"
ros2 service call /chassis/stop robogame_interfaces/srv/ExecuteMechanism \
  "{command: STOP, timeout_s: 1.0}"
```

```bash
# === 测试6：顺时针旋转 ===
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: -0.1}}"
ros2 service call /chassis/stop robogame_interfaces/srv/ExecuteMechanism \
  "{command: STOP, timeout_s: 1.0}"
```

**每次测试后记录**：

| 测试 | 命令 | 预期方向 | 实际方向 | 是否一致 |
|---|---|---|---|---|
| 前进 | vx=+0.05 | 车头前方 | | |
| 后退 | vx=-0.05 | 车尾后方 | | |
| 左移 | vy=+0.05 | 车体左侧 | | |
| 右移 | vy=-0.05 | 车体右侧 | | |
| 逆时针 | wz=+0.1 | 逆时针 | | |
| 顺时针 | wz=-0.1 | 顺时针 | | |

**如果方向反了怎么办？** 不修改代码。先确认是电控的坐标系定义和 ROS 不一样（协议问题），还是我们代码里的符号反了（软件问题）。如果是协议问题，和电控组当场确认后修改协议定义。不猜测。

#### 3.4 通信中断自动停车测试

**这是今天最重要的安全测试。** 电控承诺了"300ms 没收到命令就自己停"，现在验证它。

```bash
# 先让车慢速前进
ros2 topic pub --rate 50 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"

# 然后直接拔掉 USB 线（模拟通信断开）
# 观察：车应该在 300ms 内停止
```

**如果车继续走**，这是严重的安全问题，必须立即向电控和机械组报告。在修复之前，所有自动运动测试都必须有人手持急停按钮跟在车旁边。

**为什么拔 USB 而不是 Ctrl+C？** Ctrl+C 只是停止上位机发数据，ROS2 进程可能还会发送几帧。物理拔线是最接近真实故障的模拟（线被踢掉、USB 松动）。

#### 3.5 阶段三验收门槛

必须答出三个问题才能进入阶段四：
1. STOP 能让车停下来吗？
2. 六个运动方向都正确吗？
3. 拔 USB 后车自己停了吗？

## 阶段四：相机采图（约 30 分钟）

### 简要清单

- [ ] 采集抓取区静态场景照片
- [ ] 采集放置区静态场景照片
- [ ] 采集空场景（无方块）照片
- [ ] 拍摄一段车不动、画面中有方块的短视频
- [ ] 记录相机参数和安装位置

### 详细讲解

#### 4.1 为什么只采图不调参

相机参数调优（HSV 阈值、ROI、面积过滤）是一个**反复试错**的过程。在现场花 30 分钟调参数，不如花 10 分钟录视频、回去花 2 小时从容调整，用 JSONL 和 HTML 报告客观评估每一组参数的效果。

**第一天只需要确保相机能正常工作，把该拍的都拍回来。**

#### 4.2 采集清单

**静态照片**（用 ROS2 或直接 `fswebcam`/`cheese` 都可以）：

| 场景 | 内容 | 用途 |
|---|---|---|
| 橙色方块在抓取区 | 方块放在车前方约 0.5m | 分析 HSV 阈值、距离估算 |
| 紫色方块在抓取区 | 同上 | 同上 |
| 橙色方块在放置区 | 方块放在放置塔第一层位置 | 分析放置区 ROI |
| 空场景（抓取区） | 地上没有方块 | 分析误检来源（地面纹理、反光） |
| 空场景（放置区） | 同上 | 同上 |
| 机械臂在抓取位 | 臂展开，不抓东西 | 检查臂是否在画面中造成误检 |
| 机械臂在撤退位 | 臂收拢 | 检查撤退后能否完整看到放置区 |

**短视频**（10-15 秒）：

| 内容 | 用途 |
|---|---|
| 方块静止在抓取区 | 测试检测稳定性 |
| 方块从抓取区移开 | 测试目标丢失后的响应 |

**采集命令参考**：

```bash
# 如果 cube_perception 有 standalone 模式
```

### 详细讲解

#### 5.1 数据目录结构

```text
field_data/
  2026-08-09_hardware_inventory/
    README.md              ← 尺寸测量记录
    photos/                ← 机械结构照片
    measurements.txt       ← 每项尺寸的值

  2026-08-09_communication/
    README.md              ← 串口设备名、话题频率记录
    terminal_logs/         ← 终端输出截图或复制

  2026-08-09_safety_motion/
    README.md              ← 方向测试结果、拔 USB 结果
    terminal_logs/

  2026-08-09_camera/
    README.md              ← 相机参数表
    photos/                ← 静态照片
    videos/                ← 短视频
```

**为什么目录要这样组织？**
两个月后你可能完全不记得今天做了什么。一个写得清楚的 README 比任何"我印象中"都可靠。每个子目录的 README 至少写三句话：
1. 今天在这个领域做了什么
2. 最重要的发现是什么
3. 还有什么没确认的

#### 5.2 记录未解决问题

现场一定会发现意料之外的问题：某个螺丝松了、某个传感器没读数、某个地方和图纸不一样。**不要尝试当场修好所有问题**。记下来，拍照片，带回去分析。

格式：

```markdown
## 未解决问题

1. **问题**：左前轮编码器回传频率不稳定（有时 80Hz，有时 120Hz）
   **观察时间**：10:30
   **已尝试**：重新插拔串口 → 未改善
   **下一步**：回去分析原始数据，可能是硬件问题需电控组检查

2. **问题**：相机 USB 线太短，只能看到抓取区，看不到放置区
   **观察时间**：11:00
   **影响**：第一阶段只能做抓取闭环，不能做放置闭环
   **下一步**：找机械组确认能否调整安装位置或换更长线
```

#### 5.3 阶段五验收门槛

- 数据目录已创建且结构完整
- 每个子目录有 README
- 未解决问题列表写在 README 末尾
- 回到住处后能正常读取所有文件
