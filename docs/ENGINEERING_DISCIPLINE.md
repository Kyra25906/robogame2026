# 工程开发纪律（RoboGame 2026）

> 目的：这个项目不只是「完成学校比赛」，而是达到「可以写进简历、经得起面试追问、半年后回看仍然干净」的工程标准。本纪律是日常开发的底线，每一条都对应一项可写入简历的证据。

## 总纲

**用证据说话，而不是用形容词说话。**

简历上能写「258 项测试 0 失败」，是因为仓库里有一条条可复现的测试；能写「真车闭环 10 次成功 9 次」，是因为有一张张当场记录的验收表。**任何一条简历条目，都必须能在仓库里找到对应的证据文件。** 找不到证据的内容，宁可不上简历。

## 六条纪律

### 1. 证据分级：写「能证明什么」，不写「我完成了什么」

- **做法**：每次收工，结论拆成三栏——已验证 / 未验证 / 不能证明。
- **为什么**：模拟通过、构建通过、固定样本通过，都只能证明有限的东西。把「没观察到失败」写成「永不失败」，是简历上最容易被打假的坑。
- **简历证据**：面试能答「你的代码证明了什么、没证明什么」——这是初级工程师最稀缺的品质。

### 2. 可复现优先于「在我机器上能跑」

- **做法**：任何功能交付都附带：入口命令、输入、预期输出、验证方式。`GETTING_STARTED` 必须能让一个从没接触过项目的陌生人在干净环境跑通。
- **为什么**：面试官会点开 GitHub。他跑不起来，你的简历就只剩一堆文字。
- **简历证据**：README 顶部一段 30 秒、陌生人可复现的演示。

### 3. 改核心逻辑，先写测试；改完跑回归

- **做法**：核心逻辑（导航、状态机、协议编解码）改动前先补测试，改完依次跑：针对性测试 → 所属模块测试 → 相关回归测试。
- **为什么**：没有测试兜底的重构，等于拿整辆车赌运气。
- **简历证据**：`tests/` 目录 + 一个稳定增长、且你讲得清每项测了什么的测试数量。

### 4. 一次提交只做一件事，提交信息说清「为什么」

- **做法**：一个 commit 一个意图，禁止「改了一堆 + 顺手修了别的」。提交信息写清：改了什么、为什么、验证了什么。
- **为什么**：Git 历史本身就是作品集，面试官 `git log` 一眼能看出你的工程习惯。
- **简历证据**：干净、可读、能讲出「每个 commit 在解决什么」的分支与提交历史。

### 5. 证据当场采集，事后无法补

- **做法**：真车联调时，按验收清单边跑边抓——视频、成功率表、失败现象、定位误差、日志，当场回填到 `results/` 或对应的 field 文档。
- **为什么**：真车的视频和数据无法事后补拍。等车拆了、场地没了，「10 次成功 9 次」就只是一个没人信的说法。
- **简历证据**：README 顶图视频 + 一张可量化的验收表（成功率、耗时、误差）。

### 6. 不为了「看起来厉害」加复杂度

- **做法**：每引入一个抽象、一个依赖、一个框架，都必须能回答「它解决哪个真实问题」。答不上来就不加。P 控制够用就不上 nav2，手写校验器够用就不引 pydantic。
- **为什么**：过度设计会拖慢进度、制造 bug，还会在面试被追问「你为什么用这么重的方案」时露馅。
- **简历证据**：能说清「为什么选这个方案、为什么没选更重的方案」——这比「我用了最流行的技术」值钱。

## 完成标准（Definition of Done）

一个功能算「完成」，必须同时满足：

1. 有入口命令，陌生人可复现；
2. 有对应测试，且通过；
3. 结论按「已验证 / 未验证」分级写清；
4. 提交信息说清「为什么」；
5. 若涉及真车或硬件，证据当场采集并存档。

缺任何一条，就只能叫「写了一半」，不能叫「完成」，更不能写进简历。

## 与 AGENT.md 的关系

- `AGENT.md` 管「怎么和 Agent 协作、每轮怎么收工」；
- 本纪律管「工程性底线，能不能写进简历」。
- 两者冲突时，以「证据分级」和「不过度设计」为准。
