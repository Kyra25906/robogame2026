## 阶段性学习地图

截至 2026-08-08，我们已经从“写一个能运行的函数”逐步学习到“组织一个能验证、能协作、能安全接入硬件的项目”。

## 2026-08-08：消息“收到”不等于状态“可信”

### 背景

`robot_bridge` 已经能把串口帧按 0x10、0x11、0x12 分类，但电控尚未给出 STATUS 的逐字节布局。旧占位代码只看到 `0x12` 类型，就刷新状态时间并使用假的 `boot_id=0`。这会把“外层帧合法”误当成“内部状态可信”。

### 学到的知识：失败安全与分层校验

串口接收至少有三层结论：

```text
收到字节 → 帧头、长度和 CRC 合法 → STATUS 全字段解码和值域校验成功
```

前两层只证明通信链路有数据，第三层才允许更新 `last_decoded_status_rx`。如果真实状态无法确认，机器人应保持 `communication_ok=false`，这叫“失败时保持安全状态”（fail closed）。

本次代码让占位分支只负责识别类型，不再刷新状态时间或触发 MCU 重启判断。同时加入回归测试，明确禁止 `_dispatch_frame()` 在解析器尚未实现时修改这两个入口。以后接入真实协议时，需要先实现长度、字段和范围校验，再有意识地更新测试与状态。

### 现场摘要为什么不能只显示 PASS

机构服务返回 PASS，只能说明服务调用声称成功，不代表机器人整体安全。例如急停可能仍处于触发状态，IMU 可能还在校准，或者根本没有收到 RobotStatus。因此单动作工具同时显示五个关键状态，并把缺失字段写成 `UNKNOWN`，而不是默认成正常。

终端单行摘要用于现场快速判断，CSV 用于事后追溯。两者是“快速反馈”和“完整证据”的分工，不能互相替代。

### 为什么新建干净验收仓库

Ubuntu 中同时存在普通文件夹 `robogame` 和带 34 项本地变化的旧 Git 仓库 `robogame2026`。目录大小和修改时间会受构建产物影响，不能代表代码版本。可靠版本应由 Git 提交号确定。

一键验收脚本不覆盖任何旧目录，而是按提交号新建独立仓库。这样“正在验收的代码版本”可以直接从目录名和 `git rev-parse` 复核，旧实验文件也不会意外混入测试结果。

ROS2 的 `setup.bash` 可能读取未定义的可选环境变量，因此不能在加载它之前开启 Bash 的 `set -u`（nounset）。自动化脚本仍保留 `set -e` 和 `pipefail`：普通命令或管道失败会立即停止，但不会把 ROS2 的可选变量误判为错误。

第一次一键实跑还暴露了两种并发时序：服务可能早于话题被发现，父进程收到信号也不等于子节点收到信号。因此工具必须先拿到 RobotStatus 再允许动作；后台 ROS2 命令则放进独立进程组，退出时向整个组发送 SIGINT，并设置等待上限，必要时升级为 SIGTERM。自动化中的等待必须有期限，否则一个正常功能也可能让整条流水线永久卡住。

复验中进程已经正常结束，但 ROS2 Jazzy 会在外部关闭上下文时抛出 `ExternalShutdownException`。它和用户按 Ctrl+C 产生的 `KeyboardInterrupt` 一样，属于预期退出路径，应在节点入口捕获并正常清理；否则功能虽然通过，日志却会留下误导性的失败堆栈。

### 协议字段未知时仍然可以测试什么

电控尚未给出 ODOM、IMU 和 STATUS 的逐字节字段，所以不能猜测 payload 含义；但帧头、版本、类型、序号、长度和 CRC 已经冻结，这一层仍可独立验收。本次用 14 项测试覆盖了串口常见的分片、粘包、噪声、截断、损坏和重新同步。

这种做法体现了“按已知边界测试”：不因为部分信息未知就什么都不做，也不越过边界虚构协议。测试全部通过后协议代码没有修改，因为测试的价值不仅是发现 bug，也包括为已有正确行为建立防回归证据。

### 没有硬件时也要定义系统行为

field 模式打开不存在的串口时，旧实现会在节点构造阶段直接抛出异常。崩溃虽然不会驱动小车，但也无法持续发布“通信不可信”，现场很难区分配置错误、设备未插入和程序 bug。改进后的 bridge 保持运行、令 `communication_ok=false`，并拒绝真实机构服务和未握手速度命令。

这叫失败安全（fail-safe）而不是假装可用：缺少设备时系统仍可观察、可诊断、可安全退出，但绝不报告成功。专用 smoke 使用一个明确不存在的设备路径，因此不依赖现场硬件，也不会误碰真实串口。

### 配置也需要像代码一样测试

YAML 能被解析只说明语法正确，不说明参数组合合理。例如稳定观察 7 秒但观察超时只有 6 秒、field 配置启用 mock 证据、航点落在场地外，这些都属于“每个值单看合法，组合起来不可能正确”。

配置检查器把解析与规则分开：核心模块只处理普通字典，便于 Windows 单元测试；命令行入口负责读取 ROS2 YAML，在 Ubuntu 一键流程中检查真实文件。这样既不会因为 Windows 缺少 PyYAML 而跳过规则测试，也不会用测试夹具冒充真实配置验收。

## 2026-08-07：现场冻结表、故障测试卡片与单动作验收脚本

### 背景

今天完成了三项远程准备工作，目标是在拿到真车前，把"现场需要问什么、测什么、怎样验收"全部整理成可执行的文档和脚本。

### 学到的知识一：冻结表——把跨团队的隐性知识变成显性字段

算法、电控、机械三方各自理解的概念可能完全不同。比如算法说"抓取成功"，电控理解为"电机转到指定位置"，机械理解为"限位开关触发"。如果不在联调前逐字段对齐，现场试出来的结论也容易记错或丢失。

冻结表的设计原则：
- **每行一个问题，不要一段话问多个事**。比如"夹爪的张开/闭合极限是多少"和"怎样判断抓到了"必须分开，因为答案来源不同（机械给尺寸，电控给传感器）。
- **每列一个答案来源**：答案、确认人、日期分开，方便追溯。
- **先列"为什么需要知道"**。现场队友不是故意不回答——他们可能不知道这个参数会怎样影响软件。解释原因降低沟通成本。

冻结表不是一次性填完就扔。它有两种使用方式：
```text
远程 → 把已知问题全部写进表格框架
现场 → 逐项读出来让机械/电控回答，当场填入
事后 → 任何一方想改参数，先查表找到当时的确认人和日期
```

### 学到的知识二：故障测试卡片——验证"出问题时系统会不会安全停下"

让系统在正常情况跑通只能证明"理想条件下可以工作"。真正决定比赛是否翻车的是异常情况下的行为。故障测试卡片为每种故障准备了两个版本：

```text
模拟版本 → 在 Ubuntu 上不依赖真车复现故障，验证软件逻辑正确
真车版本 → 在物理小车上触发故障，验证整条链路正确
```

关键设计：
- 每张卡片**一行命令就能复现**，不需要理解代码。现场紧张时不可能翻源码找怎么触发。
- 先测模拟再测真车。模拟没通过的，真车一定不会通过；模拟通过了，真车可能因为硬件差异仍然失败。

五种故障的优先级有差异：
```text
急停 > 通信中断 > 机构故障 > 服务失败 > 动作超时
```
这个顺序在 `control_safety_result()` 函数中以 if-elif 实现：急停最先判断，它一触发其他检查全部跳过。

### 学到的知识三：单动作验收脚本——用 ActionSpec 数据驱动替代重复代码

四个机构动作（GRAB、RELEASE、LIFT、STOP）各有不同的服务名、服务类型和默认参数。如果为每个动作写一段代码，四段代码 90% 相同，只有几行不同。

`ActionSpec` 数据类把"不同"的部分抽成数据：
```python
ActionSpec(
    name="GRAB",
    service_name="/gripper/grab",
    ros_type=ExecuteMechanism,
    defaults={"command": "GRAB", "timeout_s": 3.0},
)
```

然后一个 `execute()` 方法通用于所有动作。新增第五个动作只需在 `_ACTIONS` 列表加一行，不用改逻辑。这体现了**开闭原则**的一个实际应用：对扩展开放（加数据），对修改封闭（不改 execute）。

脚本还展示了"异步转同步"的 ROS2 模式：服务调用是异步的，但验收脚本需要顺序执行（先等状态、再调服务、最后记录）。`_spin_until()` 用循环调用 `spin_once` 实现了可控等待，不阻塞其他回调。

### 学到的知识四：CSV 列设计是一种轻量级数据建模

RobotStatus 有 8 个字段，调用前后各一份。脚本用 `_flatten()` 加前缀铺平到 16 列：
```text
status_before_communication_ok, status_before_emergency_stop, ...
status_after_communication_ok,  status_after_emergency_stop,  ...
```

这种"宽表"格式让每行自成一次完整记录，适合：
- `grep FAIL` 找所有失败；
- Excel 筛选 `status_before_mechanism_fault=1` 看故障前状态；
- pandas `df.groupby('action')['duration_s'].mean()` 算平均耗时。

嵌套 JSON 更适合存，扁平 CSV 更适合分析。选择取决于下游是谁在消费数据。



真实回看测试发现，manifest 中保存的是供浏览器播放的 H.264 预览。重新打开工作目录后，如果再次点击“处理新视频”，旧实现会误把预览当成原始输入，生成“预览的预览”和第二套 JSONL。

这让我们学到：界面上的“视频已就绪”其实包含两种不同能力。

```text
历史预览已就绪 → 可以播放、查看标注、生成报告
原始视频已就绪 → 才可以重新运行视觉检测
```

工程设计中，两个对象即使都是 MP4，也不能因为文件类型相同就认为职责相同。代码现在分别保存 `video` 和 `source_video` 状态；恢复历史结果时只恢复预览，用户重新上传原始视频后才允许处理。

本次真实报告也说明“工具工作”和“算法通过验收”是两件事：HTML 成功生成，但结果为 1/6 时间段通过。失败报告仍然是有效证据，它指出了橙色检出率临界、空场景误检以及人工区间重叠等后续问题。

## 2026-08-07：机构模拟闭环与真实硬件接入的边界

### 模拟流程完整，不等于真机接口完整

`manipulator_client` 已经能模拟执行抓取、抬升、释放、撤退、稳定观察和取消，并覆盖大量失败路径。但它调用的是 ROS2 服务；服务下面怎样变成电机动作，仍取决于 `robot_bridge`、MCU协议和机械传感器。

```text
manipulator_client 决定“现在应该抓取”
→ ROS2 ExecuteMechanism 服务
→ robot_bridge 把请求编码为串口命令
→ MCU驱动电机
→ 限位/电流/编码器返回完成证据
→ robot_bridge 解码 RobotStatus
→ manipulator_client 决定下一步
```

目前链路的首尾已经有软件骨架，中间的真实 `0x02` 机构命令和 `0x81` 状态载荷尚未冻结。因此现在直接编写真实串口字段，得到的只是“能够运行的猜测”，现场很可能需要推翻。

### 失败安全比“先跑起来”更重要

真实状态没有解码时，系统不应因为“收到任意一帧合法串口数据”就认为机构状态健康。心跳正常只说明通信链路存在，不代表急停、夹爪、限位和故障字段可信。

通用原则是：关键证据未知时保持拒绝动作，而不是填入看起来正常的默认值。这叫失败安全（fail-safe）。

### 软件取消与硬件停止不是一回事

当前 `CANCEL` 能停止上位机流程、发布底盘零速度并阻止后续步骤。但已经发出的 `GRAB`、`LIFT` 或 `RELEASE` 服务仍可能在服务端完成。只有MCU确认了 `STOP`/取消协议，并返回“执行器已经停止”的新证据，软件才能宣称取消了硬件动作。

### 超时需要按完整时间预算设计

当前整体动作超时为12秒，而一次放置可能包含升降、释放、撤退、等待新状态和3秒稳定观察。模拟服务几乎立即完成，所以没有暴露预算问题；真机每个动作都有实际耗时。

正确方法是先列出最坏时间预算，再配置总超时：

```text
服务等待 + 升降 + 释放 + 撤退 + 状态延迟 + 稳定观察 + 安全余量
```

不能只因为单个服务超时是3秒，就认为总流程12秒一定足够。

### 状态字符串方便原型，但不是长期强类型接口

任务管理器目前通过字符串发布 `PICK_ORANGE`，并通过 `SUCCESS`、`STABLE` 或错误前缀判断结果。这适合早期原型，但字符串拼写、扩展字段和兼容性较弱。现场前两天不适合为此大规模重构；应先保持接口稳定，把真实硬件链路跑通，之后再评估 ROS2 Action 或强类型消息。

## 2026-08-07：串口有数据不代表机器人状态可信

`robot_bridge` 原来用“最近收到任意合法串口帧”判断 `communication_ok`。这会把两个不同层次混在一起：

```text
transport_fresh：串口线上最近有合法帧
status_fresh：最近成功解码了完整 RobotStatus
```

心跳、里程计或IMU帧只能证明传输链路有活动，不能证明急停、机构故障、夹爪和载荷字段已经更新。代码现在分别记录 `last_frame_rx` 和 `last_decoded_status_rx`；只有后者新鲜，真实模式才允许 `communication_ok=true`。

因为 `0x81` 的逐字节适配器尚未冻结，`last_decoded_status_rx` 当前不会被更新。这意味着真实模式会保持不健康并拒绝上层动作。它看起来“不够方便”，但这是正确的失败安全行为。

测试还发现了浮点时间边界：十进制的 `10.0 - 9.7 = 0.3` 在二进制浮点中可能略大于0.3。实现使用极小的数值容差，只把数学上等于截止点的状态视为新鲜；超过1毫秒的状态仍然过期。这个例子说明边界测试不仅检查业务逻辑，也检查计算机表示数字的方式。

## 2026-08-07：配置分离还需要代码拒绝危险组合

项目原来只有一个 `robot.yaml`，其中同时包含 `mock_mode: true` 和 `placement_evidence_policy: mock_qualified`。硬件启动文件只覆盖了 `robot_bridge.mock_mode=false`，却没有覆盖机构客户端的模拟放置证据，因此可能形成“真实机构 + 模拟成功证据”的混合运行。

现在配置分成三层：

```text
robot.yaml       → 公共算法参数
robot_mock.yaml  → 模拟硬件与模拟证据
robot_field.yaml → 真实串口与保守证据
```

但文件分开只能减少误操作，不能阻止误操作。`manipulator_client` 因此新增 `runtime_mode`，并在启动时验证：

```text
runtime_mode=field + mock_qualified → 拒绝启动
runtime_mode=field + mock_failed    → 拒绝启动
runtime_mode=field + unavailable    → 允许启动
```

这体现了安全配置的通用原则：不要只让正确配置容易找到，还要让危险组合无法运行。现场使用 `unavailable` 会得到 `INCONCLUSIVE`，虽然不能宣称闭环成功，但比伪造 `STABLE` 更诚实、更安全。

## 2026-08-07：离线视觉验收形成完整工具链

### 背景

远程开发拿不到实时小车和现场方块，只能依靠队友录制的视频。如果只是“人看视频觉得算法还可以”，不同人、不同时间很难得到一致结论。因此项目建立了可重复的离线验收链：

```text
原始视频
→ 视觉算法逐帧检测
→ detections.jsonl
→ 人工标注明确时间段
→ vision_acceptance.json
→ HTML 验收报告
```

### 学到的知识一：人工答案与算法输出必须分开

`detections.jsonl` 是算法认为每一帧出现了什么；`vision_acceptance.json` 是人观察视频后认为某个时间段应该出现什么。只有把两者分开，才能发现算法判断错误。

如果直接把算法输出复制成人工答案，报告一定看起来很好，但这种测试没有意义。这和考试时先看答案再给自己批卷是同一个问题。

### 学到的知识二：中间文件让流程可复现

把逐帧结果保存为 JSONL，而不是只把方框画到视频上，有三个好处：

1. 不重新运行检测器也能生成报告；
2. 可以检查某一帧的颜色、置信度和时间戳；
3. 修改报告阈值时不需要再次处理视频。

这体现了工程中的“数据与展示分离”：JSONL 是结构化数据，HTML 是方便人阅读的展示。

### 学到的知识三：浏览器和 OpenCV 的解码能力不同

手机视频 `VID20260806162500.mp4` 使用 HEVC/H.265。OpenCV 能读取它，不代表 Edge 浏览器也能播放它。项目因此保留原始 HEVC 作为检测输入，同时生成 H.264/YUV420p 预览供浏览器播放。

```text
同一个原始视频
├─ 原始 HEVC → 检测算法
└─ H.264 预览 → 人工标注
```

转码后必须检查帧数、帧率、尺寸和时长是否保持一致，否则人工标注的时间可能无法对应检测结果。这次真实视频在转换前后均为 574 帧、30.09 FPS、720×1280。

### 学到的知识四：耗时操作需要状态、取消和清理

视频处理不能只设计“开始”和“完成”。用户还需要知道：

- 当前是否仍在运行；
- 已处理多少帧；
- 现在处于检测还是转码；
- 能否安全取消；
- 取消后是否留下半个文件。

因此网页处理被改成后台任务，并定义了 `running`、`completed`、`failed`、`cancelled` 等状态。取消信号会传到逐帧循环或 FFmpeg 进程，半成品 JSONL 和预览会被删除。

这体现了一个通用原则：取消不是简单地隐藏进度条，而是要让真正执行工作的代码停止，并把资源恢复到可理解的状态。

### 学到的知识五：Python 环境必须保持一致

Windows 中可能同时存在多个 Python。模块安装在一个 Python 中，不代表另一个 Python 可以导入。判断环境时应先运行：

```powershell
python -c "import sys; print(sys.executable)"
```

再使用同一个解释器安装和启动：

```powershell
& "D:\python.exe" -m pip install imageio-ffmpeg==0.6.0
& "D:\python.exe" -m cube_perception.segment_annotator
```

代码也采用延迟导入 OpenCV：打开标注网页不需要立即加载 `cv2`，只有真正处理视频时才检查依赖，并给出包含当前解释器路径的错误信息。

### 学到的知识六：自动化测试与人工验收互相补充

自动化测试已经覆盖上传、Range 播放、处理、取消、清理、保存 manifest、生成 HTML 和重新恢复。它可以快速发现代码回归，但不能代替人确认网页是否易用、视频画面是否正确。

因此本项目采用两层证据：

```text
自动化测试 → 证明程序逻辑可重复
人工验收   → 证明真实视频和实际操作可用
```

截至本条记录，自动化测试为 139 项通过，真实 HEVC 视频已经确认可以转换并在网页中播放与操作。

## 2026-08-08：安全字段必须贯穿完整调用链

这次为 `motion_control` 增加边界测试时，发现核心安全函数本来已经支持
`mechanism_fault`，消息 `RobotStatus` 里也有这个字段，但运动节点调用安全函数时没有把它传进去。
这说明“某一层已经实现安全功能”不等于整条系统链路已经安全：

```text
MCU/模拟器状态
→ RobotStatus 消息
→ motion_control 读取字段
→ control_safety_result 作出判断
→ 发布零速度并返回失败原因
```

任何一个箭头漏掉字段，后面的正确代码都无法发挥作用。本次修复后，机构故障会得到
`MECHANISM_ERROR: mechanism fault`，不再被混同为通信异常。

还学习了三类适合远程完成的运动安全测试：

1. **纯逻辑边界测试**：检查限速、加速度、角度跨界、异常时间步和参数值，不需要 ROS2 或真车。
2. **代码结构守卫**：检查每个结束路径是否先调用停车，再清除当前目标，防止以后重构时漏掉零速度命令。
3. **Ubuntu 构建验收**：确认 Windows 上通过的逻辑代码仍能在 ROS2 Jazzy 环境中正确安装和导入。

测试中还遇到 `0.35000000000000003` 与 `0.35`。这是二进制浮点数的正常表示误差，
物理量测试应使用近似比较，而不能要求十进制文本完全相等。

## 2026-08-10：时序稳定不等于任务目标正确

现场手机视频同时出现目标方块、木凳和背景方块。旧时序过滤器会为每种颜色选择最高置信度候选，再持续跟踪旧位置附近的候选；因此背景物体可以被非常稳定地错误确认。

本次把“没有足够信息”变成显式失败边界：同色初始候选超过一个时不猜测，已有轨迹附近出现多个候选时中断连续确认，并在调试状态中记录 `ambiguous=true`。已有轨迹附近只有一个候选时，仍可忽略远处干扰并保持连续跟踪。

真实视频还说明检测和跟踪必须分开分析：橙色多候选问题可以由歧义规则阻止，但中央紫色方块在检测阶段就因画面裁切和长宽比超限被拒绝，时序逻辑看不到它，也就无法选择它。工程上应先保证目标进入候选集合，再用真实 ROI 或任务提示选择目标，不能期待时间滤波修复上游漏检。

## 2026-08-12：传输层与应用层信任分离 + 安全审计方法

### 背景

交接文档指出 `/cmd_vel` 门控存在缺口：握手由合法 0x12 帧信封完成，但 STATUS payload 尚未解码，`communication_ok` 依然为 False，非零速度仍可能被转发到串口。本轮回合修复了这个缺口，并对 robot_bridge 做了完整安全审计。

### 学到的知识一：两层信任边界必须分开

串口通信至少有三层：

```text
收到字节 → 帧头+长度+CRC合法（传输层）→ payload全字段解码+值域校验成功（应用层）
```

旧代码的 `_on_cmd_vel` 只检查了传输层握手状态（`_handshake_state`），没检查应用层状态可信度（`_communication_ok`）。修复后两道门都必须通过：

```python
if self._handshake_state != _HANDSHAKE_READY:  # 传输层：能通信吗
    return
if not self._communication_ok:                   # 应用层：数据可信吗
    return
```

这叫 **defense in depth**（纵深防御）：不是一道万能门，而是多道窄门，每道只管自己那一层。一层被绕过，下一层仍然能拦。

### 学到的知识二：握手不应该等 payload 解码

有人会问：既然握手只查帧类型不够，为什么不让握手也等 payload 解码？答案是 **关注点分离**（separation of concerns）：

- 握手 = 传输层："电话接通了没"
- `communication_ok` = 应用层："对方身份核实了没"

两层分开的好处：
1. **独立调试**：payload 解码器没实现时，握手仍能建立，可以先验证链路质量
2. **独立替换**：换 MCU 固件时只改 payload 解码器，握手不动
3. **不会锁死**：如果握手也等 payload，而 payload 解码器还没写，整个通信链路永远建立不了

这种"宁可部分功能不可用，也不把不同层的判断混在一起"的设计，在工程中叫 **fail-closed**：不确定时拒绝动作，而不是用默认值假装正常。

### 学到的知识三：AST 测试与行为测试互补

本轮写了两种测试：

| 类型 | 检查什么 | 局限 |
|---|---|---|
| AST 测试 | 代码里有没有 `_communication_ok` 变量名 | 把 `if not` 写成 `if` 也能过 |
| 行为测试 | 设不同状态调 `_on_cmd_vel`，检查 velocity 是否更新 | 需要 rclpy，Windows 上跑不了 |

两者互补：AST 保证"写了这道门"，行为测试保证"门的方向对"。行为测试用真值表覆盖了所有状态组合：

| 握手 | communication_ok | 应该放行？ |
|---|---|---|
| READY | True | 放行 |
| READY | False | **拦截**（本次修复的核心） |
| HANDSHAKING | True | 拦截 |
| HANDSHAKING | False | 拦截 |

### 学到的知识四：诊断日志的限流设计

`_on_cmd_vel` 可能被高频调用（20-50Hz），如果每次拦截都打 warning，日志几秒就爆了。用了一个哨兵标记 `_cmd_vel_block_warned`：

```python
if not self._cmd_vel_block_warned:         # 首次？打一次
    self.get_logger().warn(...)
    self._cmd_vel_block_warned = True
# 命令通过时重置标记
self._cmd_vel_block_warned = False
```

这叫 **rate-limited logging**（限流日志），是分布式系统中处理高频事件的常见模式。本质是用一点内存状态（一个 bool）换取大幅减少日志量。

### 学到的知识五：安全审计不只是找 bug

对 robot_bridge 逐行动审计发现了 10 个观察项，但只有 2 个需要修复：

- **HIGH**：串口读写无异常保护——USB 断开可能冻结整个 bridge
- **MEDIUM**：命令超时不发零速度帧——MCU 可能短暂失控

其余 8 项要么是设计意图（握手跳过 communication_ok），要么在当前单线程执行器下安全（线程安全），要么依赖 MCU 自行处理（encode_velocity 不校验 NaN）。

审计的价值不仅在于找到要修的，还在于**确认哪些不需要修**。把"看起来可疑但实际正确"的设计写成文档，防止下一个人重复调查。

## 2026-08-12：特征不变性 — 选对特征比加规则更重要

### 背景

P1 侧转角度实验：GF100 相机下，方块从 0° 转到 45°（两个方向各 15°/30°/45°），42 张照片全部检出。距离仅浮动 3cm（0.60–0.64m），置信度最低 0.740 仍远超 0.45 门槛。

### 学到的知识：特征不变性（Feature Invariance）

之前将测距从"旋转矩形长边"改为"短边"，当时是为了解决透视压缩导致的距离高估。这次实验证明这个改动还有一个更大的好处：**短边（方块高度）对 yaw 旋转是不变的**。

```text
方块绕竖直轴旋转时：
  长边（可见宽度）→ 随角度变窄 → 旧逻辑距离会飘
  短边（方块高度）→ 不变       → 新逻辑距离稳定
```

选什么特征直接决定了算法在什么条件下失效。如果你选"正面宽度"，一转就崩；换"高度"，就没这个问题。

**更通用的认识：** 遇到检测问题时，先判断是"选错了特征"还是"需要新规则"。不是每个问题都要加过滤——有时候之前的设计已经顺手解决了，只是没测试过。

### 遮挡分级：降级曲线（Graceful Degradation）

P1 遮挡实验得出一条清晰的降级曲线：

```text
10% 遮挡 → 完全正常（距离准确、置信度 >0.89）
30% 遮挡 → 还能工作但精度下降（距离高估 ~30%）
50% 遮挡 → 完全丢失
```

好的系统不追求"什么情况都能完美处理"，而是**明确知道每种情况下的能力边界**，在超出边界时安全降级——标记为不确定、拒绝候选、或请求调整视角。

30% 这个"中间状态"暴露了当前接口的不足：`DetectionEstimate` 只能表达"检测到"或"没检测到"，无法表达"检测到了但距离不可信"。这是 `distance_valid` 字段需求的来源。

### 空间过滤必须先于时序过滤

空场景误检修复验证了一个重要顺序：

```text
正确：颜色→形状→距离(far)→时序确认
错误：颜色→形状→时序确认→距离
```

时序过滤器只管"这个东西是否连续出现"，判断不了语义正确性。一个固定在车上的橙色接线端子也能连续出现。距离过滤（空间过滤的一种）必须在时序过滤之前执行，否则远距离假候选会建立轨迹、制造歧义，即使最终不输出也会阻塞真正的目标确认。

这跟数据库查询优化同理——**最便宜的过滤条件放在最前面。** 距离比较只需要一次浮点数判断，比连续 3 帧跟踪便宜得多。

### 本次没有加新规则

侧转实验的结论是"不需要加角度拒绝规则"——这本身也是一个重要的工程判断。有时候研究的结果就是"不需要改"，这同样有价值。不加代码意味着不增加复杂度、不引入新边界条件、不需要维护新参数。

## 2026-08-13：调试链路、业务通信与部署时机

### 学到的知识一：ST-Link 不是业务串口

ST-Link 走的是 SWD 调试链路，主要用于烧录程序、暂停 CPU 和查看内存。USB 转串口模块走的是 UART 业务通信，用来传输项目定义的 `HELLO`、心跳、里程计和状态帧。

因此：

```text
Keil 看到 ARM CoreSight SW-DP
→ 证明调试线基本可用
≠ 证明树莓派与 STM32 的业务协议已通
```

### 学到的知识二：回环测试只证明链路的一段

把 USB 转串口模块的 TX 和 RX 相连，树莓派发出 `hello` 又收到 `b'hello'`，这叫 **loopback test（回环测试）**。它证明了：

- 树莓派能识别 `/dev/ttyUSB0`；
- 权限问题解决后，串口可以打开；
- 转串口模块的发送和接收基本正常。

它不能证明 STM32 固件会解析 V1 协议，因为测试时 STM32 没有参与。这叫 **证据边界**：结论不能超过测试真正覆盖的范围。

### 学到的知识三：为什么改了 STM32 程序就要重新烧录

源代码是人能读的文本，STM32 实际执行的是编译后存入 Flash 的固件。改代码只会改电脑里的文件；经过“编译→烧录”，新版本才会进入 STM32。这与修改文档后必须重新打印，纸上内容才会变化是同一个道理。

### 学到的知识四：部署应该选在“可验证的小节点”

不是每改一行上位机代码都要立即部署树莓派。这次选择暂不部署，因为当前改动还是未提交状态，而且缺少一个能在树莓派上直接运行的 V1 协议验收入口。

更合适的节奏是：

```text
完成一个小能力
→ 跑针对测试和全量回归
→ 提交形成可追踪版本
→ 部署到新目录
→ 保留旧版用于回退
```

这种做法叫 **reproducible deployment（可复现部署）**：知道树莓派上运行的究竟是哪一版，出问题时能回退和对比。

### 学到的知识二：通信通过不是控制通过

`HELLO`、`HEARTBEAT` 和 `STATUS` 通过，只能证明基础通信与安全看门狗。今晚没有向真实 STM32 发送非零 `/cmd_vel`，也没有观察四轮目标 RPM、PWM或实际运动，因此底盘速度链路仍未验收。

### 学到的知识三：重复发布者会污染证据

第一次在树莓派读取 `/robot/status` 时出现 `detail: mock hardware`、24V和 `imu_valid=true`，与真实 STM32 状态矛盾。检查发现有两个残留 `robot_bridge` 进程。清理后真实状态才显示 boot_id=1、battery=0、imu_valid=false。

这说明 ROS 话题名相同不代表数据来源相同。验收前后都必须检查并清理残留进程，不能只看话题有数据就认定来自真实硬件。第一次机械臂 smoke 的瞬时 stale 失败也可能受这些残留发布者影响；清理后连续三轮均通过。

### 学到的知识四：稳定设备身份优于枚举编号

`/dev/ttyACM0` 是本次启动的枚举编号，重新插拔后可能变化；`/dev/serial/by-id/...` 由设备身份生成，更适合作为正式配置。两者当前指向同一个设备，但可靠性语义不同。

### 今晚明确保留的缺口

- 上位机仍缺 `/cmd_vel → robot_bridge → V1 CMD_VEL` 的 ROS→伪串口端到端测试；
- 上位机仍缺 V1 ODOM/IMU → ROS话题 → localization 的端到端测试；
- ODOM与IMU ROS协方差语义仍需收尾；
- STM32虽然定义了 `RPI_SendOdom()` 和 `RPI_SendImu()`，主循环没有调用；
- STM32工程没有发现真实 IMU 驱动；
- 真实机械臂命令和状态协议尚未接入；
- 今晚没有底盘或机构真实运动，也没有烧录 STM32。

### 一根USB线如何改变故障判断

第一次启动 `robot_bridge` 时，系统持续报告目标 `by-id` 路径不存在。`lsusb` 中只有USB Hub，没有STM32，`/dev/ttyACM*` 和 `/dev/serial/by-id/` 也不存在。这证明问题位于USB枚举之前，不是ROS参数或 `dialout` 权限。

更换支持数据传输的USB线后，树莓派立即识别：

```text
0483:5740 STMicroelectronics Virtual COM Port
/dev/ttyACM0
/dev/serial/by-id/usb-STMicroelectronics_STM32_Virtual_ComPort_307A39653433-if00
```

因此调试顺序应当是：先看 `lsusb`，再看字符设备和稳定身份路径，最后才讨论权限与ROS配置。只供电不传数据的USB线会让上层软件看起来像“配置错误”，但软件无法修复一个没有被内核枚举的设备。

### 真实V1通信、失联恢复与STOP闭环

正式 `robot_bridge` 与STM32建立真实V1会话后，现场观察到：

```text
communication_ok: true
detail: decoded MCU V1 STATUS
boot_id: 1
STATUS: 约50Hz
ODOM话题: 约50Hz，静止时为零
IMU话题: 约50Hz，但 imu_valid=false
```

拔掉USB后桥接进入失败安全状态；重新插入同一设备后，节点未退出并自动重新握手，状态恢复到约50Hz。随后调用 `/chassis/stop`，树莓派成功发送“零速度帧+紧急停止帧”，STM32回传：

```text
emergency_stop: true
error_code: 9001
communication_ok: true
```

这次证据同时覆盖了“主机写出STOP”和“STM32执行后回传急停状态”，比只看ROS服务 `success=true` 更完整。STOP后通信继续正常，桥接退出后无残留进程，STM32 USB仍在线。整个过程未给执行器接通动力、未发送非零 `/cmd_vel`，小车未运动。

### 电控源码把现场推测变成了代码事实

收到的 `Four_Motor_PID_Test` STM32F427工程包含 `rpi_protocol.c`、`safety.c`、`chassis_control.c`、USB CDC入口和编译产物。只读审查确认：

- `9001` 正式定义为软件急停；
- 软件急停锁存并清空速度，通信恢复不会自动清除；
- 只有本地长按PB2白色USER KEY约1.5秒，并通过启动故障、遥控器回中、车轮近乎静止等检查后，才清急停/协议故障并重新授权；
- `physical_start=false` 时所有控制源均被停车；
- 树莓派控制看门狗为150ms，超时清除速度并返回错误码4001；
- 独立IWDG约0.5秒；
- 遥控器在线时优先接管，树莓派命令会被取出并丢弃；
- 新HELLO代表新会话，会先清除旧速度，避免重连后续跑；
- 非有限数、非法enable和超限速度会清命令并锁存协议故障。

最关键的是，当前固件把三个树莓派自动速度限值都设为 `0.0f`。这不是参数遗漏后仍可运行，而是明确的失败安全设计：限幅未冻结前拒绝所有启用的自动运动命令。因此下一步不是直接发布非零 `/cmd_vel`，而是先确认机械参数和首次架空试验限值，形成新的可追溯固件版本，再编译、烧录和重新完成安全门验证。

### 新的证据边界

压缩包源码与现场的USB身份、V1状态、9001急停行为高度一致，但仍不能仅凭压缩包证明板上Flash与该工程逐字节相同。固件侧后续应增加可读取的版本号或构建哈希，并在每次实车证据中同时记录上位机commit和STM32固件身份。
