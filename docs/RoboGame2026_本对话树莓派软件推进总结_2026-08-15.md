## 4. mock与real运行来源隔离

### 4.1 要解决的问题

如果mock节点和real节点同时发布同名ROS话题，下游节点可能交替收到两套数据。它不是简单的“后启动者覆盖前启动者”，而是两个发布者并存，导致控制和状态来源混杂。

### 4.2 实现设计

增加运行来源检查，并接入标准启动程序：

- 模拟启动只允许模拟来源；
- 真实启动只允许真实硬件来源；
- 启动时检查关键话题的发布者来源；
- 发现mock与real冲突时终止启动流程；
- 现场配置禁止启用模拟证据策略。

这相当于在标准启动入口增加一道自动门禁，不再依靠操作人员手工记住关闭哪套程序。

### 4.3 边界

该检查主要保护受控启动过程。如果系统已经运行，又有人绕过标准launch单独启动第二套发布程序，启动时检查不会天然持续重跑。因此后续仍应坚持统一launch管理，避免人为重复启动和残留进程。

## 5. STM32通信断开时的安全停车

检查并修复了 `robot_bridge` 在STM32状态通信断开后的安全行为。

修复后的流程：

```text
持续监控正确解码的STATUS
→ STATUS超过时限未更新
→ 尝试发送零速度帧
→ 尝试发送急停帧
→ 停止正常心跳
→ 标记通信不可信
→ 清除旧STATUS、ODOM、IMU和会话状态
→ 要求重新握手
→ 新握手和新状态建立前禁止非零速度
```

坏帧、无法解码的帧或普通串口活动不能冒充有效STATUS，也不能持续维持“通信正常”。

### 安全边界

如果串口已经物理断开，树莓派发送的零速度或急停帧可能到不了STM32。因此最终物理安全仍依赖STM32本地看门狗：超过规定时间收不到上位机心跳或控制帧后，STM32必须自行停车。该能力仍需真实硬件验证。

## 6. `robot_bridge`正常退出时的停车顺序

按照用户指定顺序实现：

```text
收到正常退出信号
→ 发送零速度
→ 发送急停帧
→ 关闭串口
```

测试不是只检查函数是否被调用，而是从PTY另一端读取实际串口字节流，解码后确认帧顺序正确。

同时覆盖：

- 零速度写入失败时，仍继续尝试急停；
- 急停部分写入或失败时能够报告失败；
- 只有停车帧尝试结束后才关闭串口。

## 7. PTY伪串口端到端测试框架

Linux PTY创建一对伪终端：

- 一端交给 `robot_bridge`，使其认为连接了真实STM32串口；
- 另一端由测试程序扮演STM32，发送真实V1二进制协议帧；
- 测试订阅ROS话题，检查最终输出和日志。

测试覆盖的真实软件路径为：

```text
测试程序模拟STM32
→ V1二进制串口帧
→ robot_bridge
→ ROS话题
→ localization
→ /pose
```

与直接调用内部函数相比，这类测试能发现帧解码、字段映射、节点发布、话题连接、数据过期和会话重置等集成问题。

## 11. ODOM与IMU协方差

此前协方差不够明确，容易让下游错误地把传感器理解为“完全准确”。新增可配置的保守临时值：

| 参数 | 当前临时值 |
|---|---:|
| ODOM平面位置方差 | `0.25` |
| ODOM航向角方差 | `0.1219` |
| ODOM线速度方差 | `0.04` |
| ODOM角速度方差 | `0.09` |
| IMU航向角速度方差 | `0.09` |
| 不可测量方向方差 | `1e6` |

处理原则：

- 正常ODOM使用非零方差；
- ODOM过期时速度归零，但速度方差增大，表示该零值可信度低；
- IMU无效或过期时标记不可用；
- 配置校验拒绝零、负数和非法值。

这些数值是明确标注的保守临时值，不是实机标定结果。当时相关回归121项全部通过。

## 12. `mcu_tick_ms`时间连续性检查

V1 ODOM和IMU帧都携带 `mcu_tick_ms`。新增独立时间连续性检查：

- 第一帧建立基准；
- 正常递增放行；
- 32位计时器正常回绕放行；
- 重复时间戳拒绝；
- 倒退时间戳拒绝；
- 大间隔拒绝当前帧，并以当前时间戳重建基准，使后续数据可以恢复；
- 被拒绝的帧不更新缓存，也不刷新数据新鲜时间。

ODOM和IMU使用两套独立历史，互不干扰。

新增配置：

```text
max_mcu_sample_gap_ms = 250
```

该值必须为正整数。当时相关回归129项全部通过。

## 14. 转向与IMU融合端到端测试

第三项测试让假STM32同时发送：

- `ODOM.wz_radps`
- `IMU.gyro_z_radps`
- `STATUS.imu_valid`

然后观察最终 `/pose.twist.twist.angular.z` 和 `/rosout`。

融合门控采用双重确认：

```text
STATUS说明IMU硬件可用
并且
当前IMU测量自身没有失效或过期
→ 使用IMU角速度

否则
→ 回退轮式ODOM角速度
```

端到端覆盖：

- IMU有效时采用IMU角速度；
- `STATUS.imu_valid=false` 时采用轮式角速度；
- IMU过期时采用轮式角速度；
- 正向旋转符号正确；
- 反向旋转符号正确；
- 轮式ODOM和IMU差异过大时 `/rosout` 输出告警；
- 出现差异告警时 `/pose` 关键数值仍为有限值，不产生NaN或Inf。

## 15. 第三项发现并修复的真实缺陷

首次正确运行端到端测试时，7项中有1项失败：IMU过期后没有回退轮式ODOM。

原因：

1. `robot_bridge` 已经在IMU过期后使用 `angular_velocity_covariance[0] = -1` 标记测量不可用；
2. `localization` 原先只检查 `STATUS.imu_valid`；
3. 定位节点没有检查当前IMU消息自身的不可用标记；
4. 因此STATUS仍表示IMU硬件正常时，重复发布的旧缓存可能继续影响融合。

修复后，定位节点同时检查：

- `_imu_valid`：STM32状态是否认为IMU硬件正常；
- `_imu_measurement_valid`：当前IMU测量是否仍然可用。

IMU过期约0.30秒后，定位日志明确输出：

```text
latest IMU measurement unavailable; falling back to wheel odometry
```

然后使用轮式ODOM角速度。

## 19. 证据结论

### 当前证据能够证明

- 已覆盖的软件规则在Ubuntu ROS 2 Jazzy和PTY模拟串口条件下通过；
- V1 ODOM/IMU帧能够经过 `robot_bridge` 到达ROS话题；
- 定位节点能够按状态和测量有效性选择IMU或轮式角速度；
- 已覆盖的断联、退出、过期、重启和异常时间戳路径具有自动测试保护。

### 当前证据不能证明

- 真实STM32发送频率和协议实现完全正确；
- 真实编码器和IMU的安装方向、单位及符号正确；
- 真实底盘一定按照软件模拟结果运动；
- 串口物理断开或树莓派突然掉电后，STM32本地看门狗一定在150 ms内停车；
- 当前临时协方差已经适合实车定位；
- 相机装车后的SEARCH距离和视觉参数已经合理。
