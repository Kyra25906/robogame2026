## 第 1 站：串口通信（UART）

### 大白话

串口就是两台设备之间的一根数据线。树莓派（上位机）通过 USB 线连到 STM32（下位机/MCU），双方按约定好的速度（波特率）发送 0 和 1。

### 要理解的概念

| 概念 | 一句话解释 | 在本项目中 |
|---|---|---|
| 波特率 (baud rate) | 每秒传多少位，收发双方必须一致 | `robot.yaml` 中 `baud_rate: 115200` |
| UART/USB 转串口 | 树莓派没有原生串口，靠 USB 模拟 | 设备路径 `/dev/ttyACM0` |
| 全双工 | 可以同时收发，互不干扰 | 上位机发命令、下位机回状态可以同时进行 |
| 流控制 | 防止发送太快对方来不及处理 | 本项目未使用，靠协议自身帧定界 |

### 对应代码

- `robot_bridge/node.py` 第 94-107 行：`_open_serial()` 打开串口
- `robot_bridge/node.py` 第 301-302 行：`_tick()` 中从串口读数据

### 学完后能回答

- 为什么 `baud_rate` 设错就收不到数据？
- `serial.read()` 一次能读到多少字节？谁来拼帧？

## 第 2 站：二进制协议与帧格式

### 大白话

串口只传字节（0-255 的数字）。要传"速度 0.3 m/s"这样的浮点数，需要把它拆成 4 个字节，对方收到后再拼回来。这就是"序列化"和"结构体打包"。

一个完整的"数据包"叫一帧（frame），本项目格式：

```
帧头 AA 55 → 版本号 → 消息类型 → 序号 → 长度 → 数据 → CRC校验
```

帧头 `AA 55` 就像一句话的开头标记——串口线上全是连续字节流，接收方需要一个"对齐点"来找到帧的起点。

### 要理解的概念

| 概念 | 一句话解释 | 在本项目中 |
|---|---|---|
| 字节序 (endianness) | 多字节数字先存高位还是低位 | 本项目用**小端**（little-endian） |
| struct 打包 | Python 的 `struct.pack` 把 Python 数字变成字节 | `serial_protocol.py` 所有 `pack`/`unpack` |
| 帧定界 (framing) | 在一串字节中区分"哪里是一帧的起点和终点" | 帧头 `AA 55` + 长度字段 |
| CRC 校验 | 对数据算一个校验码，收到后重算对比 | CRC-16/CCITT-FALSE |
| 序号 (sequence) | 每帧一个递增编号，用于检测丢帧和重复 | 0-65535 回绕 |
| 粘包/拆包 | TCP/串口中多帧可能连在一起或一帧分几次到达 | `StreamDecoder` 处理 |

### 对应代码

- `robogame_core/serial_protocol.py` 第 41-50 行：`encode_frame()` 打包一帧
- `robogame_core/serial_protocol.py` 第 52-70 行：`decode_frame()` 解包一帧
- `robogame_core/serial_protocol.py` 第 81-112 行：`StreamDecoder` 从字节流中切帧

### 学完后能回答

- 为什么帧头是 `AA 55`，不是 `00 00`？
- CRC 校验失败意味着什么？应该怎么处理？
- 如果收到一个长度字段写着 2000 的帧，怎么办？

## 第 3 站：编码器与轮式里程计

### 大白话

编码器装在电机轴上，电机转一圈编码器发出固定数量的脉冲。数脉冲就知道电机转了多少圈，乘以轮子周长就知道车走了多远。

**"里程计"不是 GPS**——它从"车本来在哪"开始累加位移。所以会漂移：每步有小误差，时间长了累积成大误差。因此需要 IMU 来修正方向漂移。

### 要理解的概念

| 概念 | 一句话解释 |
|---|---|
| 编码器分辨率 | 电机转一圈能产生多少个脉冲（比如 1000 PPR） |
| 减速比 | 电机转 N 圈，轮子才转 1 圈 |
| 轮式里程计 | 用四个轮子的转速推算车体的 vx, vy, wz |
| 积分漂移 | 每次微小误差随时间累积，定位越来越不准 |
| 麦克纳姆轮 | 特殊轮子，四个轮子不同组合可以全向移动 |

### 对应代码

- `robogame_core/navigation.py`：`OdometryIntegrator` 用速度积分推算位置
- `robot_bridge/node.py` 第 319-335 行：发布 `/wheel_odom` 话题

### 学完后能回答

- 为什么"上位机命令速度"不能冒充"真实里程计"？
- 编码器的 PPR、减速比、轮径三个数字只要错一个，里程计就全错——为什么？

## 第 4 站：IMU（惯性测量单元）

### 大白话

IMU 是一块小芯片，里面有一个陀螺仪（测角速度）和一个加速度计（测加速度）。本项目主要用陀螺仪的 Z 轴——车在水平面转了多少。

**IMU 测的是角速度（度/秒或弧度/秒），不是角度。** 要得到角度需要积分。积分又会漂移——静止时陀螺仪也有微小输出（零偏），积分后变成缓慢旋转。

所以定位策略是：**里程计提供位置，IMU 提供方向。IMU 失效时（未校准或数据过期）退回到纯里程计。**

### 要理解的概念

| 概念 | 一句话解释 |
|---|---|
| 角速度 vs 角度 | 角速度是"转得多快"，角度是"转了多少"——积分关系 |
| 零偏 (bias) | 静止时陀螺仪输出的微小非零值 |
| 校准 (calibration) | 上电后静止几秒，采集零偏，后续减掉 |
| 漂移 (drift) | 零偏随时间变化，校准不能完全消除 |
| 四元数 | 表示 3D 旋转的一种数学工具，比欧拉角稳定 |

### 对应代码

- `localization/node.py`：IMU+里程计融合定位
- `localization/quality.py` 第 16-25 行：`choose_yaw_rate()` 选择陀螺仪还是轮速差
- `robot_bridge/node.py` 第 338-347 行：mock 模式 2 秒假装校准

### 学完后能回答

- 为什么 `imu_valid=False` 时要用轮速差代替陀螺仪？
- 陀螺仪的单位是 rad/s，如果电控给了度/秒，不转换直接用会怎样？

## 第 5 站：安全机制

### 大白话

机器人安全不是"期望不出事"，而是"假设一切都会出事，但出事时能停下来"。

### 要理解的概念

| 概念 | 一句话解释 | 在本项目中 |
|---|---|---|
| 看门狗 (watchdog) | MCU 内部定时器，超时没被"喂"就自动复位 | MCU 150ms 没收到命令就停车 |
| 急停 (E-stop) | 物理按钮，按下直接断电/停止，不经过软件 | `emergency_stop` 字段 |
| 失联停车 | 通信断了，MCU 自己把速度归零 | 硬件安全链第 1 条 |
| 心跳 (heartbeat) | 定时互发小包，证明"我还活着" | `0x03` 消息类型 |
| 上电默认安全 | 通电后不动，直到收到明确启动信号 | `physical_start` 字段 |
| boot_id | MCU 每次重启后递增的计数器 | 检测 MCU 是否意外重启过 |

### 对应代码

- `robot_bridge/node.py` 第 229-250 行：`_on_status_boot_id()` 检测 MCU 重启
- `robot_bridge/node.py` 第 190-227 行：握手状态机
- `robogame_core/hardware_readiness.py`：`robot_status_communication_ok()` 通信健康判定

### 学完后能回答

- 为什么软件急停不能代替硬件急停？
- `boot_id` 变了意味着什么？算法应该做什么？
- "150ms 失联停车"为什么必须在 MCU 上实现而不能靠上位机？

## 最后：不需要当嵌入式工程师

你的角色是算法开发。你需要的不是"会写 STM32 固件"，而是：

- **看懂协议文档**：知道偏移 0 的 u16 是什么含义
- **写解码器**：用 `struct.unpack` 把字节变成 Python 数字
- **判断数据可信度**：时间戳对不对、值域合不合理、频率是否正常
- **安全对接**：知道什么情况下该拒绝数据、拒绝动作

你不负责让电机转起来——你负责在电机数据可信时发正确的命令，在数据不可信时拒绝发命令。
